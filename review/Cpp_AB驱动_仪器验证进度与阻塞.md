## 二、仍未通过的部分（阻塞）

### 2.1 三个真实臂全部 0 胜，且兜底率 100%

| 臂 | 胜率 | cap(兜底) |
|---|---:|---:|
| safety | **0/100 = 0%** | 113 |
| ply3 | **0/100 = 0%** | 113 |
| production | **0/100 = 0%** | 113 |

生产实际胜率约 36% ⇒ **完全不可比**。

### 2.2 根因（已确认，非猜测）

我自己写的 `enumerate_worlds` 里有一条**我拍的**上限：

```cpp
if (nf > 20) return false;   // 前沿格超过 20 就放弃
```

而真实局面前沿格数（对 1509 个真实中局点统计）：

| 统计量 | 值 |
|---|---:|
| 中位 | **22** |
| p90 | 34 |
| 最大 | 67 |

⇒ **中位就超过我设的 20**，所以绝大多数真实局面直接判失败，
   全部掉进兜底分支 ⇒ 三个臂退化成同一个确定性占位策略 ⇒ 读数无意义。

**关键自我批评**：
1. `nf > 20` 这个上限**生产代码里根本没有**，是我凭空拍的；
2. 我最初把兜底写成"随机点击"，而生产是 `process_bigger_situation`（枚举求解）；
3. 这两点叠加，使"驱动有 bug"和"局面真难"在读数上**无法区分**——
   直到 Oracle 100% 通过才把两者分开。

## 三、正确做法（已确认，但需决策）

Advisor 的判断成立：**不应继续修这个自制枚举器**。

理由：我这版是"朴素 2^nf 全枚举"，而生产用的是**约束分组递归枚举**
（`mscore.cpp:455` 的 `PartSolveCtx`，按组解 + 剪枝）。
两者是**两套语义**，我这版修得再好也不能代表生产。

### 3.1 可选路径

| 方案 | 内容 | 障碍 |
|---|---|---|
| **B1** | 把 `ab_native.cpp` 与 `mscore.cpp` 编进同一 pyd，直接 C++ 调用 `PartSolveCtx` | 两个 `PYBIND11_MODULE` 会冲突，需给 mscore.cpp 的模块定义加保护宏（= 要动生产文件） |
| **B2** | 在 `mscore.cpp` 里加一个 `run_ab` 入口（复用其枚举） | Advisor 明确反对：仪器代码与生产算法耦合，且基线二进制会与线上不同 |
| **B3** | 把 `PartSolveCtx` 逻辑**复制**到 `ab_native.cpp`（不改生产文件） | 约 300-400 行；但仍是"复制一份"，有双实现漂移风险 |
| **B4** | 整局循环留在 Python（已验证的 `ab_policy.play_one`），只把**决策**走 C++ | 不满足"全部 C++"的字面要求，但决策（最耗时部分）确实是 C++ |

### 3.2 我的建议

**B1**：给 `mscore.cpp` 的 `PYBIND11_MODULE` 加一个 `#ifndef AB_NATIVE_MERGED` 保护宏
（只加预处理保护，**不加任何逻辑**），然后两个源文件一起编译进同一个 pyd。
这样：
- 生产 `mscore.pyd` 不受影响（单独编译时行为完全一致）
- `ab_native` 可以直接 C++ 调用 `PartSolveCtx` / `wr_f`，**复用已验证的枚举**
- 不产生双实现

⚠️ 但这需要改 `mscore.cpp`（哪怕只是加 3 行宏保护），
   而你此前明确"不改生产"。**这一条需要你批准。**
