# 架构与工程域审查

> 审查基线：当前工作区、commit `cfb27da`。当前 `utils/probability.py` 为 1467 行、`main.py` 为 1239 行，行号均以本次读取版本为准。**实测**仅指主会话已给读数或我读取的现有日志；**静态**指源码可确定的事实；**推断**指尚需并发/故障注入验证的风险。本审查未修改源码。

## Summary（摘要）

目录上的 vision/deduction/probability 拆分并未形成独立模块：`Solver` 把三个 Mixin、QThread、配置、点击、缓存、统计和 UI 信号重新合并为一个隐式状态容器。最高优先级不是再拆文件，而是先封住并发与持久化边界：两个 Solver 可写相同状态文件，GUI 与工作线程还共享 `self.img`；`data.json`、`cfg.json` 直接截断重写。随后用很小的 `BoardConfig / DecisionResult / Repository` 契约收束依赖，再拆分 `_number5_1_core`（361-786 行，共 426 行）的编排职责。

## Analysis（分析）与分级问题

### P0：正确性、数据完整性与热路径失控

**P0-1 样本热路径把“每次枚举”变成全量 IO + 二次拟合。** `utils/probability.py:105-148` 每次 `_ps_observe` 都调用 `_ps_record_ms` 读取、追加并全量重写 JSON，再重拟合；`utils/probability.py:161-194` 对样本两两组合，复杂度 O(n²)；`utils/probability.py:197-205` 文档承诺 `rows[-200:]`，实际却传 `rows[:]`。调用点位于每次真实 `part_solve` 后的 `utils/probability.py:573-584`。本次只读盘点为 1777 条、159458 字节；主会话先前实测 1748 条时全量拟合约 520ms、200 条约 1.8ms。改法：先改 `_ps_fit_k(rows[-200:], ...)` 并补一条 >200 条、新旧样本给出不同 k 的窗口测试；样本追加改 JSONL 环形/有界文件，拟合按批或固定间隔触发。收益是消除“越玩越慢”和大部分热路径 IO；风险是短窗 k 更易受机器负载影响，应保留 native 模式过滤、夹限并做真实样本回归。

**P0-2 原子替换不等于并发安全，且两个文件连原子写都没有。** `_ps_record_ms`、`time_budget`、`game_stats` 分别用固定 `.tmp` + `os.replace`（`utils/probability.py:118-148,230-239`、`utils/solver.py:40-59`），可防单写者半截文件，却没有跨进程/跨实例锁和合并；两个 Solver 在 `main.py:187,229` 同时存在，耗时状态又是各自首次懒加载（`utils/probability.py:372-375`），可能基于旧副本覆盖，固定 tmp 名还可能冲突（并发后果为**推断**）。`data.json` 在 `utils/solver.py:131-148` 整文件直接 `open(...,"w")`，`cfg.json` 在 `main.py:1081-1082,1094-1095` 同样直接截断写；异常中断会留下空/半文件。改法：统一 Repository，临时文件名带进程/线程唯一标识、flush+fsync 后 replace；更新计数采用单写者队列或事务合并，启动读坏文件不得静默清空后直接覆盖。收益是断电不毁文件、并行不丢计数；风险是 Windows replace/锁语义与退出时序需要故障注入验证。

**P0-3 同一个帮助 Solver 被 GUI 线程与工作线程同时使用。** `main.py:534-536` 启动 `help_thread` 后，`main.py:562-566` 又在 GUI 调用线程直接执行其 `complete_scan`；扫描在 `utils/vision.py:157-166` 内调用 `_grab_board` 并写共享 `self.img`（`utils/vision.py:133-147`），后台帮助流程也经 `utils/solver.py:436-452` 扫描。这里是明确的共享可变状态，不只是“Mixin 不美观”。改法：最小修复是删除第二次直接扫描，统一消费后台发出的首个棋盘快照；或让 GUI 使用独立、只读截图对象，绝不共享 Solver。收益是消除交叉截图和棋盘状态错帧；风险是改变首屏时序，须补 GUI/后台同步测试。

### P1：边界、生命周期与环境可重复性

**P1-1 Mixin 的接口只是注释，没有所有权。** 组合点 `utils/solver.py:86` 下，Vision 依赖配置和图像缓存（`utils/vision.py:4-8`）；Deduction 除了 `w/h`，还直接点击、重扫、发 UI、读写帮助列表（`utils/deduction.py:41,55-104,240,255`）；Probability 反向调用 Vision、Deduction、Solver 的统计与 Qt 信号（其依赖清单在 `utils/probability.py:6-12`）。尤其 `is_play` 在 `utils/deduction.py:55,78,101` 改变整套副作用；`checked` 在 `utils/probability.py:544-610` 读写，却只在部分新局路径清空（`utils/solver.py:253,281,320,349`）；`reload()` 更新 w/h/a 等但未重算构造时的 `p`（比较 `utils/solver.py:101-111,174-188`）。最小契约建议：`BoardConfig`（不可变 w/h/a/limit/cell_width/coords）、`BoardState`（ndarray + checked 所属局 id）、`DecisionResult`（pos/confidence/prob/explanations/total）、四个窄端口 `Vision.scan`、`Actions.click`、`Telemetry.emit`、`Stats.record`。先以适配器包现有方法，不搬算法。收益是让缓存失效、配置重载和测试初始化有唯一入口；风险是适配器暂时多一层，必须禁止新旧状态并行写。

**P1-2 `_number5_1_core` 是编排、算法、设备 IO 与持久化的混合体。** `utils/probability.py:367-415` 识别/恢复局面；`420-433,628-655` 随机决策；`446-610` 分组、预算和缓存；`617-742` 胜率/PBS、帮助解释、热力图；`744-776` 点击、胜负检测、统计；`780-786` 再全量重扫。应拆为五层（而非再建一个“大 Service”）：① `partition_board` 纯函数产前沿/内部格/分组；② `enumerate_groups` 仅枚举与缓存；③ `choose_move` 仅返回 DecisionResult；④ `DecisionPresenter` 组装 heatmap/帮助项；⑤ `SolverWorkflow` 执行点击、重扫和记录。收益是可脱离 Qt/屏幕测试概率语义，随机选择也能统一；风险是 `clicks/clicks9/res_list/ck/total` 当前顺序强耦合，拆分须先固定等价 fixture。

**P1-3 强制 terminate 绕过清理，存储的 finally 不是保证。** `main.py:399-416` 对 QThread 调 `terminate()`；自动循环虽在 `utils/solver.py:389-390` 用 finally flush，但线程被强杀不能依赖 Python finally 正常完成。改法：增加协作式 cancel Event，在 `play/help` 每轮及长枚举安全点检查，等待退出后再刷新；紧急强杀只作最后兜底。收益是减少状态丢失和原生资源悬置；风险是长 C++ 调用不能即时响应，需要明确取消粒度。

**P1-4 启动环境由 cwd、机器绝对路径和 ABI 共同钉死。** `setting.py:3` 在 import 时读 `./cfg.json`；`main.py:78` 与 `utils/solver.py:101` 也按 cwd 读，图片在 `utils/vision.py:42,59` 按 cwd 读。`cpp/build.bat:9-10,35-37` 硬编码本机 Python/MSVC、cp310 和 python310.lib；仓内只有 cp310 pyd，而 `utils/native.py:33-43` 把 ABI 失败吞成纯 Python 回退，诊断函数 `report_load_error`（`57-60`）没有生产调用。改法：用 `Path(__file__).resolve()` 或冻结时 `sys._MEIPASS` 定位只读资源，可写配置/状态放显式用户数据目录；构建从传入 Python 获取 include/lib 与扩展后缀；启动页展示 native 不可用原因。收益是可从任意目录启动、换机可诊断；风险是打包后资源目录与可写目录必须分离，需源码和 PyInstaller 双路径验收。

**P1-5 依赖声明与实际运行基线不一致。** `README.md:13-16,222-228` 写 Python 3.7，`requirements.txt:1-10` 固定旧 SciPy 生态和 `pywin32==302`；但 README 自身 `43-47` 又指定 cp310，主会话实测可用环境是 Python 3.10 + pywin32 312，3.12 的 win32 DLL 不可加载。改法：声明并锁定“Windows x64 + Python 3.10”为唯一支持基线，记录实际验证过的 pywin32 版本，加启动预检（sys.version、platform、win32gui import、native 状态）；随后再考虑解除旧版本钉死。收益是避免安装成功但 import 即崩或静默失速；风险是严格 pin 会缩小未来环境范围，应以 CI 矩阵而不是放宽文档解决。

### P2：可收敛的工程债

**P2-1 重复决策与展示字典会持续漂移。** 内部格“5×5 开格数→权重→随机选点”在 `utils/probability.py:425-433,633-643,978-986` 重复，最大概率附近选点在 `950-967` 又有一份；`process_bigger_situation`（903-1069）把 `_pbs_compute_python` 的纯计算（823-901）与点击建议/解释拼接混在一起，不能只把两者当“重复代码”删除。`main.py:1138-1164` 的模板清单又与 `utils/vision.py:24-36` 重复。改法：抽 `weighted_interior_choice(candidates, scores, rng)` 与共享 `TEMPLATE_LAYOUT`，帮助字典用统一 factory。收益是修选择策略只改一处；风险是随机序列会变化，比较测试需注入 seeded RNG，而非强求旧随机轨迹。

**P2-2 死/旧路径与注释使审查成本上升。** `main.py:1223-1232` 再定义 `MyEncoder`，`utils/misc.py:13-22` 已有同实现；`main.py:202-203` 注释开局坐标、`main.py:864,874-877` 注释 UI 代码可清理。`utils/probability.py:32` 仍写 10 秒预算，实际 41 行是 30 秒；`README.md:56-65` 同时保留 0.75 降档旧规则和代码 `_WR_SLOW_FRAC=1`（`utils/probability.py:51,259-285`）的新规则。`main.spec:8` 仍列已迁移的顶层 `utils.py/window.py` 等旧入口，且 `main.spec:11` 只收 image，未声明 cfg/原生模块，打包完整性存疑（未实际打包，标**推断**）。改法：以当前架构重写 spec、删本地重复实现、让 README 只描述现行控制器。收益是降低错误维护与打包排障成本；风险是历史兼容入口可能被外部用户使用，删前先按发布说明确认。

**P2-3 测试验证了单写者，不覆盖真正的边界。** `tests/test_real_io.py:34-70` 验证 JSON 追加、损坏读和状态 roundtrip，但没有双写者、写中断、唯一 tmp 冲突测试；`tests/helpers.py:13-46` 用 `__new__` 后手工补 20 余项属性，正是隐式契约脆弱性的证据。现有 `review_test.log` 记录 97 通过/1 失败，失败为 `tests/test_ui_heatmap.py:81-90` 的旧文案断言，对应现行 `main.py:720-731`；本次未重跑测试，避免生成/改写运行数据。复跑命令：`D:\anaconda3\envs\py310\python.exe -m unittest discover -s tests -v`（在隔离输出目录并记录日志）。改法：为 BoardConfig/Repository 建正常构造 fixture，加并发与故障注入，不只继续扩充手工属性清单。

## Root Cause（根因）

根因是**职责按算法名词拆文件，但运行状态、副作用和持久化仍按“全能 Solver”共享**。因此 Mixin 并未降低耦合，反而让字段来源、缓存生命周期与线程所有权不可见；五个 JSON 也不是一个存储设计，而是不同功能各自把全局变量映射到文件。优先建立状态所有权和写入协议，比直接搬函数或一次性上大型框架更有效。

## 持久化职责与方案对比

| 文件及证据 | 当前职责 | 膨胀/风险 | 建议 |
|---|---|---|---|
| `cfg.json`，`main.py:78,1081` | 棋盘、坐标、exe 路径等用户配置 | 固定大小；直接截断写、cwd 依赖 | 保留 JSON，schema 校验 + 原子写；不放程序资源目录 |
| `data.json`，`utils/solver.py:131-148`；结构见 `probability.py:756-771` | 按置信度桶聚合 `{win,lose}` | 桶至多约 101 个，**不是无限增长**；有覆盖/截断风险 | 小文件可保留 JSON + 原子写；频繁合并时转 SQLite 聚合表 |
| `state/game_stats.json`，`utils/solver.py:34-59,218-220` | 全局 played/win 两计数 | 固定大小；多实例读改写可丢更新 | SQLite 单行 UPSERT，或限定单写者后保留原子 JSON |
| `state/time_budget.json`，`utils/probability.py:214-239,247-285` | ps_k/base/native 与 wr 阈值 | 固定大小；实例间旧快照覆盖 | 小型模型状态 JSON 足够；统一进程级 ModelStore |
| `data_time.json`，`utils/probability.py:84-87,105-158` | 原始 `(ts,size,ms,native)` 样本 | **只增不减**；全量重写 + O(n²) 拟合 | 最省改动：有界 JSONL 环形重写；长期：SQLite samples 表 + 索引/保留窗口 |

具体取舍：SQLite（WAL、事务 UPSERT、`DELETE` 保留最近 N 条）最适合需要多实例合并、查询与保留策略的场景，但引入迁移、锁和备份成本；有界 JSONL 最适合当前单机顺序样本流，追加 O(1)，达到上限再原子压实，但仍需单写者；只存聚合虽最省空间，却丢失按 size/native 重拟合所需分布，**不应**用它替代原始滑窗。建议先“窗口修复 + JSONL + 原子 Repository”，只有确需并行写入/历史分析时再上 SQLite。

## Trade-offs（权衡）

| 选项 | 利 | 弊 |
|---|---|---|
| 最小适配器契约 | 不改算法、逐步可回归 | 过渡层仍存在，需纪律防旁路 |
| 立即全面拆 Solver | 长期边界最干净 | 426 行决策与 Qt/视觉牵连大，回归面最大 |
| JSONL/原子 JSON | 依赖少、容易排障 | 多写者与复杂查询能力弱 |
| SQLite WAL | 事务、合并、窗口清理可靠 | 模式迁移和运维复杂度上升 |

## 构建顺序与依赖标注

1. **类型与接口**：BoardConfig/BoardState/DecisionResult、Repository 接口；无先序依赖，被以下全部步骤消费。
2. **核心逻辑**：窗口拟合、统一随机选择、纯 PBS/决策分层；依赖步骤 1，被集成层消费。
3. **集成与存储**：路径解析、原子写/单写者、配置 reload 和缓存局 id；依赖 1-2，被工作流消费。
4. **线程与 UI**：取消协议、去除 GUI 对 Solver 直接扫描、Presenter；依赖 1 和 3，被端到端流程消费。
5. **测试**：先用现有局面锁定等价，再加并发/中断/任意 cwd/ABI 失败测试；各实现步同步补，最终依赖 1-4。
6. **文档与打包**：更新 requirements、README、spec；依赖已验证的 1-5，禁止先改声明后补实现。
