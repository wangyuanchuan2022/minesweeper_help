生成时间：2026-11-02
本文件只回答两个问题：**(一) Arbiter 的雷生成算法是什么；(二) 纯规则基线胜率是多少。**

口径从严：**不包含视觉输入处理，不包含点击输出**。只评估"决策算法本身"。

## 一、Arbiter 0.52.3 的雷生成算法（逆向还原）

### 1.1 一句话结论

**纯拒绝采样（uniform rejection sampling），循环体内没有任何排除规则。**

「首点必不是雷」不是生成时的排除，而是 **延迟布雷**：棋盘在首次左键点击之前
没有雷；首次点击先打开该格（含 flood-fill 展开），然后才布雷，而拒绝采样
只判「该格是否为未开」——已打开的格子自然被跳过。

### 1.2 还原出的算法（逐字对应机器码）

```
procedure PlaceMines(mineCount: Integer);      // 函数 @0x4d9228，mineCount 由 EAX 传入
var x, y: Byte; count: SmallInt;
begin
  count := 1;
  while count <= mineCount do
  begin
    repeat
      x := Random(Width  + 1);                 // call 0x4033c8, 参数 = [0x547108]+1
      y := Random(Height + 1);                 // call 0x4033c8, 参数 = [0x546fe8]+1
    until GetCell(x, y) = UNOPENED;            // cmp al, [esi]  —— 唯一的过滤条件
    SetCell(x, y, MINE);                       // mov ecx,[0x546d14] 棋盘数组
    Inc(count);
  end;
end;
```

`Random` 本身（@0x4033c8，REA 反编译逐字）：

```
RandSeed := RandSeed * 0x08088405 + 1;         // Delphi System.Random（LCG）
Random(n):= (uint64)n * RandSeed >> 32
```

`RandSeed`（全局 `0x544008`）的初值来自 **CryptGenRandom**（@0x4d47ac）：

```
BVar1 := CryptGenRandom(hProv, 4, @local_8);
RandSeed := local_8 * 0x1000000 + (local_8 shr 8 and $ff) * $10000
         + (local_8 shr 16 and $ff) * $100 + (local_8 shr 24);
```

即：**每局种子是密码学随机的，序列本身不可预测**；可预测的只有"分布"：
每格等概率、无位置偏好、无相邻限制、无 3BV 或边界排除。

### 1.3 证据链（每条都可用 `tools/arbiter_generation_truth.py` 复算）

| 编号 | 证据 | 复算结果 |
|---|---|---|
| E1 | UPX 加壳 → 脱壳：493,056 → 1,944,576 字节，18 → 5305 函数 | 已实测 |
| E1b | 编译器 Borland Delphi（`x86:LE:32:default:borlanddelphi`） | Ghidra 加载日志 |
| E2 | LCG 常数 `0x08088405` 全代码段**仅 1 处**（VA 0x4033d1） | ✅ 1 处 |
| E3 | `CryptGenRandom` 存在，且唯一调用者是 WinMain 初始化 | ✅ |
| E4 | 布雷函数 @0x4d9228 关键指令逐条核对 | ✅ **8/8 OK** |
| E4b | 函数体内引用 宽(2处)/高(2处)/棋盘(1处)，**雷数 0 处** | ✅ 决定性 |
| E5 | `call 0x4d9228` 共 6 处，全在函数 0x5313b8 的不同分支 | ✅ 6 处 |

E4b 是关键：雷数不在函数体内被读取，而是由 EAX 传入（`8b f8` = `mov edi,eax`），
这证明它就是「按给定雷数布雷」，而不是别的什么。

### 1.4 与本项目模拟器的对应关系

本项目 `sim/minesweeper_sim.py` 用的是：

```
generate(first_x, first_y):  先构造 safe = 首点 3x3 区域 → 从其余格抽 mineCount 个
```

**行为等价**（首点区域必无雷），但机制不同：
- Arbiter：先打开 → 再布雷 → 拒绝采样跳过已开格
- 本项目：先排除 3x3 → 再布雷

差异：Arbiter 实际被跳过的区域 = 首次 flood-fill 展开的全部格子（可能大于 3x3），
所以它的首点安全区**通常比 3x3 更大**，开局更宽松。

### 1.5 勘误记录（必须保留，防止后人重踩）

本项工作过程中出现过 3 次错误判断，均已自我推翻：

1. 误把 0x4d9228 的入参读成"坐标序列"（实为"雷数"，由 EAX 传入）。
2. 误把 6 个调用点后的 0x52c7ac 读成"首点保护"（实为"按坐标读屏幕像素"）。
3. 曾判定"14 个模板因 cv.error 被吞而成为死模板"——子席实测证伪：
   OpenCV 4.5.4 在模板大于图像时会自动交换，真实机制是"量级不可比，
   大模板永远赢不了争"，不是异常被吞。详见 `review/视觉域.md`。

## 二、纯规则随机基线（2000 局实测）

### 2.1 结果

| 策略 | 胜率 | 95% CI（Wilson） | 平均踩雷步数 |
|---|---:|---|---:|
| **B1 纯瞎猜**（从不推理，每次均匀随机点未开格） | **0/2000 = 0.000%** | [0.00%, 0.19%] | **4.3** |
| **B2 纯推理 + 瞎猜**（只用确定性规则，无解即随机） | **15/2000 = 0.750%** | [0.46%, 1.23%] | **64.1** |

复现命令：

```bat
cd D:\python\projects\minesweeper_help
D:\anaconda3\envs\py310\python.exe sim\baseline_winrate.py --games 2000 --seed 20261102
```

### 2.2 口径（写死，避免误读）

**包含**：
- 真实扫雷规则：30×16、99 雷、点开 0 触发 flood-fill、开完所有非雷格即胜
- 首点安全（3×3 约定，与 Arbiter 行为等价）
- B2 的"确定性规则"= 数字减已标雷数 = 相邻未开格数 → 全雷；数字 = 已标雷数 → 全安全
  （这是纯人类可复现的推理，不含概率计算、不含搜索）

**排除**：
- 视觉识别、点击、等待、UI —— 全部不参与
- 任何概率枚举 / win_rate 搜索（那是 B2 之上的东西）

**因此这两个数是"无智能下限"，不是项目算法的胜率。**
项目 `number5_1`（含分组枚举 + 胜率搜索 + DP 聚合）应显著高于 B2，
其独立度量脚本为 `sim/algorithm_winrate.py`（同样排除视觉与点击）。

### 2.3 这两个数说明什么

- **B1 = 0%**：专家局平均第 4.3 步就踩雷。99 雷 / 480 格 ≈ 20.6% 雷密度，
  纯随机几乎不可能连续避开。这证明"随便点"在专家局完全不可行。
- **B2 = 0.75%**：纯逻辑能撑到平均第 64 步，但专家局需要几十次**猜测**，
  每一次猜测都是独立的风险乘子。这解释了为什么胜率上限低。
- **差距 B2 0.75% vs 项目真实 33.86%**（`state/game_stats.json`：107 胜 / 316 局，
  口径已核对：107/316 = 33.86%）：
  这 **45 倍**的差距全部来自"猜得更准"——即概率枚举与胜率搜索。
  这就是算法改进唯一有价值的方向。

## 三、算法极限胜率怎么测（给你自己跑）

### 3.1 脚本

`sim/algorithm_winrate.py` —— 只包决策算法，硬屏蔽视觉与点击：

```python
self.s.complete_scan = lambda cell_value, no_10=True: cell_value   # 视觉屏蔽
# 不 sleep、不 pyautogui、不走 UI                                     # 点击屏蔽
```

求解器只能拿到 `BoardView`（未开/已开数字/标记/剩余雷数），
每局开始跑 `audit_no_leak()` 审计，**真实雷位物理上不在视图里**。

### 3.2 你自己跑的命令

```bat
cd D:\python\projects\minesweeper_help
set QT_QPA_PLATFORM=offscreen
D:\anaconda3\envs\py310\python.exe sim\algorithm_winrate.py --games 200
```

单局实测约 5.9 秒（含 `number5_1` 全链），200 局约 **20 分钟**。
样本量建议：200 局 → CI 半宽约 ±3pp；500 局 → ±2pp。

### 3.3 这个数字的用途

它是**算法上限**，因为视觉被替换成"100% 正确识别"。所以：
- 算法改进 → 这个数上升 → 说明改进有效
- 这个数不变 → 说明改的只是速度/工程，不是决策质量

对比基准：项目真实对局 **33.86%**（107/316，`state/game_stats.json`，含视觉误识、含点击时序损耗）。
两者差距 = 视觉与执行损耗的总和。
