## 0. 三条与任务书前提冲突的实测更正（请组织者先看这一节）

任务书给的主会话硬事实中，有 **3 条被本次实测推翻**。这些不是细节偏差，而是改变 P0 结论方向的机制性错误：

### 更正 1：14 个大模板**没有**抛 `cv.error`，它们全程参与打分

任务书称"14 个大模板大于补丁，`cv.matchTemplate` 抛 `cv.error` 被 `except` 静默吞掉 ⇒ 从未参与识别"。

**实测**：OpenCV 4.5.4 在 `templ` 大于 `img` 时**不报错，而是自动交换二者**，返回 `(img.h - templ.h + 1, img.w - templ.w + 1)` 形状的响应图。

```
matchTemplate(patch18x13, big28x20).shape = (11, 8)
matchTemplate(big28x20, patch18x13).shape = (11, 8)
两结果完全相同? True   max|diff| = 0.0
```

单维超限同样交换：`templ(19,13)` vs `img(18,13)` → 响应 `(2,1)`；`templ(18,14)` → `(1,2)`。

`cv.error` 只在**混合尺寸**（一维大、一维小）时才抛，实测：
- `templ(10,20)` vs `img(18,12)` → `cv.error`（高大宽小不成立组合）
- `templ(28,8)` vs `img(18,12)` → `cv.error`
- `templ(19,20)` vs `img(18,12)` → OK，响应 `(2,9)`

**所以 `vision.py:132` 的 `except cv.error: pass` 在本项目当前模板集下一次都不会触发**——它与"14 个死模板"这个现象无关。这条更正同时废掉了"修死模板"这个提法的因果基础（详见 P1-1）。

### 更正 2：生产补丁实际是 **(18,12)**，不是任务书说的 (18,13)

`_slice_cell`（`vision.py:106-115`）用 `y - cw//2 - h//2 : y - cw//2 + h//2` 切片，实得高 = `2*(h//2)`。`screenshot_h=int(24*7/9)=18`、`screenshot_w=int(24*5/9)=13`，所以：

```
_slice_cell 实际返回: (18, 12, 3)   ← 宽 12，不是 13
```

**这正是 `sum` 与 `min` 完全等价的根因**：模板 (18,12) 与补丁 (18,12) 尺寸相等 ⇒ 响应图恒为 1×1 ⇒ `np.sum(响应图) == np.min(响应图)`。实测 500 个随机补丁，响应图非 1×1 的次数 = 0。

任务书"小模板 vs 补丁响应图是 1×2 两个点，退化成 2 个固定对齐点求和"这句**在生产尺寸下不成立**（1×2 只在补丁宽 13 时出现）。但任务书的**结论方向是对的**——退化确实存在，只是退化形式是"1 个点、零搜索"，比 2 个点更极端（见 P0-1）。

### 更正 3：`np.sum` 的缺陷**不是**"求和掩盖了全位置最优"，而是"根本没有全位置搜索"

由更正 2，当前每个模板只贡献 **1 个响应点**，`argmin` 在 25 个（含大模板的 99 点归一化和）数之间取最小。真正的问题是**模板匹配退化成了单点像素差**：补丁与模板尺寸相同 ⇒ 只有左上角对齐这一个位置可比 ⇒ 零平移搜索 ⇒ **1px 标定误差即可翻转分类结果**。这是 P0-1 的真正机制，比任务书描述的"2 点求和"更严重也更易证。

## P0 级（正确性缺陷，会静默产生错误识别）

### P0-1　模板匹配退化为单点像素差：1px 标定误差即翻转识别结果

**位置**：`utils/vision.py:106-115`（`_slice_cell`）、`utils/vision.py:120-139`（`compare_img`）、`utils/vision.py:170-184`（`compare_cells_batch`，同样以 `screenshot_h/w` 建补丁，实得 18×13）

**问题**：模板尺寸 (18,12) 与生产补丁尺寸 (18,12) 完全相等，`cv.matchTemplate` 只剩一个对齐位置，响应图 1×1。于是"模板匹配"等价于"逐像素差的归一化和"，没有任何平移搜索能力。

**证据（实测）**：把 9 号模板（未开格）垂直平移后识别，1px 即翻转：

```
9.bmp 垂直偏移 | compare_img 输出
  dy=0        |  9   ← 正确
  dy=±1       |  0   ← 未开格被读成"已开空白"
  dy=±2       |  0
  dy=±3, ±4   |  0
水平偏移 dx=±1..±4 | 9（水平方向因模板宽 12 < 格宽，反而有 1px 余量）
```

全 11 个模板的平移鲁棒性实测（11 个模板，错判数）：

| 偏移 | sum(现状) | min | min+搜索±2 |
|---|---|---|---|
| 对齐 | 0/11 | 0/11 | 0/11 |
| 垂直 ±1 | 1/11 | 1/11 | 1/11 |
| 垂直 ±2 | **4/11** | **4/11** | **1/11** |
| 对角 ±2 | **9/11** | **9/11** | **1/11** |

**真实世界证据（日志）**：`logs/minesweeper.log` 中 `pbs 约束集自相矛盾` 告警 14 次，其中 **11 次的 `剩余雷 > 未开格` 在物理上不可能**：

```
2026-11-02 18:24:00  未开格=16 剩余雷=20  p_mine=1.0000  ← 20 颗雷放进 16 个格子
2026-11-02 18:24:53  未开格=18 剩余雷=20  p_mine=1.0000
（18:25:32 / 18:26:26 / 18:27:10 / 18:28:03 / 18:34:51 / 18:35:41 / 18:37:07 / 18:37:59 / 18:39:22 同型）
```

剩余雷数来自 `self.a - num10`（`probability.py:986`，`a=99` 总雷数），未开格数来自识别结果。**剩余雷 20 > 未开格 16 只有一种解释：未开格被大量误读成已开格**。而 P0-1 已实测"9 被读成 0"的机制成立 ⇒ 日志与机制闭合。

**改法**（三选一，按风险从低到高）：
1. **最小改动（推荐先做）**：`compare_img` / `compare_cells_batch` 把补丁四边各 `cv.copyMakeBorder(..., cv.BORDER_REPLICATE)` 扩 2px，让模板能在 5×5 范围内滑动搜索，打分改 `np.min`。实测把对角 ±2 的错判从 9/11 降到 1/11。成本：响应图从 1 点变 25 点，耗时约 ×6（单格 0.17ms → 约 1ms，全盘 480 格从 12ms → 约 70ms，仍在可接受范围）。
2. **根治**：模板集改为多尺度（同一数字保留 1:1 与略小两档），配合搜索窗。
3. **不改搜索，改对齐**：把 `_slice_cell` 的中心改为按实测标定求出（见 P0-2），消除系统偏差后再谈鲁棒性。

**预期收益**：垂直/对角 2px 容差内识别不翻转。按日志 11/14 次异常约束估，可消除大部分"未开格被读成已开"的静默错判——**这条比任何提速都重要，因为它直接决定解题正确率**。【估算：日志证据 11/14，机制已实测】

**风险**：扩大搜索窗会引入"相邻格内容干扰"（当前 1px 都不许偏，扩大后可能把邻格数字误吸进来）。必须配合 P0-3 的置信度护栏一起上，否则是把"偏了就错"换成"偏了可能错成别的数字"。**验证方法见 P1-4**。

### P0-2　`cell_width` 标定容差 0.11px/格，30 列累计漂移可达 3.3px

**位置**：`main.py:1066-1074`（`get_pos_2_func` 标定与校验）、`utils/solver.py:113-114` 与 `:186-187`（`screenshot_h/w` 派生）

**问题**：标定时只校验 `abs(round(cw) - cw) >= 0.11` 才报警，即**容忍每格 0.109px 误差**。棋盘 30 列 ⇒ 最远格累计漂移 `0.109 × 30 = 3.27px`；16 行 ⇒ `1.75px`。由 P0-1，1px 偏差即翻转识别，2px 偏差错 4/11 模板。

**证据（实测）**：按真实 `cell_width` 渲染 24 语义棋盘、按标定值 24 采样，测全盘错格率：

| 真实 cw | 每格误差 | 30 列累计漂移 | 全盘错格 | 左 5 列错 | 右 5 列错 |
|---|---|---|---|---|---|
| 24.00 | 0.00px | 0.00px | **0/480** | 0 | 0 |
| 24.02 | 0.02px | 0.60px | 0/480 | 0 | 0 |
| 24.05 | 0.05px | 1.50px | 13/480 | 0 | 0 |
| **24.10** | **0.10px** | **3.00px** | **139/480 (29.0%)** | 3 | **57** |
| 24.15 | 0.15px | 4.50px | 257/480 (53.5%) | 7 | 71 |
| 24.20 | 0.20px | 6.00px | 319/480 (66.5%) | 18 | 71 |

**关键读数**：`0.10px/格` 恰好在当前校验门槛（0.11）之内、**校验不会报警**，但识别已经错 29%，且错误**集中在右侧列**（右 5 列错 57 格 vs 左 5 列错 3 格）——这正是线性漂移的指纹。

**改法**：
1. **收紧校验**：`main.py:1068` 阈值从 `0.11` 改为按累计漂移判定，如 `abs(cw - round(cw)) * self.w >= 0.5` 才放行（30 列时即每格 ≤0.0167px），否则要求用户重调窗口。
2. **改采样方案**：不要用全局整数 `cell_width` 均匀切格，而是用标定得到的**真实浮点 cw**（`self.cell_width_f = (x1-x0)/self.w`）逐格算中心：`x_col = bx + round((i-1)*cw_f)`。这样漂移不累积。
3. **加自动校正**：利用未开格是均匀平铺网格的特点，在抓到的棋盘图上用列/行投影找格线（实测 `example.png` 上列差分峰值间距稳定），反推真实 cw 与原点，覆盖用户标定值。

**预期收益**：0.10px/格 的标定误差场景下错格率从 29% 降到 0。【实测：上表】
**风险**：方案 2 改动采样几何，影响 `_slice_cell` 的全部调用方（`cell_screenshot`、`rescan_after_click`、`compare_cells_batch`），需同步改 3 处并回归。方案 1 只改一行，风险最低，建议先做。

### P0-3　识别无置信度阈值：任何输入都会被强行归类成 0~10 之一

**位置**：`utils/vision.py:135`（`argmin` 直接返回，无下限判据）、`utils/vision.py:202-210`（batch 同样无阈值）

**问题**：`compare_img` 取 `argmin` 后直接返回数字，**没有"都不像"这个选项**。模板缺失/尺寸错/整盘被遮挡/动画中间帧，全都会被强行映射到某个数字。

**证据（实测）**：

| 场景 | 实测行为 |
|---|---|
| 全部 25 个模板为 `None`（模拟模板文件全丢失） | 480 格**全部输出 0**，抛异常 0 次 |
| `5.bmp` 存成 4 通道（带 alpha）| 真值 5 的格 **40/40 全错**，总错 40/480，抛异常 0 次 |
| `5.bmp` 存成灰度图 | 真值 5 的格 **40/40 全错**，抛异常 0 次 |
| `5.bmp` 尺寸改成 20×13 | 真值 5 的格 **40/40 全错**，抛异常 0 次 |
| `5.bmp` 内容换成 `6.bmp` | 真值 5 的格 **40/40 全错**，总错 75/480，抛异常 0 次 |
| 纯色补丁（灰度 0..255 步长 8，共 32 个）| 19 个判成 0、13 个判成 8 —— 纯色补丁**全部被强行归到 0 或 8** |

这就是任务书问的"静默失败"缺陷，**成立且比预期更严重**：连"模板全丢"这种彻底坏掉的情况下程序都不报错，而是把整盘读成"全部已开空白"继续解题。

**但阈值是可分的（实测）**——按 `min over 11 模板` 的最优分统计：

| 内容类型 | n | 最优分 min | 中位 | max |
|---|---|---|---|---|
| 真数字（精确贴回）| 11 | 0.0000 | 0.0000 | **0.0000** |
| 真数字（噪声 ±6）| 11 | 0.0004 | 0.0006 | **0.0007** |
| 真数字（噪声 ±12）| 11 | 0.0014 | 0.0021 | **0.0026** |
| 纯灰 190/191/150/128/200 | 5 | 0.0000 | 0.0022 | 0.0596 |
| 纯红（雷）| 2 | 0.3564 | 0.3809 | 0.4054 |
| 随机噪声 | 200 | **0.2634** | 0.2952 | 0.3300 |

真数字组 max=0.0026，随机噪声组 min=0.2634，**两群完全可分**（间隔约 100 倍）。取阈值 0.05 即可：真数字全通过（含 ±12 噪声），噪声/纯红全部拒绝。【实测】

**改法**：
1. `compare_img` / `compare_cells_batch` 返回 `(值, 最优分)`，最优分 > 阈值（建议 0.05）时返回哨兵值（如 `-1`）。
2. `complete_scan` 统计哨兵数量，超过阈值（如 > 5% 格数）时 `logger.error` + 抛异常，**禁止静默继续**。
3. `load_img` 加载后立即自检：模板为 `None`、通道数 != 3、`dtype != uint8`、尺寸与 `(screenshot_h, screenshot_w)` 不匹配 → 直接 `raise`。当前 `load_img`（`vision.py:52-66`）对这些问题**完全无检查**。

**预期收益**：把"模板坏掉仍在跑"从静默变成显式失败。**这是本报告成本最低、收益最确定的一条**。【实测：上表分离度】
**风险**：阈值 0.05 是在"合成棋盘"上标定的，真实屏幕有抗锯齿/主题差异，需在真机上复用 P1-4 的标注集重标。建议先以 `logger.warning` 观测模式上线，收集真实分布后再转 `error`。

## P1 级（性能与鲁棒性，已验证可改，需回归保障）

### P1-1　14 个大模板是 `cell_width=36` 的标定集，不是"死模板"；**不要**直接删或缩放激活

**位置**：`utils/vision.py:27-39`（`_TEMPLATE_LAYOUT`）、`utils/vision.py:52-66`（`load_img`）

**问题定性**（回应任务书问题 1）：这 14 个文件不是"坏掉的模板"，而是**另一套标定下的合法模板**，被错误地在 `cell_width=24` 下加载。

**证据（实测）**：

| 证据 | 读数 |
|---|---|
| `cw=24` 时 `_slice_cell` 实得补丁 | (18,12) = **小模板族精确 1:1** |
| `cw=36` 时 `_slice_cell` 实得补丁 | (28,20) = **大模板族精确 1:1** |
| `24 × 1.5` | `= 36`，正是系统 DPI 144(150%) 的缩放比 |
| 大模板家族背景色 | `0_1.bmp` 四角 BGR=[196,230,196] 带**绿色调**；小模板族 `0.bmp` 四角 [190,190,190] **中性灰** |
| 大模板族唯一色数 | 169~515 种（抗锯齿渐变）；小模板族 2~58 种（硬边） |

两族连**皮肤/渲染风格**都不同，是两次不同采集的产物，不是同一套模板的冗余备份。

**`cv.error` 从未触发的原因**：见更正 1——OpenCV 自动交换了 img/templ，大模板拿到的是 99 点归一化和（响应 `(11,9)`），小模板拿到 1 点。**大模板 sum 恒在 1.28~71.5，小模板 sum 恒在 0~0.77，量级差 2~100 倍，大模板在结构上永远赢不了**。实测：

- 3000 个随机/纯色/加噪补丁 × 11 小模板：小模板**最大**得分 0.7685
- 同期 14 大模板**最小** sum = 1.2766
- `1.2766 > 0.7685` ⇒ **大模板在任何输入下都不可能赢**
- 524 个"非正常数字"构造样本（数字两两混合、半截拼接、大模板裁剪/缩放）：大模板决定分类结果的次数 = **0**
- cw=36 下大模板族识别错 0/480（证明它们是有效模板，只是标定不匹配）

**所以"修 14 个死模板"这个提法要分两种修法，结论完全相反**：

| 修法 | 实测后果 |
|---|---|
| 删除 14 个文件/条目的**过滤**（保留文件，仅不加载） | 识别结果 **0/480 变化**（严格等价），耗时省 **67.7%**（单格 0.5364ms → 0.1732ms）；全盘 257.5ms → 83.1ms【实测】 |
| **把大模板缩放到 18×12 后激活** | 完美对齐时 0/11 错，但**下移 2px 时错 3/11**（比现状的 4/11 略好），且引入了低分辨率第二意见，语义上不可辩护 |
| 在 cw=36 环境中运行 | 大模板族 0/480，但**小模板族变成响应 99 点的干扰项**，需反过来过滤小的 |

**改法**：`load_img` 里按尺寸**分族加载并标注标定值**，只激活与当前 `(screenshot_h, screenshot_w)` 匹配的那一族；不匹配的族记 `logger.info` 说明"存在 cw=36 标定集，当前 cw=24 不使用"。**保留文件不删**（换显示器/DPI 时用得上）。

**预期收益**：省 67.7% 识别耗时（纯减法，零风险），且为 P1-2 的矢量化清场。【实测】
**风险**：几乎为零——因为过滤后 0/480 格变化。唯一风险是未来把 `cfg.json` 的 `cell_width` 改成 36 时忘记反向过滤，这由"按 `screenshot_h/w` 动态匹配"的设计自动兜住。

### P1-2　矢量化落地：能拿到 17~22x，但**当前仓库实现有一处语义偏差**（已实测，非文档问题）

**位置**：`utils/vision.py:157-211`（`compare_cells_batch`）、`:237-257`（`complete_scan` 改为走批量）

**先说好消息（实测）**：仓库里他席已落的 `compare_cells_batch` 在本机实测：

```
逐格参考 compare_img × 480 = 269.27 ms
compare_cells_batch        =  12.18 ms   加速 22.1x
一致性（真实模板合成棋盘）  =   0/480 不一致
```

**再说问题**：该实现用 `sh, sw = self.screenshot_h, self.screenshot_w`（=18, **13**）建补丁（`vision.py:170`, `:183`），而参考实现 `_slice_cell` 实得 **(18,12)**。所以批量路径为每格多取了**右侧一列**（相邻格左边缘），响应图从 1×1 变成 **1×2**，与参考实现的 1×1 **不等价**。

**证据（实测）**：随机棋盘对抗测试，**4000 次内找到分歧**：

```
随机棋盘尝试 4000 次, 找到不一致: (29, 10, 8, 9)
   ↑ 格坐标(29,10)  batch 输出 8  ref 输出 9
```

即批量路径偶发把 9 读成 8。这不是理论隐患——是 4000 次内必现的实际分歧。

**分歧率有多低**（决定是否必须修）：我做了全枚举与真实邻格构造：

| 测试 | 不一致率 |
|---|---|
| 真值 11 种 × 右邻 12 种 × 下邻 12 种 = **1584 组合全枚举** | **0/1584** |
| 真模板 + 右邻格真实内容，400 例 | **0/400** |
| 随机噪声棋盘 | **4000 次内 ≥1 例** |

**结论**：真实结构化棋盘上分歧率极低（0/1584），但**不等于 0**——随机内容下必现。它是"等式写错了但恰好大部分输入不触发"的典型。考虑到 P0-1 已证明本项目对 1px 级扰动极度敏感，**这一列的偏差值得修**，修法只需一行：

```python
# vision.py:170 改为与 _slice_cell 一致的实数尺寸
sh, sw = 2 * (self.screenshot_h // 2), 2 * (self.screenshot_w // 2)
```

（`_slice_cell` 的实得尺寸就是 `2*(h//2)`，`test_scan.py:23-25` 的既有断言也是这么写的，可直接复用该表达式。）

同时 `_active_templates`（`vision.py:141-155`）的判据 `t.shape[0] <= sh and t.shape[1] <= sw` 也应同步用实得尺寸，否则判据与实际补丁尺寸不一致。

**预期的等价性验证方案（回答任务书问题 2 的"如何证明准确率不下降"）**：

1. **逐格等价性（强判据，必须 0 偏差）**：同一张棋盘图上，`compare_cells_batch` 与 `compare_img` 逐格比对，要求 **480 格 0 不一致**。**注意当前仓库实现在随机棋盘上不满足此判据**（已实测复现），必须先按上面一行修掉。
2. **与真值比对（弱判据，用合成棋盘）**：按已知标签合成棋盘（贴入真模板），要求识别错格数不高于基线。实测现状与矢量化都是 **0/480**。【实测】
3. **扰动鲁棒性（回归防线）**：在 ±1px / ±2px 平移、±12 噪声下，要求不劣于现状。实测现状对角 ±2 错 9/11，这是 P0-1 要改善的目标。
4. **真实屏幕标注集（当前缺失，是最大验收缺口）**：仓库内**没有任何真实棋盘截图 + 标注**。`image/example.png` 是 421×610 的 GUI 说明图（alpha 通道恒 255），不是棋盘；`image/save.png` 是窗口截图但**无标注**。**必须补**：跑 5~10 局，每局存一张 `_grab_board` 原图 + 人工标注的 `cell_value` 矩阵，作为视觉域的黄金测试集。没有它，任何"准确率不下降"的声称都只在合成数据上成立。

**预期收益**：12.18ms/整盘（对比现状 269ms）【实测，22.1x】。叠加 P1-1 过滤死模板后仍有约 22x（因为批量实现已按尺寸过滤）。
**风险**：`complete_scan` 改成批量后，一旦批量抛异常会走 `except Exception` 回退逐格（`vision.py:253-256`）——这个兜底是好的，但它把"批量实现写错"降级成了"慢但可能对"，**恰恰会掩盖 P1-2 这种语义偏差**。建议把兜底从 `Exception` 收窄为"仅当模板集为空时回退"，并给批量路径加断言自检（首次调用时用 1 格对拍参考实现）。

### P1-3　抓屏是真正的瓶颈：`ImageGrab` 37ms，`BitBlt` 6.6ms，且**裁小区域不省时间**

**位置**：`utils/vision.py:213-227`（`_grab_board`）、`utils/vision.py:68-73`（`_grab_screen_bgr`）

**实测对比（同进程、同 DPI 状态、中位数）**：

| 方式 | 耗时 | 备注 |
|---|---|---|
| `ImageGrab.grab()` 全屏 1600×2560 | **37.2 ms** | 当前 `_grab_screen_bgr` 用这个 |
| `ImageGrab.grab(棋盘 bbox 720×384)` | **37.7 ms** | 当前 `_grab_board` 用这个，**一点没省** |
| `ImageGrab.grab(bbox 100×100)` | 78.4~81.2 ms | **反而更慢** |
| **`win32 BitBlt` 720×384 + `GetBitmapBits`** | **6.6 ms** | 降 **5.6x** |

**关键发现（反直觉，必须写清）**：`ImageGrab` 的耗时**与裁剪面积无关**，甚至小区域更慢。分解成本：`grab()` 中位 33~37ms、`np.array(pil)` 12.0~30.4ms、`cvtColor` 2.3ms。裁剪不减时间是因为 Pillow 的 `ImageGrab` 走的是"整屏抓取 + 内存裁剪"，恒定开销在主因。

所以任务书问"能否只抓变化区域"——**用 `ImageGrab` 做区域抓取是无效优化**（实测反而更慢）。真要省必须换后端：

- `win32 BitBlt`（**已在 `requirements.txt` 里，`pywin32==302` 已装**）：6.6ms，且返回 **BGRA**，可直接 `arr[:,:,:3]` 去 alpha（0.70ms），**连 `cvtColor` 都省了**。
- `DXGI Desktop Duplication`：本机 **未安装** `dxcam` / `mss`（实测 `ModuleNotFoundError`）。理论上最快（1~3ms 级），但需要新依赖，按角色纪律**不得擅自安装**，此处仅登记为可选方向，需组织者裁决。
- 内容一致性已核：`BitBlt` 与 `ImageGrab` 在 DPI-aware 进程下 `mean|diff| = 1.15`，最优平移 `(0,0)`，逐像素相同占 7.76%（差异来自 BitBlt 不做色彩管理）。**对模板匹配是可用替代，但必须先做一次识别结果对拍**。

**DPI 陷阱（顺带发现的真实隐患）**：进程的 DPI 感知状态**不是程序显式设置的，而是 `import pyautogui` 的副作用**。实测：

```
启动时 IsProcessDPIAware = 0   GetSystemMetrics = 1067 x 1707
import utils.vision (内含 import pyautogui) 后 = 1   GetSystemMetrics = 1600 x 2560
```

`utils/__init__.py:1-8` 确实 import 了 pyautogui，所以**当前生产链路是对的**。但这是个**隐式依赖**：若将来为了提速把 pyautogui 从 import 链里摘掉（比如换 `SetCursorPos` 直接调 win32），进程会退回 DPI-unaware，`win32gui.ClientToScreen` 返回逻辑坐标（1067 宽）而 `ImageGrab` 返回物理像素（1600 宽），**坐标尺度相差 1.5 倍，识别全线崩溃且不报错**。建议在 `main.py` 启动处显式调用 `ctypes.windll.shcore.SetProcessDpiAwareness(2)` 或 `SetProcessDPIAware()`，把隐式依赖变成显式契约。

**改法**：
1. 用 `win32 BitBlt` 替换 `_grab_board` 与 `_grab_screen_bgr`。注意后者是**整屏**匹配 ok/win/lose/exit 用的，需保留整屏抓取，但同样可换 BitBlt（整屏 BitBlt 未单独测，按面积推断与 720×384 同量级，因 Blt 是显卡 blit）。
2. 显式设 DPI 感知。
3. **不要**尝试"只抓变化区域"省时间——见下条。

**预期收益**：单次抓屏 37.2ms → 6.6ms，降 **30.6ms/次**【实测】。视觉全链路（抓屏 + 识别）从 37.2+12.2=49.4ms 降到 6.6+12.2=18.8ms。
**风险**：BitBlt 在有 DWM 合成/独占全屏/硬件叠加层时可能抓到黑屏或旧帧（`ImageGrab` 走的是同一路径，风险相当，但 `BitBlt` 对某些显卡叠加层更敏感）。**必须先做 A/B 对拍**：同一时刻两种方式各抓一次，比对识别结果 480 格一致再切换。

### P1-4　增量扫描在矢量化之后是**负优化**（实测），但 `rescan_after_click` 的变更检测本身可提速且语义等价

**位置**：`utils/vision.py:259-287`（`rescan_after_click`）、`utils/vision.py:229-235`（`_cell_changed`）

**回应任务书问题 3 的"增量扫描能再省多少"**：**答案是不能省，是负优化**。实测（矢量化之后）：

| 方案 | 耗时 |
|---|---|
| 全盘批量识别 480 格 | **12.27 ms** |
| 逐格 `_cell_changed` 480 格（仅检测，不含识别） | **5.31 ms** |
| 若只重认 30 个变化格 | +0.70 ms |
| **增量总成本** = 抓屏 37.2 + 检测 5.31 + 识别 0.70 | **43.2 ms** |
| **全量总成本** = 抓屏 37.2 + 识别 12.27 | **49.5 ms** |

单看"检测 vs 全认"：检测 5.31ms 只比全认 12.27ms 省 0.4 倍，而检测本身还要遍历 480 格、做 480 次 `astype(np.int16)` + `mean()`。**省下的 7ms 与抓屏 37ms 相比微不足道**。任务书设想的"增量能再省一大截"在 18.3x 矢量化达成后**已不成立**——这正是"先做减法（P1-1 67.7%）再做矢量化"的政策后果：识别不再是瓶颈，抓屏才是。

**但有两处真实可省**：

1. **`_cell_changed` 可用整盘差分替代**（实测**语义严格等价**）：`diff.max(axis=2)` + 积分图按格归约，正确性已全枚举验证：

```
逐格参考检出: 37   积分图检出: 37   完全一致: True
```

耗时：逐格 5.31ms → 整盘逐像素差分 1.93ms（3.2x，但按格归约要 3.18ms，**净收益接近零**）。所以这条**不推荐做**，除非把归约改成向量化批处理。

2. **抓屏同步**：`complete_scan` 在 `moveTo(10,640)` 后**立即**抓屏（`vision.py:243-244`），中间无任何等待。`moveTo` 本身实测仅 **0.020ms**（`_pause=False` 生效），它唯一的目的是把鼠标移开避免悬停高亮污染识别。**真实风险不是"等待"，而是"鼠标移开后 Windows 重绘尚未完成就抓屏"**。`rescan_after_click`（`:266-267`）连 `moveTo` 都没有，直接抓屏，风险更高。

   **但必须说清**：本机无扫雷窗口，**无法实测重绘延迟**。给验证协议：连续抓 20 帧，比较相邻帧差异，若第一帧与第二帧不同则说明存在未完成重绘；用 `_cell_changed` 的 `mean|diff| > 3.0` 作为判据（阈值已由 `test_scan.py:40-58` 覆盖）。若确实存在，标准做法是**轮询直到帧稳定**而非固定 sleep。

**改法**：
1. **不做增量扫描**（矢量化已足够快），保留 `rescan_after_click` 但把它也改成批量（当前已是批量，见 `vision.py:280`）。
2. `complete_scan` 把 `moveTo` + 抓屏改为"抓屏 → 若与上一帧差异过大则短轮询重抓（上限如 3 次/50ms）"，把固定等待换成条件等待。
3. `rescan_after_click` 补上 `moveTo`，消除悬停高亮对变更检测的污染（当前缺）。

**预期收益**：避免"抓屏抓到重绘中间帧"，这是合成棋盘测不出来的**真机类错误**【估算，需真机验证】。
**风险**：轮询会引入不确定延迟（最坏 50ms），需设上限避免卡死。

### P1-5　`_locate` 全屏匹配：单次 133~780ms，play 模式每步都跑

**位置**：`utils/vision.py:84-104`（`_match_template_on_screen` / `_locate` / `locate_exit`）、调用点 `utils/solver.py:241,269,285,291,296,326`、`utils/probability.py:777`

**问题**：`_locate` 在**整屏**（1600×2560）上做 `matchTemplate`，且多处调用**每次都重新抓整屏**。

**实测（同进程 DPI 状态，中位数 n=5）**：

| 模板 | 整屏匹配 | 半分辨率 | 棋盘 crop（772×464） |
|---|---|---|---|
| lose.bmp (29×31) | 133.5 ms | 36.7 ms | **12.1 ms** |
| win.bmp (28×22) | 134.9 ms | 79.2 ms | 59.2 ms |
| exit.bmp (28×33) | 616.6 ms | 162.0 ms | 61.2 ms |
| ok.png (43×158) | 596.0 ms | 140.2 ms | 49.4 ms |

叠加 `ImageGrab.grab()` 37ms，**单次 `_locate(lose)` 实测 185.6 ms**、`locate_exit` **752 ms**。

**影响范围要说清**：主会话实测的"单步 308.7ms 视觉"是 **help 模式**（`is_play=False`），**不走 `_locate` 分支**。但 **play 模式**下 `probability.py:777` 在每次点击后都调 `_locate("./image/lose.bmp")`，而 `solver.py:284-326` 每轮主循环还要跑 ok/win/lose 三次匹配。**这是 play 模式独有的、未被主会话计入的巨额开销**。

**改法**：
1. **限定搜索区域**：胜负提示框只会出现在棋盘窗口内，用 `self.bx/self.by` 算出的棋盘矩形外扩 40px 作为 crop 再匹配。实测 lose 从 133.5ms 降到 **12.1ms**（11x）。
2. **降分辨率**：半分辨率匹配 + 原分辨率复核（先粗定位再精定位），lose 从 133.5 → 36.7ms。
3. **合并抓屏**：`solver.py:284-326` 的 ok/win/lose 三次匹配共用同一张 `screen`（代码已共用，这点是对的），但 `_locate` 内部若 `screen=None` 会各自重抓——检查所有调用点是否都传了 screen。实测 `probability.py:777` 传的是 `None` ⇒ **每次点击都多抓一次整屏 37ms**。
4. `_locate` 阈值 0.015（`vision.py:104`）与 `locate_exit` **无阈值**（`:94-98`，直接把最像位置当按钮）——后者在窗口不存在时会把随机位置当 exit 按钮点下去，是**误点击风险**。

**预期收益**：lose 检测 185.6 → 约 50ms（crop 12.1 + 抓屏 37）。若同时换 BitBlt 抓屏，约 **25ms**。play 模式每步省 100ms 级。【实测 + 估算】
**风险**：crop 区域若算错会漏检提示框（例如窗口位置变了但 `bx/by` 未刷新）。建议 crop 失败时回退整屏一次并 warning。

### P2-2　`_grab_board` 的 0.5 像素偏移与 `_slice_cell` 中心定义不自洽

**位置**：`utils/vision.py:213-227` 与 `:106-115`

`_grab_board` 的 bbox 左边界 = `bx + 0.5*cw`（实测 24.0，整数），而 `main.py:1075` 标定时 `bx = round(x0 - cw*0.5)`，即 `bx + 0.5*cw ≈ 棋盘左上角`。`_slice_cell` 以 `i*cw - cw//2` 为切片中心，当前 `cw=24` 为偶数、`cw//2 = 12 = cw/2`，恰好自洽。但 `cw` 为奇数时（如 27），`cw//2=13` 而 `0.5*cw=13.5`，两者差 0.5px，`_slice_cell` 会系统偏移半像素。

**改法**：`_slice_cell` 统一用 `round((i-0.5)*cw)` 计算左边界，不依赖 `cw//2` 的整除假设；或在标定时强制偶数 `cell_width`。
**预期收益**：消除奇数 cw 下的半像素系统偏差。【估算】
**风险**：低，但改变所有切片取整行为，需全回归。

### P2-3　`np.ones((11,3))*100` 硬编码与 `_TEMPLATE_LAYOUT` 结构耦合

**位置**：`utils/vision.py:126`

`result = np.ones((11, 3)) * 100` 把"11 个数字 × 最多 3 个模板"硬编码。若 `_TEMPLATE_LAYOUT`（`:27-39`）增删模板，此处不会自动适配，会静默截断/越界。且 `100` 这个初始分远大于任何真实得分（实测最大 0.77），语义上是"未匹配哨兵"，却与 P0-3 的阈值判据混在同一数组，无法区分"真得分 100"与"异常未填"。

**改法**：`result = np.full((len(layout), max_len), np.inf)`，哨兵与真实得分分离。
**预期收益**：消除模板集变更时的静默截断风险。【估算】**风险**：无。

### P2-4　`_template_mtime` 静默吞 `OSError`

**位置**：`utils/vision.py:41-50`

任一模板文件缺失时 `except OSError: return -1.0`，只让 mtime 缓存失效（每次重载），不报告缺了哪个文件。配合 P0-3：缺文件 → `cv.imread` 返 None → `compare_img` 静默降级。这是"文件丢了 → 静默给错结果"的完整链条。

**改法**：`except OSError as e: logger.error("模板文件缺失: %s", e); raise`。
**预期收益**：把缺文件从静默变显式。【实测链条】**风险**：无。

## 一句话结论

视觉域的真实瓶颈不是"模板太多/打分方式差"，而是三件更基础的事：**① 模板与补丁恰好等尺寸，使匹配退化成零搜索的单点像素差，1px 标定误差即翻转识别（日志 11 次"剩余雷>未开格"是它的真实世界指纹）；② 识别无置信度阈值，模板坏掉/整盘遮挡都会静默给出错误数字；③ 抓屏用 ImageGrab 固定 37ms，是矢量化之后剩下的最大单项。** 已实测的收益排序：置信度护栏（正确性）> cell_width 校验（正确性）> 抓屏换 BitBlt（30.6ms/次）> 过滤大模板（省 67.7%）> compare_cells_batch 修偏差（正确性）> 矢量化提速（22x，但需先修偏差）。
