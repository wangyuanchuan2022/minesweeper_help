# B 线结论：adaptive_depth 未生效，不是"无收益"

日期：2026-11-04　分支：main
二进制版本：`utils/mscore.cp310-win_amd64.pyd`
sha256 = `5B22EC2BDE70ACC8E64DAD8A8CBF9305970DF8EB228A744F06ED22AAC50219CD`

---

## 零、结论先行

**ad1 的规则在 400 局真实对局里「实际触发 0 次」。**

| 指标 | 数值 | 含义 |
|---|---:|---|
| win_rate 调用次数 | 248 | 这 400 局里总共进入 win_rate 的次数 |
| **`shrunk`（规则实际触发）** | **0（0.00%）** | **adaptive 规则从未改变过 depth_limit** |
| `cap` 触发 | 7（2.82%） | node_cap 异常降级，与规则无关 |
| 胜率 base | 141/400 = 35.25% | |
| 胜率 ad1 | 141/400 = 35.25% | |
| 配对 | **0 独赢 / 0 独赢** | McNemar p=1.0000 |

⇒ **正确表述**：「ad1 的当前预算阈值在这批对局里**从未触发**，
因此两臂在**构造上必然**给出相同结果」。

**不能**表述为「ad1 无收益」或「adaptive_depth 方向无效」——
那是把"规则没生效"误读成"规则生效了但没用"。

---

## 一、为什么之前会误判

上一轮我只看 `cap 率 1.57%` 就写下「规则极少触发，对胜率无可测影响」。
这是**把 cap 率当成了规则触发率**。

两者是完全不同的量：

| 量 | 定义 | 观测方式 |
|---|---|---|
| `cap` 触发 | `wr_f` 递归节点数超 `node_cap`，抛异常 → 整步降级为贪心 | 捕获 RuntimeError |
| `shrunk` 触发 | `adaptive_depth` 规则算出 `cost > budget`，**主动降低 depth_limit** | C++ 侧 `last_phase()` 的 `shrunk` 字段 |

前者是**异常路径**，后者是**规则生效路径**。cap 触发 7 次不代表规则触发 7 次。

**修复方式**：在 C++ 侧加 `last_phase()` 查询接口（thread_local 快照），
返回最近一次 `win_rate` 的 `(worlds, enum_ms, outer_ms, depth_limit,
shrunk, wr_nodes)`。B 线评测器每次调用后读 `shrunk` 累加。

---

## 二、为什么规则从未触发（成本预算不匹配）

`adaptive_depth=1` 的预算是 `cost = n_cand × total > 1e4` 才收缩。

真实对局的 `n_cand × total` 分布（来自 462 个可枚举决策点实测）：
- 中位数只有 **4,032**
- p75 = 19,080，p90 = 77,760
- 最大 3.57e6

而**能进入 `win_rate` 的决策点本身就已经是小局面**——生产在
`limitation > wr_threshold`（默认 8）时根本不走 win_rate，走的是
`process_bigger_situation`（贪心分支）。所以：
- 走 win_rate 的点，其 `n_cand × total` 天然偏小；
- 预算 1e4 对这些点几乎不触发；
- 只有极少数边界点会触发。

**⇒ 正确的表述是「ad1 当前配置未覆盖目标局面」，不是「规则选错了阈值」。**

必须区分这两句：
- ✅ **可以说**：ad1 的预算 1e4 在这批对局的 `cost` 分布上**未覆盖到**
  目标局面（即"发生 cap 降级的高复杂度决策点"）。
- ❌ **不能说**：「应该降低阈值」。
  0/248 只证明**该预算在这批对局中未生效**，**不能**推出"降阈值就有收益"。
  降阈值可能只是在**尚未证实有损失的局面**里主动变浅，
  反而引入新的质量损失。

**继续这条线前必须先做的核对（本轮未做）**：
1. 找出实际进入 `win_rate` **且发生 cap 的决策点**（不是全部 248 次调用）；
2. 核对这些点的 `cost = n_cand × total` 分布，与预算 1e4 对照；
3. 确认「cap 降级」是否真的对应质量损失（需要"降级 vs 未降级"的配对质量差，
   而不是只看 cap 次数）。

**已知的结构性事实**（可作为线索，但不是"应降阈值"的证明）：
高复杂度局面很可能**根本不进 win_rate**（被 `_wr_memory_ok` 与
`limitation <= wr_threshold` 双重拦住）⇒ 即使降阈值，也可能仍然覆盖不到
真正有降级损失的那些局面。

## 三、这与合成用例的验证结果不矛盾

`bench/verify_adaptive_depth_synthetic.py` 里 G10（total=1024, n_cand=20,
cost=20480）在 ad=1 时**确实触发**：`depth_limit` 10.000 → 4.883、
`wr_nodes` 1,241,184 → 47,016（26x）、输出改变。

合成用例能触发，真实对局不触发，原因是**cost 分布不同**：
- 合成 G10 的 cost=20480（人为构造，超过 1e4 预算）
- 真实对局的 cost 中位数 4032（低于预算）

⇒ **接线正确性已证明，但规则在真实分布上选错了阈值。**

---

## 四、若要继续这条线，需要先解决什么（未做）

1. **降低预算阈值**：让规则在真实分布上触发（如 budget=3e3 可覆盖 p50 以上）。
   但这会让规则在**一半以上的 win_rate 决策**上生效，风险大得多，
   必须重新做整局 A/B。
2. **改变作用位置**：把自适应逻辑放到 `process_bigger_situation`（贪心分支），
   而不是 win_rate —— 因为高复杂度局面都走那条路径。
   但这需要先证明"贪心分支的降级也有质量损失"，本轮未测。
3. **先量化"降级到底损失多少"**：目前只有间接证据
   （22 个可枚举点里 3 次 cap，p90 耗时 18.2s 接近 30s 预算），
   没有直接的"降级 vs 不降级"配对质量差。

**结论**：在解决上述任一问题之前，不应继续调这个阈值。
当前配置下规则触发率 0%，继续调参没有观测对象。

## 五、证据边界

| 项 | 状态 |
|---|---|
| 规则接线是否正确 | **已证明**（合成 G10：depth_limit 10→4.883，nodes 1.24M→47K，输出改变） |
| 规则在真实对局触发率 | **0/248 = 0.00%**（400 局，seed 20269000+） |
| ad1 当前配置是否覆盖目标局面 | **未覆盖**（触发 0 次 ⇒ 无观测对象） |
| ad1 是否有胜率收益 | **不可判定**——规则从未生效 |
| 是否"应该降阈值" | **未验证**。0 次触发不能推出降阈值有收益；降阈值可能只是在未证实有损失的局面里主动变浅 |
| cap 降级是否真的造成质量损失 | **未量化**（只有间接证据：22 点里 3 次 cap、p90 18.2s） |
| 600 局探测（seed 20268000+）的 0 差异 | 同理解释：规则未触发（该批 cap 率 1.57%） |
| 降级的真实质量损失 | **未量化** |
| 阈值降到 3e3 后是否有收益 | **未测** |
