# 生产参数联合评估：wr_threshold × node_cap

日期：2026-11-03　基线 commit：`ed2c5ce`

> **口径**：本报告测的是「**各参数组合下、在给定种子样本上的**胜率与资源成本」，
> **不是**"理论胜率极限"，也不是"最优参数"。
> 所有胜率标注完成局数；超时/未完成局单独列出，不剔除、不当作失败样本。

---

## 结论先行

1. **`wr_threshold` 从 8 提到 16，胜率完全没有变化**（三档都是 **33.33%**，
   配对差 0.00pp，McNemar p=1.000），但**尾部耗时暴涨**：
   - p90：12.5s → 22.7s（1.8 倍）
   - **p99：20.5s → 181.2s（8.8 倍）**
   ⇒ **提高阈值在当前样本上没有收益，只有成本。**

2. **`node_cap=2e6` 在三档阈值下均零降级**，说明它不是瓶颈。

3. ⚠️ **样本仅 12 局/档**，CI 宽达 ±20pp，**不能宣称"阈值无收益"**，
   只能说"当前样本未检出收益，而成本显著上升"。

4. 本轮**修复了一个关键陷阱**：`wr_threshold` 此前根本无法从外部设定
   （见 §零），若不修复，任何阈值扫描读数都是假的。

---

## 零、⚠️ 关键陷阱：`wr_threshold` 的设置路径（本轮修复）

### 0.1 陷阱

`utils/probability.py` 的 `number5_1` 里，阈值有**两个来源**：

```python
wr_threshold = 6 + (native.LIMIT_BONUS_WIN_RATE if native.tuned() else 0)  # ① 常量兜底
...
if _tb is not None:
    wr_threshold = _wr_current_threshold(_tb)                              # ② 真实读取
```

而 `bench/ab_policy.play_one` **硬编码 `s._time_budget = None`**
⇒ 永远走 ① 常量路径 ⇒ **外部设 `wr_threshold` 完全无效**。

实测证据（修复前）：目标 `th=16`，实际生效 **8**：

```
目标 th=8.0:  实际 ['8.0']   OK
目标 th=16.0: 实际 ['8.0']   XX 不匹配
```

这会导致所有阈值扫描读数都是假的（两档实际是同一配置）。

### 0.2 修复

给 `play_one` 增加 `wr_threshold` 参数，传入时构造真实状态：

```python
if wr_threshold is not None:
    s._time_budget = {"wr": {"t": float(wr_threshold)}}
else:
    s._time_budget = None
```

并**在每个组合跑完后回读校验** `_wr_current_threshold(tb) == 目标值`。
修复后三档全部 OK。

### 0.3 这条闸门为什么必须有

本项目此前踩过同类坑：**阈值 8 与 999 两臂逐局完全一致**，因为两臂实际都在用 8。
若没有"回读校验"，我会把"两档无差异"误读成"阈值无影响"。

## 一、设计

| 项 | 设置 |
|---|---|
| 参数轴 | `wr_threshold` ∈ {8, 12, 16} × `node_cap` = 2e6 |
| 种子 | 固定 `20261102..20261113`（12 局，各档完全相同） |
| 配对 | 同 seed 同棋盘，McNemar 精确检验 |
| `node_cap` | 给足 2e6，避免成为提前降级瓶颈 |
| 时限 | 每组合 600s（实测均未触发） |
| 落盘 | 逐局 jsonl、flush 进度、退出码、`--resume` |
| 校验 | 每档回读实际生效阈值 |

### 2.3 读法

**胜率**：三档完全相同（都是 4/12 胜），配对差 0。这说明在本样本中，
提高阈值让更多局面进 `win_rate` 前瞻，**没有改变任何一个决策的胜负**。

**成本**：p99 从 20.5s → 181.2s（**8.8 倍**），p90 从 12.5s → 22.7s（1.8 倍）。
生产 `DECISION_TIME_BUDGET = 30s`，**181 秒远超单次决策预算**。

⇒ 提高阈值在当前样本上**收益为零、成本超预算**。

**峰值内存**：三档都在 64–85 MB，远低于 1.5GB 预算
⇒ 内存不是约束（与用户"可用更多内存"一致，但瓶颈不在内存而在时间）。

**降级**：三档均零降级，`node_cap=2e6` 未成为瓶颈。

## 三、为什么阈值提高没有带来收益（解释性假说，未验证）

可能原因（**均未验证，不得当作结论**）：

1. **能进 win_rate 的局面本就极少**：`limitation` 中位 61（生产分布），
   阈值 8 时仅约 33% 决策进入；提到 16 也只到 46%。
2. **新增覆盖的那些局面，前瞻未必优于贪心**：`limitation` 大意味着
   内部格多、世界数大，`win_rate` 在这种局面上本身是启发式近似
   （见 `docs/变量名与算法细节.md` 2.2 节：wr_f 有四处与真实规则不符）。
3. **样本太小**：12 局中只有 4 胜，胜负差异可能被噪声淹没。

---

## 四、诚实边界

1. **样本仅 12 局/档**，CI 宽达 ±20pp（[13.81%, 60.94%]），
   **不能宣称"阈值无收益"**，只能说"当前样本未检出收益"。
2. **只测 3 个阈值 × 1 个 node_cap**，只测 `baseline` 臂。
3. **未测更高阈值**（如 24、32），不知道是否存在"收益出现"的拐点。
4. **未测 `node_cap` 与阈值的交互**（阈值提高后新增的大局面可能触发 node_cap）。
5. **未做受控大局面资源确认**（Advisor 建议的"先用受控大局面确认资源可承受"）。
6. 本报告**不含**任何"理论胜率极限"结论。
