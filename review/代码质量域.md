### F1【P0】pbs 空解集分支返回 ndarray，破坏四元组契约 → 自动扫雷线程崩溃

- **位置**: utils/probability.py:1057
- **问题**: `process_bigger_situation` 有两条返回路径：正常路径返回 4 元组；但 `len(res)==0` 分支返回裸 `cell_value`（ndarray）。调用方按 4 元组解包，必然 `ValueError: too many values to unpack (expected 4)`。且该分支由 `_pbs_compute_python` 的 DP 空路径（:947 `return np.array([]), 0.0, total`）稳定触发。
- **证据**:
  - :947 `return np.array([]), 0.0, total`
  - :1030 `if 1 in res:` → 空数组为 False → 进入 else
  - :1050 `if len(res) == 0:` → :1057 `return cell_value`
  - :739 `pos, confidence, total, _prob = self.process_bigger_situation(` （调用方）
  - 【事实】实测（native 可用，`test_4.json` 真实局面：num10=79, a=99, clicks9=8）：DP 分支 `R=a-num10=20 > U=8` → denom=0 → `res=[]`；`process_bigger_situation` 返回 `numpy.ndarray`，调用方解包抛 `ValueError: too many values to unpack (expected 4)`。
  - 【事实】纯 Python 回退路径同样复现（`native.available=False` 时返回形状 (7,7) 的 ndarray，解包抛 `ValueError: too many values`）。
- **影响面**: `Solver.play()` 主循环中该异常向上冒泡（`play` 的 `except` 只捕 `FailSafeException`/`win32ui.error`），自动模式整线程崩溃 → 对局中断；且 `self.count` 不递增，`count>=3` 的“请检查设置”自愈机制对此失效。触发条件（剩余雷数 > 无约束内部格数）在残局/总雷数配置偏差时真实存在（`test_4` 即真实数据）。
- **严重度**: **P0（CRITICAL）** / **置信度: HIGH（已实测复现，非推断）**
- **修复**: 把 :1057 改为返回契约一致的四元组（`return [], 0.0, float(total), {}`）或抛出专用异常由 `_number5_1_core` 决定降级（重新扫描 + `count += 1`）；在 :739 前后加契约断言。
- **风险**: 不改则「一局打不下去就崩线程」；改时注意 `pos` 为空时下游 `for p in pos` 与 `self._last_heatmap["best"]=None` 的既有处理（已存在，可复用）。
- **补测建议（不要改测试凑绿，而是新增）**: `tests/test_probability.py` 增 `test_pbs_infeasible_returns_tuple`：用 `test_4.json` + `total=10001` 断言返回 4 元组且 `pos==[]`。

### F2【P0】视觉打分指标用 `np.sum` 跨模板求和，尺寸不可比 —— 9/25 模板结构性失效

- **位置**: utils/vision.py:131
- **问题**: `compare_img` 对每个模板的 `cv.matchTemplate(TM_SQDIFF_NORMED)` 响应矩阵取 `np.sum` 作为得分，再跨模板取 argmin。归一化 SQDIFF 的每个位置都在 [0,1]，而**模板越小、响应矩阵位置数越少**，求和后天然更小 → 该指标系统性偏好小模板，与“像不像”无关。`_1/_2` 系列（28x20，背景深浅变体）在 88 个位置上累加，数值必然是大模板垫底。
- **证据**:
  - 【事实】真实截图 `image/save.png`（720x384，30x16 格，cell_width=24，补丁 18x12）上对 480 格实跑：`sum` 口径胜者直方图 = `{0.bmp:407, 8.bmp:57, 10.bmp:5, 9.bmp:3, 6.bmp:2, 5.bmp:2, 2.bmp:2, 7.bmp:1, 4.bmp:1}` —— **全部 9 个 `_1/_2` 模板一次都没赢过**（`_1/_2` 出现次数 = 0）。
  - 【事实】同一批格子改用 `np.min` 口径：胜者出现 `9_2.bmp:88, 2_1.bmp:8, 5_1.bmp:7, 1_1.bmp:5, 10_1.bmp:4` 等；两口径在 480 格中 **123 格判定不同**。
  - 【事实】正对照：把 12x18 的主模板直接当补丁喂给本算法，11/12 正确识别回自身（说明指标在“同尺寸”下可用）；把 28x20 模板缩放到 18x12 后喂入，则 12 个中 9 个被误判（多为误判成 8/0）——证明缺陷出在**跨尺寸比较**而非模板本身。
  - 【事实】`_active_templates`(:141) 以“模板大于补丁时 `matchTemplate` 会抛 cv.error”为前提把 14 个模板过滤掉；实测 OpenCV 4.5.4 **不抛错**（28x20 模板匹配 18x12 补丁返回 `res.shape=(11,9)`，无异常）。即该前提已被证伪，注释(:138-139)承诺的“同一判据”并不存在。
- **影响面**: 视觉识别实际只用每类数字的 1 张主模板，`_1/_2`（背景深浅适配）全部闲置 → 换主题/换背景色时识别率下降；且 `compare_cells_batch` 与 `compare_img` 的模板集合不同，两条路径的“等价”只是当前测试棋盘上的巧合。
- **严重度**: **P0（识别正确性根基）** / **置信度: HIGH（480 格实测 + 正对照）**
- **修复**: 得分改为 `np.min(res)`（标准 TM_SQDIFF 用法），或先把模板缩放到补丁尺寸再匹配；`_active_templates` 的过滤判据改为与 `compare_img` 完全一致的“实际是否会被打分”而非尺寸猜测；两条路径共用同一 `_score_cell()`。
- **风险**: 改打分口径会改变所有历史识别结果，需用真实对局截图做一次 `bench/verify_vision_accuracy.py` 式回归（该 bench 存在，但用的是合成噪声板，见 F7）。
- **说明**: 「1px 错位」缺陷已由 `5b01e6b` 修复，本报告已复核真实截图 `legacy vs batch` 不一致 = **0/480**（正面对照成立）；F2 是**另一个**独立缺陷。

### F3【P1】胜局统计落盘早于自增：赢局数永久滞后 1

- **位置**: utils/solver.py:235
- **问题**: “游戏胜利”分支先 `_gs_save(total, win)` 再 `win += 1; total += 1`；而“游戏失败”分支(:264-265)是先 `total += 1` 再 `_gs_save`。同构分支顺序不一致 → 赢局那次落盘写的是**自增前**的值，进程若在下次落盘前退出，最后一次胜利永久丢失。
- **证据**:
  - :235 `_gs_save(total, win)  # 对局统计累计落盘` / :236 `win += 1` / :237 `total += 1`
  - 对照 :264 `total += 1` / :265 `_gs_save(total, win)`
  - 【事实】`state/game_stats.json` 当前内容 `{"played": 316, "win": 107}`，与 `data.json` 中 `100` 档 4931 胜等历史累计口径不同源（两套统计从未对齐，见越界发现 O2）。
- **影响面**: 用户看到的“已完局/赢局/胜率”统计（`_emit_heatmap` 透传到状态栏）与真实值偏 1，且胜/负分支行为不一致，长期累积误差；连输几局后统计反而可能“追上”。
- **严重度**: P1 / **置信度: HIGH（代码顺序 + 对照分支，事实）**
- **修复**: 两分支统一为「先自增 → 再 `_gs_save`」；更好的是抽 `_record_result(win: bool)` 单点写入（顺带消除 F12 的四段重复）。
- **风险**: 低（仅统计，不动对局决策）。

### F4【P1】`ValueError("识别错误")` 在 play 主循环被无上限静默重试 → 卡死不自愈

- **位置**: utils/solver.py:359（异常源 utils/deduction.py:48）
- **问题**: `deduction.number0` 在“邻域已标雷数 / 未开数”与格子读数矛盾时抛 `ValueError("识别错误")`；`play()` 用 `except ValueError: continue` 吞掉并重来。而 `self.count`（`count>=3` 才触发“请检查设置”告警）只在 `number5_1` 的识别失败分支递增，**这条路径永远不递增** → 只要矛盾持续存在（例如设置的总雷数错、或视觉持续误读同一格），主循环就无限重扫屏幕、不告警、不退出。
- **证据**:
  - utils/deduction.py:48 `if not cnt10 <= cell_value[j, i] <= cnt9 + cnt10:` / :49 `raise ValueError("识别错误")`
  - utils/solver.py:356-360 `try: ... mine_clear1(...) ... except ValueError: continue`
  - 【事实】实测（桩：`mine_clear1` 恒抛 ValueError，其余用 mock 隔离鼠标/截图）：`play()` 连续跑了 **31 轮 `complete_scan`**，`warning_signal.emit` 调用 **0 次**，`self.count` 恒为 **0**（探针在第 31 轮主动中止，否则不退出）。
  - 【事实】`mine_clear3_1`（同一推理族）却没有 try 包裹（:361），同类矛盾在那里会直接冒泡成崩溃 —— 同一故障两种表现（静默卡死 / 崩溃），说明错误处理策略未统一。
- **影响面**: 用户点“自动”后程序看起来在跑（进度条/热力图停更），实际死循环；只能手动终止。与“不要静默失败”的工程纪律相悖。
- **严重度**: P1 / **置信度: HIGH（实测复现循环与告警缺失）**
- **修复**: 在 `play()` 的 `except ValueError` 分支里 `self.count += 1`（复用既有阈值）或维护独立 `_scan_error_streak`，达阈值发 `warning_signal` 并 `return`；`mine_clear3_1` 用同一策略包裹；错误信息带上坐标与 `cell_value` 现场值以便定位。
- **风险**: 阈值太敏感会误报（一次误读很常见），建议连续 ≥5 轮才告警，并在重试间插入强制重扫（现有 `complete_scan` 已满足）。

### F6【P1】`pbs_compute 近似分支` 的一致性 bench 是空路径假绿 —— “两边一致”掩盖“两边都没算”

- **位置**: bench/compare_native.py:213（被评对象 utils/probability.py:942-948）
- **问题**: bench 以「C++ 与 Python 逐位一致」作为 pbs 近似分支的正确性证据。但当约束集不可行时两边都返回**空数组**，`rows_equal`/`array_equal` 对两个空数组恒真 → 打 `[OK]`，实际上什么也没验证。
- **证据**:

- **O2（架构域）** 两套对局统计从未对齐：`state/game_stats.json`（`Solver.play` 维护，316 局/107 胜）与 `data.json`（`number5_1` 按置信度分档维护，`100` 档已 4931 胜）语义不同源，UI 状态栏只用前者，`test_accuracy.py`/`mm0.__main__` 只用后者 —— 用户看到的“胜率”与离线分析口径不一致。
- **O3（算法域）** `pbs` 精确分支（total≤10000）用 `combination_ratio` 的 `assert 0 <= x <= x_min <= n`：当 `a - mine_num - num10 > x_min` 时**断言失败直接抛 AssertionError**（非 ValueError，:`play` 不捕）。实测 `a=8, 未开=3` 时走到“约束集自相矛盾→均匀先验”兜底（有 WARNING），但那是 `mine_num` 为空的路径；`assert` 路径的可达性我未构造出反例（**推断**，未复现），建议改为显式 `if` + 兜底而非 assert（`python -O` 下 assert 会消失）。

## Open Questions（低置信度/需产品裁决，不阻塞）

1. **`1 in res` 与 `0.99` 阈值的产品口径**（utils/probability.py:1030 vs :1032）：当前实现是“只要有任一格概率**精确等于 1.0** 就进入确定性分支，而分支内又用 `>=0.99` 收割格子”。实测 float32 下 `1-1e-8` 会被判等于 1.0，而 `1-1e-7` 不会 —— 即该分支对 0.99~0.9999999 区间是**随机不可控的边界行为**。是希望“只点必然安全”（则应门与收割都用同一阈值，如 `>=0.99`，并把 `confidence` 记为真实值而非 1），还是“只要有一个必然安全就顺带点掉 0.99 的”？需产品裁决。当前实现同时做两件事且 `confidence=1`，会把 0.995 的格子标成“确定”并自动点击（实测：构造 `[1.0,0.995,0.4]` → `pos=[(1,1),(2,1)]`, `confidence=1`）。
2. **`number5_1` 是否应返回 `(pos, confidence, total, prob)`**：`_number5_1_core` 内部已经组装了 `_last_heatmap`，但对外只返回重扫后的棋盘；`tests/test_probability.py` 的注释期待元组。这是历史契约残留，是否要正式化需作者定（本报告不阻塞）。
3. **`test_4.json`/`test_6.json` 的 `num10=79` 与真实棋盘规模是否自洽**：用 `a=99, num10=79, clicks9=8` 会构造出 `R=20>U=8` 的不可行场景（F1 的触发源）。若这批夹具是从真实局面导出的，说明**真实局面里就存在 `a-num10 > 未开格数`** 的组合 —— 值得确认是夹具 num10 记录口径（含已标雷）问题还是真实可发生，这决定 F1 的触发概率等级。

## 正面观察

- **pbs 生成函数 DP 的数学是正确的**：我用独立手算 oracle（3 组，组内雷数分布 {0:1,1:2}/{1:2}/{1:2}，2 个无约束内部格，总雷 4）验证 `[0.6,0.6,0.5,0.5,0.5,0.5]`、mine=2.8，逐项一致；9 格 1 雷 → 8/9、2 格 1 雷 → 0.5 亦精确。`_pbs_group_histograms`/`_pbs_convolve` 的分层是干净的（每组直方图卷积 + `C(U, R-Σm)` 耦合项），比旧的“各组独立归一化”在数学上严格更优。
- **`win_rate` 与闭式解一致**：3 个非相邻未知格 1 雷 → 1/3、4 格 → 1/4（对称性实验：交换 `res_list` 顺序结果不变，仅在两组相邻时按期望变化）。
- **`part_solve` 与独立暴力 oracle 在 40 个随机局面 0 分歧**，枚举解集合与“局部数字约束”定义严格吻合。
- **持久化层的健壮性做得很好**：`_tb_save`/`_ps_record_ms`/`_gs_save` 都是「写 tmp → `os.replace`」原子替换 + 异常只记日志不打断主流程，`_tb_load`/`_gs_load`/`_ps_read_samples` 对缺失/损坏 JSON 均返回空结构并已用真实 IO 测试覆盖（`tests/test_real_io.py`，包括写入损坏内容后读取）。
- **热力图发射是单点收口**（`_emit_heatmap`）且用 `try/except` 隔离 UI 故障，`payload` 结构统一；样式去重（`_hm_last`）+ `setUpdatesEnabled` 批更新是对 Qt 重绘的正确用法。
- **`_ps_fit_k` 的拟合设计有统计学素养**：只用同模式样本、只用 `|ΔL|≥3` 的样本对、取中位数抗形状噪声、对 k 夹限 [1.05,2.0]、样本不足回退；`TestFitK` 4 个用例刚好覆盖“能拟合/样本不足/模式过滤/夹限”，是本仓测试质量最高的一组。
- **1px 错位的修复（`5b01e6b`）方向正确**：改为 `2*(screenshot_h//2) × 2*(screenshot_w//2)` 与 `_slice_cell` 实际取窗对齐，我复核真实截图 `legacy vs batch` = **0/480 不一致**（正面对照成立），且修复者补了变异体负向测试。
