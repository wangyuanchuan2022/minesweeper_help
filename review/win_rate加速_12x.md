## 一、瓶颈定位（靠测量，不靠猜）

基线：33 个生产真实决策点，最重用例 #13 只有 **6 个世界**却耗时 **2246 ms**（42.4 万递归节点）。
⇒ 瓶颈不在世界数，在**每节点固定开销**。

热度统计（`MSW_WR_STATS=1`）显示 case 13：
```
hash_calls=424114  hit=221282  miss=202832  hit_rate=52.2%  entries=62455
lookup_ms=136.50  insert_ms=23.49
```
每次递归都要：
1. 把棋盘归一化成 **2304 字节**缓冲区（分配）
2. 对 2304 字节算 **MD5**
3. 输出 16 字节 `std::string` 作为 memo 键

⇒ **哈希是压倒性瓶颈**。

---

## 二、三个方案演进（含两次失败，务必读）

### 方案 A：无分配 128 位哈希 → **4.66x**

- 零分配、单遍内联，归一化融进循环（不再建 2304B 缓冲区）
- 总耗时 4803.7 → 998.3 ms
- **但仍每节点扫整盘 576 格**

### 方案 B（错误，已修正）：位置感知「可加」哈希想做到 O(1)

关键观察：递归时子棋盘只在**一个格**上与父棋盘不同
（`wr_f` 里 `nb[v*W2+u] = c10`），所以哈希可以增量更新。

**但我第一版把 `cell_mix` 写成了顺序混合**：
```cpp
h1 += ...;
h1 ^= h1 >> 31;      // ← 不可逆！
```
`xor-shift` 不可逆 ⇒ 无法用"减去旧值"撤销 ⇒ **增量算出的键与全盘哈希不一致**
⇒ 同一棋盘产生两个键 ⇒ memo 命中率崩塌：
```
hash_calls 42.4万 → 145万      entries 6.2万 → 22.7万
```
耗时反而劣化（376 ms → 1299 ms）。

**修正为纯可加**（`H = Σ_i f(i, v_i)`，累加器只做加法）后恢复正确，
并写成**不变式测试**逐位证明（见下）。

### 方案 C（用户建议，失败）：把整个棋盘打包成 4 位/格长整数

用户建议："用长整数存整个棋盘，每 4 位存一个格子，因为格子信息不超过 16 种"。

实现了 `PackedBoard`（36 个 uint64 = 2304 位，无碰撞），**但性能崩溃**：
```
总耗时 380 ms → 424348 ms（劣化 1000 倍）
case 13: 245 ms → 422202 ms（劣化 1700 倍）
```

**根因（重要教训）**：`PackedBoard` 用 `std::array<uint64_t, 64>` 固定大小
（避免堆分配），但这样**每个键是 ~512 字节**。`unordered_map` 的
`find`/`insert` 需要复制整键 ⇒ 比算 MD5 还贵。

**教训：打包表示适合"存棋盘"，不适合"当 memo 键"。键必须小。**

> 打包方案的增量更新本身是对的（不变式测试通过），
> 但作为 memo 键体积太大。若要用它，应该：
> 存棋盘用打包，而 memo 键仍用 128 位哈希。这属于下一步可做的优化，
> 不在本次 10x 目标范围内。

## 三、最终方案（当前实现）

**memo 键 = 纯可加 128 位增量哈希**：

```cpp
// 每格贡献只依赖 (位置 i, 值 v)，累加器只做加法 ⇒ 可增量撤销
static inline void cell_mix(size_t i, int32_t v, uint64_t& h1, uint64_t& h2);
Key128 hash_board(const Board& b);                    // 根节点全盘算一次
static Key128 inc_hash(base, pos, oldv, newv);        // 递归时 O(1) 更新
```

递归时父层把"已增量更新的哈希向量"传给子层，**每节点不再扫整盘**。

| 版本 | 总耗时 | 加速 |
|---|---:|---:|
| MD5（原实现） | 4652.15 ms | 1.0x |
| 无分配 128 位哈希 | 998.3 ms | 4.66x |
| **纯可加增量哈希（当前）** | **380.47 ms** | **12.23x** |
| 打包棋盘（失败） | 424348 ms | 0.01x |

## 五、诚实边界

1. **本加速只在微基准（33 个固定决策点）上验证**。
   端到端整局耗时受视觉扫描/点击等非算法段影响，整局加速比会**低于** 12.23x。
2. **未测整局 2000 局**的胜率与总耗时变化。
3. 打包棋盘方案**失败但保留记录**，因为它的"无碰撞精确表示"思路
   在别处（如世界表示）可能仍有价值。
4. `MSW_WR_STATS` 统计是**诊断探针**（默认关闭），不参与生产路径，
   但会带来分支判断开销（实测影响 <1%，未单独量化）。
5. **未验证**更大盘面（>1024 格）下 `PACK_MAX_WORDS=64` 是否够用
   （当前打包代码已回退，不生效）。
