  - `[静态]` 由当前源码直接确定

## 0. 结论先行

项目已经具备一条相当完整的“屏幕识别 → 规则推理 → 概率决策 → 鼠标执行 → Qt 展示”产品链路，且 C++ 加速、热力图和帮助解释已经接入。但当前最值得优化的不是继续堆算法，而是把**正确性、状态所有权、失败可见性和 UI 信息架构**先收紧。

优先级结论：

1. **P0：视觉识别失败会被强行分类，可能把错误棋盘送进求解器。** `utils/vision.py` 的识别路径没有“无法识别”状态，模板损坏、遮挡、动画中间帧或标定偏移都可能被归类为 0 到 10 中的某个值。[静态]
2. **P0：工作区当前测试并非全绿。** Python 3.10 支持环境运行 104 个用例，101 通过、3 个失败；其中 1 个是 UI 文案契约过时，2 个暴露 C++ decide 连续循环与旧 stub 测试假设不一致。[实测]
3. **P0/P1：UI、线程和求解器仍共享隐式状态。** `Solver` 同时承担 QThread、视觉缓存、算法状态、点击动作、统计写盘和 Qt 信号；帮助流程还需要 GUI 线程做一次首屏扫描。当前虽然使用了独立一次性扫描器缓解一处竞态，但架构仍容易继续产生错帧、缓存污染和停止不完整。[静态]
4. **P1：UI 的主要问题是可理解性与状态反馈，而不是按钮样式。** 颜色热力图、概率、胜率、推理次序和“确定安全/推荐/确定是雷”混在同一视觉体系中；用户很难知道当前程序处于扫描、推理、等待、点击、失败恢复还是已停止。[静态 + 实测]
5. **P1：运行环境和打包契约不一致。** 项目文档写 Python 3.7，源码/原生扩展却绑定 Python 3.10；系统 Python 3.12 本轮实测 `win32gui` DLL 导入失败。`main.spec` 仍引用已迁移的旧入口且没有显式声明 `cfg.json`、状态文件和原生扩展。[实测 + 静态]
6. **P1：固定等待和全屏模板匹配会拖慢自动模式。** 仓库已有视觉域报告实测 `ImageGrab` 抓屏约 37ms、全屏 `_locate` 可达百毫秒级，`probability.py` 仍有固定 `sleep(0.1)`；这些比继续微优化枚举更值得优先验证。[历史证据 + 静态]

推荐目标不是“大重构”，而是分三阶段：

- **阶段 A：先封住错误**：识别置信度护栏、坏模板显式失败、测试契约对齐、native 回退原因可见、停止流程改协作式取消。
- **阶段 B：重做状态展示**：把 UI 改成“当前状态 + 当前建议 + 证据解释 + 可操作动作”的信息层级，并统一颜色/文字语义。
- **阶段 C：再做性能与架构收敛**：BitBlt/局部搜索、条件等待、Repository、BoardState/DecisionResult 契约，以及把纯算法从设备 IO 中分离。

### 1.3 失败测试的准确解释

#### 失败 A：`tests/test_ui_heatmap.py::test_stats_line_content`

测试仍期待“当前点击方格不是雷的概率”，当前实现显示“当前格非雷的概率”。这属于展示文案契约漂移。不能直接把测试改成通过而不决定产品术语；应先确定正式术语，再同步代码、测试、帮助页说明和 README。

#### 失败 B：`tests/test_cpp_decide_wiring.py::test_click_offset_batch_and_single`

当前自动模式已经从“单次 decide 后返回主循环”变为“decide → 点击 → rescan → 再 decide”的连续循环。旧测试 stub 的 `rescan_after_click` 没有模拟棋盘变化，因此生产循环继续拿到同一个响应并追加一次点击。这个失败既不能简单判定为生产 bug，也不能简单改断言；它说明测试没有覆盖新状态机的终止条件。

#### 失败 C：`tests/test_cpp_decide_wiring.py::test_heatmap_contract_shape`

同样因为 stub 没有推进盘面，后续 decide 响应覆盖了第一次 `_last_heatmap` 的最佳格。测试需要模拟“点击后打开格减少”或使用单次 decide 的隔离测试；生产代码还应明确热力图事件是“每次决策快照”还是“本次 number5_1 最终快照”。

## 2. 当前调用流程与逻辑图

### 2.1 启动与 UI 装配

```text
main.py
  └─ MyMainWindow.__init__
      ├─ 读取 cfg.json
      ├─ setupUi() 装配 ui/window.py 生成的 Qt 控件
      ├─ 创建 auto_play_thread = Solver()
      ├─ 创建 help_thread = Solver()
      ├─ 连接 pv / warning / heatmap / help-result 等 Qt signal
      ├─ 创建帮助页 30×16 按钮网格
      └─ 创建自动页 30×16 热力图按钮网格
```

主要问题：

- `main.py` 既是 UI 控制器、配置管理器、窗口操作器、截图流程管理器、线程生命周期管理器，又包含帮助解释弹窗逻辑。
- `ui/window.py` 是 pyuic 生成文件，但包含大量手工修改、业务注释和运行时依赖 `main.oklch_grad`；重新生成 UI 时有丢失手工逻辑的风险。[静态]
- 配置读取散落在 `setting.py`、`main.py`、`utils/solver.py`、`EditWindow`、`ScreenShot`，且均以当前工作目录为基准。[静态]

### 2.2 自动模式

```text
用户点击“自动”
  → MyMainWindow.auto_play_func()
  → reload cfg.json
  → minesweeper_run(path) 启动/激活扫雷窗口
  → Solver.set_args(value)
  → Solver.start()
  → Solver.run()
  → Solver.play(limit)
      → 找到扫雷窗口并计算 bx/by
      → 首点点击
      → 循环检测胜利/失败/弹窗
      → complete_scan()
          → 抓屏 _grab_board()
          → compare_cells_batch()
      → mine_clear1() 基础规则
      → mine_clear3_1() 集合差规则
      → 若无进展，number5_1()
          → native.decide() 三层 C++ 决策，或 Python 回退链
          → pyautogui.click()
          → rescan_after_click()
      → heatmap_signal(payload)
      → main.update_heatmap(payload)
```

自动模式当前有两个决策层：

1. `mine_clear1/mine_clear3_1` 直接执行确定安全点击或推理标雷。
2. `number5_1` 的 C++ decide 连续循环执行安全点击，再把控制权交回主循环。

这两个层都可能触发点击、重扫、进度信号和热力图更新。因此调用顺序、重复点击保护、失败弹窗检测和 `cell_value` 的生命周期必须有单一状态机，而不是靠多个函数共同维护。

### 2.3 帮助模式

```text
用户点击“帮助人类”
  → MyMainWindow.update_image()
  → 启动/激活扫雷窗口
  → reset_btn_list()
  → stackedWidget 切到帮助页
  → help_thread.start()
      → Solver.help()
          → complete_scan()
          → mine_clear1()/mine_clear3_1()
          → number5_1()
          → update_btn_list(pos_dict_list)
  → GUI 线程同时调用 _gui_scan_once()
  → 首屏棋盘预览写入 label_p3
  → 用户点击格子查看 MyMessageBox 解释
  → 用户点击“点击所有的确定方格”执行 pyautogui 点击/右键标雷
```

当前代码已经使用 `_gui_scan_once()` 避免直接调用后台 Solver 的 `complete_scan()`，这是正确方向。但它仍说明架构的接口缺失：GUI 需要“首屏棋盘快照”，却只能自己创建临时视觉对象读取屏幕。更好的做法是让后台工作流发布不可变的 `BoardSnapshot`，GUI 只消费快照。

### 2.4 配置与截图帮助

```text
设置
  → EditWindow
      ├─ 修改 w/h/a/limit
      ├─ 选择扫雷 exe
      ├─ 获取左上角和右下角鼠标位置
      ├─ 计算 bx/by/cell_width
      └─ accept/closeEvent 直接写 cfg.json

截图帮助
  → ScreenShot
      ├─ 输入坐标 i/j
      ├─ ImageGrab.grab 整个棋盘
      ├─ 裁剪对应单格
      └─ 写 image/temp.bmp 或覆盖 image/<模板>.bmp
```

配置流程的核心风险：

- `accept()` 和 `closeEvent()` 都写配置，且直接 `open(..., "w")` 截断，异常中断可能损坏配置。[静态]
- 修改宽、高、雷数后没有统一 schema 校验；可以输入 0 或互相不一致的参数，之后在 Solver 中才以异常或警告暴露。[静态]
- 设置页通过“让鼠标静止”采样位置，交互成本高且缺少取消、超时、当前步骤进度、撤销。[静态]
- `ScreenShot._save_img()` 会直接覆盖模板文件，没有备份、确认、尺寸/通道校验和撤销。[静态]

## 3. UI 设计审查

### 3.1 当前 UI 的优点

1. **功能分区清楚**：主页面、自动页、帮助页使用 stacked widget；设置和截图帮助在左侧入口。
2. **对自动模式有可观测反馈**：进度条、热力图、累计完局/赢局/胜率统计已经接入同一 payload。
3. **帮助模式具备解释意识**：格子上的数字表示判断次序，点击格子可以弹出推理文本。
4. **颜色渐变已经注意到色彩空间一致性**：`oklch_grad` 和帮助页图例同源，避免图例与现场颜色不一致。
5. **高频重绘已有工程优化**：`update_heatmap` 使用 `_hm_last` 样式去重和 `setUpdatesEnabled(False)` 批量更新。仓库历史报告实测 UI 重绘不是当前主要瓶颈。[历史证据]

### 3.2 P0/P1 UI 问题

#### UI-P1-1：状态模型缺失，用户不知道程序“正在做什么”

当前 UI 主要显示“计算中百分比”和热力图，没有显式状态枚举。用户可能看到同一个进度条，却不知道程序是在：

- 启动目标窗口
- 等待窗口出现
- 截图
- 识别棋盘
- 规则推理
- 概率枚举
- 等待画面稳定
- 执行点击
- 检测胜负
- 从识别异常恢复
- 已停止但线程尚未退出

建议定义并显示状态：

```text
IDLE → STARTING_GAME → CALIBRATING → SCANNING → DEDUCING
     → DECIDING → WAITING_BOARD → CLICKING → CHECKING_RESULT
     → WON / LOST / PAUSED / STOPPING / ERROR
```

UI 至少要有：当前状态、最近动作、最近一次耗时、失败原因、可用动作。进度条只能表示阶段进度，不能承担状态说明。

#### UI-P1-2：热力图颜色没有足够的文字语义

当前红到绿的连续色带表达“不是雷的概率”，但同时存在：

- 红色：高概率是雷
- 绿色：高概率安全
- 蓝框：最佳点击
- 黄框：推荐
- 紫色解释高亮
- 红色推理确定雷
- 灰色：无概率或已开格

用户需要记忆颜色、边框和不同页面之间的约定。对于色觉差异用户，红绿渐变也不可靠。

建议：

- 在每个概率格上显示短百分比或 hover tooltip，不要只靠颜色。
- 将“雷风险”和“点击价值”拆成两个字段；当前 `confidence` 在不同分支可能是 safety 或启发式胜率，UI 文案不应统一写成同一个概率。
- 用图例明确“安全概率”“策略胜率”“确定安全”“确定是雷”“推荐但未证明”。
- 颜色只做辅助，形状/图标/文字做主语义；提供高对比度和色弱模式。

#### UI-P1-3：自动页的热力图缺少交互闭环

当前自动页主要是被动显示热力图和统计栏。用户不能：

- 暂停后查看某一步的决策依据
- 查看当前候选格排序
- 查看识别到的棋盘数字
- 看到本次点击是否触发了重扫和状态变化
- 一键复制诊断信息
- 在失败时知道是模板识别失败、目标窗口丢失还是算法无可行解

建议在热力图下方增加“当前决策卡片”：

```text
建议点击： (x, y)
安全概率：87.50%
决策类型：精确边际 / 启发式前瞻 / 均匀先验
候选世界数：N
原因：与哪些数字格形成约束
[暂停] [跳过本步] [查看棋盘快照] [复制诊断]
```

#### UI-P1-4：帮助页信息密度和阅读顺序不合理

帮助页同时放置说明文字、图例、截图、30×16 格子按钮和底部操作按钮。固定几何坐标使其对不同字体和 DPI 不够稳健。

建议：

- 顶部只保留一句任务说明和当前状态。
- 图例采用卡片化的四项说明。
- 棋盘区域使用专门的 `QTableView/QGridLayout` 或自绘 widget，避免给 480 个按钮逐个设置绝对坐标。
- 右侧或下方提供“当前建议详情”，而不是只能点击格子后弹出窗口。
- 将推理文本改成结构化内容：规则名、涉及数字、结论、置信度、操作建议。

#### UI-P1-5：固定窗口尺寸限制可用性

本轮 offscreen 实测主窗口为 1035×783，最小宽度和最大宽度都为 1035。窗口不能真正响应式缩放；按钮网格、说明文字和截图区域都以硬编码尺寸构造。[实测 + 静态]

这会导致：

- 小屏或系统缩放下内容被裁切
- 大屏无法放大棋盘/解释区
- 不同棋盘尺寸只能通过重建 UI 控件适配
- 字体替换后标签可能溢出

建议：

- 主窗口允许调整大小；棋盘 widget 根据可用空间计算 cell size。
- 将“逻辑棋盘尺寸”和“显示 cell size”分离。
- 使用 `QScrollArea` 处理大棋盘，使用缩放滑块或 Ctrl+滚轮。
- 所有文本使用 layout 和 `wordWrap`，禁止依赖固定 QLabel geometry。
- 明确支持的 DPI/字体矩阵并截图回归。

### 3.3 UI-P2 问题

- 多处使用“楷体”“宋体”等机器相关字体，offscreen 本轮出现 Qt 找不到字体目录警告；应提供字体回退链并避免把字体作为视觉语义依赖。[实测]
- `MyMessageBox.closeEvent()` 和 `buttonClicked` 都可能发送位置/状态信号，生命周期语义复杂；建议改为单一 `finished`/`accepted` 信号。[静态]
- “下次不在显示”文案有错别字，应为“下次不再显示”。[静态]
- “帮助人类”“截图帮助”“自动”等命名偏口语，建议使用任务导向文案：“获取下一步建议”“校准识别模板”“自动运行”。
- 页面背景图、半透明白色按钮和半透明深色卡片同时存在，视觉层级较多；建议统一为一套背景、表面、边框、强调色设计 token。
- 进度条样式在自动页已显式设置文字色，但帮助页 `pgb_p3` 仍使用另一套样式，建议统一可读性规则。

## 4. 逻辑与正确性审查

### 4.1 视觉识别：最高风险

当前 `compare_img()`：

- 遍历模板并计算 `cv.matchTemplate`
- 对每个模板响应图使用 `np.sum`
- 取全局最小值
- 没有返回分数，也没有拒绝阈值
- `None` 模板或异常可能被跳过，最终仍返回某个类别

这意味着识别没有“不确定”分支。建议至少引入：

```text
RecognitionResult {
  value: 0..10 or UNKNOWN,
  score: float,
  template_id: str,
  frame_id: str,
  geometry: {x, y, width, height},
}
```

验收要求：

- 真模板合成棋盘：逐格识别正确
- batch 与参考实现：480 格 0 分歧
- 模板缺失/通道错误/尺寸错误：启动或扫描时显式失败
- 低分置信度：停止自动点击，显示“无法确认棋盘，请重新截图/校准”
- 真实屏幕截图标注集：不能只用 `image/example.png` 代替

仓库已有视觉域报告给出重要历史证据：模板与生产补丁尺寸相等时匹配退化为单点对齐；1px 垂直偏移可能翻转类别；BitBlt 比 ImageGrab 更快；这些方向应在真实截图集上复核后再修改。[历史证据]

### 4.2 线程和停止流程

`main.py` 多处直接调用 `QThread.terminate()`。这会绕过 Python `finally`、状态落盘、按键释放和原生调用清理。`Solver.play()` 的 `finally` 不能保证在线程被强杀时执行。[静态]

改进方案：

1. 给 `Solver` 注入 `threading.Event` 或 Qt 原子取消标志。
2. 在主循环、枚举批次、点击间隔和重扫阶段检查取消。
3. 进入 STOPPING 后禁用所有互斥动作，等待线程 `finished`。
4. 最后才保留强制 terminate 作为不可恢复故障兜底，并记录“非正常停止”。
5. `pyautogui.keyDown("ctrl")` 必须用 `try/finally` 保证 `keyUp`，不应只在 `FailSafeException` 分支处理。

### 4.3 C++ decide 连续循环与测试契约

当前 `number5_1` 自动路径会循环调用 native decide，并通过 `num9` 是否减少判断进展。这是合理的防死循环方向，但需要把状态机契约写清楚：

- 输入棋盘快照是否会被原地修改
- `rescan_after_click` 是否保证每个已打开格都被识别
- 点击后遇到失败弹窗时，返回值是什么
- decide 返回无效坐标时，是否保留当前热力图
- 一轮点击批次中部分成功、部分踩雷时，如何记录
- `_last_heatmap` 是每轮事件、每次 number5_1 最终值，还是整局最后值

测试必须包含：

- 单次 decide 的纯接线测试
- 连续 decide 的状态机测试，stub 必须推进棋盘
- 无进展终止测试
- 失败弹窗终止测试
- 512 次上限测试
- C++ 异常后 Python 回退测试
- 旧 pyd 签名兼容测试

### 4.4 概率与“confidence”语义

源码文档已经指出 `confidence` 在不同分支可能代表：

- 前瞻胜率
- 非雷安全概率
- 均匀先验安全概率

但 UI 统计栏把它统一显示成“当前格非雷的概率”。这可能在启发式胜率分支产生产品语义错误。[静态]

建议改为结构化结果：

```text
DecisionResult {
  position,
  safety_probability,
  strategy_value,
  value_kind: exact_safety | heuristic_win_rate | uniform_prior,
  explanation,
  world_count,
  solver_path,
  elapsed_ms,
  is_proven_safe,
  is_proven_mine,
}
```

UI 按 `value_kind` 显示不同文案，不能只靠一个 `confidence` 字段。

### 4.5 缓存、配置与持久化

静态检查发现：

- `cfg.json` 直接按 cwd 读取和截断写
- `data.json` 直接整文件写回
- 状态文件使用固定 `.tmp` 名称
- 两个 Solver 实例都存在，并可能写共享统计/模型文件
- `reload()` 更新部分配置，但构造时计算的 `p` 等派生状态需要统一重算
- `checked`、`pos_dict_list`、`appended_pos` 等缓存的局生命周期依赖调用者手动清理

建议先做小型 Repository，而不是立即引入大型框架：

- `ConfigRepository`：schema 校验、绝对路径、原子保存、备份和版本字段
- `GameStatsRepository`：单写者或带锁的 played/win 更新
- `TimeBudgetRepository`：模型状态独立保存，带模式/版本
- `TemplateRepository`：模板族、尺寸、通道、mtime 和校验

文件写入至少使用唯一临时文件名、flush、fsync、replace；读取损坏文件时要区分“恢复默认”和“阻止自动点击”，不能静默把错误配置当空配置继续运行。

## 5. 性能审查与优化顺序

### 5.1 不建议优先做的事

- 不要继续微优化当前已经很快的 `part_solve`，除非目标是降低极端尾延迟。
- 不要为了“更智能”盲目提高 `wr_threshold` 或 `limit`；这可能把更多局面送入昂贵搜索。
- 不要只把跨组乘积并行化而不先确认全局总雷数约束的正确性。
- 不要把 UI 的 480 个按钮重绘直觉地当成第一瓶颈；已有历史实测显示去重后影响较小。[历史证据]

### 5.2 建议优先验证的优化

1. **识别护栏**：正确性优先，先做低分拒绝和坏模板检查。
2. **固定等待改条件等待**：点击后轮询棋盘帧稳定或状态变化，设置最大超时；不要直接把 100ms 改成更小常数。
3. **整屏模板匹配改限定区域**：胜负/退出/确认按钮在已知窗口附近时，只搜索 crop；无结果再回退整屏并 warning。
4. **抓屏后端 A/B**：BitBlt 与 ImageGrab 同时抓同一帧，逐格结果对拍后再切换。
5. **显式 DPI 感知**：不要依赖 `pyautogui` import 副作用。
6. **批量视觉路径先做参考等价门**：batch 与逐格参考必须逐格 0 分歧，避免异常回退掩盖语义偏差。
7. **耗时模型移出热路径**：样本窗口、拟合频率和写入策略固定化；把监控开销纳入预算。

## 6. 工程与发布问题

### 6.1 环境声明

当前存在明显矛盾：

- README 写 Python 3.7
- `main.spec` 和原生扩展使用 cp310/python310.lib
- 本轮 Python 3.10 可导入 `win32gui`；Python 3.12 导入失败
- requirements 固定 `pywin32==302`，但支持环境实际版本并非该版本

建议明确发布矩阵：

```text
Windows x64
Python 3.10.x
PyQt5 5.15.x
OpenCV 4.5.x
NumPy 1.21.x
native extension: cp310-win_amd64
```

启动时显示版本、native 是否加载、模板目录和 cfg 路径；native 失败时显示“已切换纯 Python，预计性能下降”以及具体原因，而不是只写日志。

### 6.2 打包

`main.spec` 仍列出 `bg_rc.py`、`edit_setting.py`、`mm0.py`、`screenshot.py`、`setting.py`、`utils.py`、`window.py` 等旧的顶层入口，而当前代码位于 `ui/` 和 `utils/` 包中；`datas` 只声明 `image/`，没有显式处理 cfg、state、日志目录和原生 pyd。[静态]

建议把打包验收纳入正式门：

- 干净目录启动
- 任意 cwd 启动
- 缺 cfg 时显示配置向导而不是 traceback
- 缺模板时显式错误
- native 缺失时可运行纯 Python 且 UI 有提示
- 真实生成的 exe 能完成设置、截图帮助、帮助模式和自动模式启动检查

## 7. 推荐实施路线

### 第一批：正确性和可诊断性

1. 加 `RecognitionResult.UNKNOWN` 与分数阈值。
2. 模板加载自检：缺失、尺寸、通道、dtype、模板族。
3. 统一 `confidence` 字段语义，输出 `value_kind`。
4. 修正并重写 decide 连续循环测试，保留旧版单次接线测试。
5. UI 文案、测试、帮助页和 README 同步确定术语。
6. native 回退原因在启动页/设置页可见。

验收：坏模板、遮挡、低分、失败弹窗都不会自动点击；支持环境测试全绿；真实截图集至少覆盖 5 局。

### 第二批：状态机和 UI 信息架构

1. 引入 `SolverState` 枚举和统一状态事件。
2. 引入 `BoardSnapshot`、`DecisionResult`、`ActionResult`。
3. GUI 只消费快照和结果，不直接触碰 Solver 视觉缓存。
4. 自动页增加当前状态、当前建议、证据详情、暂停/继续/跳过/复制诊断。
5. 帮助页改为响应式棋盘 widget 和结构化解释卡片。
6. 统一颜色 token、图例、色弱/高对比模式。

验收：每个状态都有可见文字；停止后线程必定退出；帮助和自动模式不共享可变视觉状态。

### 第三批：性能和部署

1. BitBlt 与 ImageGrab 对拍并切换。
2. `_locate` 限定 crop，固定等待改条件等待。
3. 将统计和耗时样本写入 Repository，避免多实例覆盖。
4. 配置使用绝对资源路径和用户数据目录。
5. 重写 PyInstaller spec，做干净目录启动矩阵。
6. 用真实局面集报告 P50/P95/P99，而不是只报单次最好值。

## 8. 最小验收矩阵

| 领域 | 必须验证 | 通过条件 |
|---|---|---|
| UI | 100%、125%、150% DPI；小/大窗口；字体缺失 | 无裁切、无重叠、状态文字可读 |
| 视觉 | 真模板、坏模板、遮挡、动画帧、偏移 | 低置信度拒绝；batch/ref 0 分歧 |
| 求解 | 确定安全、确定雷、概率、无解、超预算 | 结果字段语义明确，禁止错误自动点击 |
| 线程 | 启动、暂停、取消、异常、窗口消失 | 协作退出，无残留点击/按键/线程 |
| 持久化 | 并发写、断电模拟、损坏 JSON、任意 cwd | 不丢数据、不静默覆盖、不依赖 cwd |
| 打包 | 干净目录、缺 native、缺模板、缺 cfg | 可诊断启动，回退行为明确 |
| 性能 | 同一局面集、固定 seed、P50/P95/P99 | 优化前后结果一致，再比较耗时 |

## 9. 最终判断

这个项目目前最需要的是“把已经实现的能力变得可信、可解释、可恢复”，而不是继续增加更多算法分支。UI 的下一步也不是简单换颜色或换圆角，而是把求解器内部的真实状态和证据转化为用户能理解的操作界面。

如果只允许做三件事，建议按以下顺序：

1. **视觉识别不确定性护栏**：识别不确定就停，不要继续点。
2. **统一状态机与协作取消**：所有扫描、决策、点击、停止和错误都有明确状态。
3. **重做自动/帮助页的信息层级**：显示“现在在做什么、为什么推荐、可信度是什么、用户下一步能做什么”。

这三件事完成后，再做抓屏和条件等待优化，性能收益才不会建立在错误棋盘和不可诊断流程之上。
