# 成本代理验证：limitation 不可靠，应改用 n_cand×n_worlds

日期：2026-11-04
脚本：`bench/validate_cost_proxy.py`
样本：30 点（每 limitation 桶 5 点，含深局面），每点 3 次取中位

---

## 零、三条结论先行

1. **`limitation` 不是可靠的成本代理**（Spearman = **0.786** < 0.8）
   ⇒ 按它分档会让同档内混入差异巨大的成本，**延迟保证不成立**。
2. **`n_cand × n_worlds` 是强代理**（Spearman = **0.960**）
   ⇒ 应改用它（或 `n_cand`、`n_worlds` 单独也 ≥0.92）做分档/预判。
3. **生产真实预算是 27 秒，不是 1 秒**
   ⇒ 我此前"limitation>16 超限、应不前瞻"的判断**是错的**，需撤回。

---

## 一、生产预算锚点（从代码推出，不是拍的）

Advisor 要求从仓库已有预算推出，而非让用户拍板。查得：

| 项 | 值 | 来源 |
|---|---:|---|
| **`DECISION_TIME_BUDGET`** | **30.0 秒** | `utils/probability.py:41`，注释明确"用户确认的上限" |
| `_PS_RESERVE_S` | 3.0 秒 | `probability.py:44`，为 win_rate/pbs/输出预留 |
| `_WR_NODE_CAP_RECOMMENDED` | 2,000,000 | `probability.py:104` |
| `_WR_FAST_FRAC` | 0.25 | `probability.py:50`，升档要求耗时 < 预算×0.25 |
| `wr_threshold` 初值 | 6 + bonus | `probability.py:542`，由 `_wr_update` 在线调整 |

⇒ **前瞻可用预算 ≈ 30 − 3 = 27 秒**（且需与枚举阶段共享）。

### 1.1 用真实预算重估成本

| limitation 桶 | ply3 中位 | 占 27s 预算 |
|---|---:|---:|
| [8,10] | 2.0 ms | 0.01% |
| [10,12] | 1.5 ms | 0.01% |
| [12,14] | 269 ms | 1.0% |

**⇒ 全部档位都在预算内，最大档仅占 5.2%。**

**必须撤回的结论**：
我此前用假设的"≤1s 实时预算"判定 `(16,20]` 超限、进而得出
"limitation>16 应不前瞻（排除 44.5% 深局面）"——**这个判断基于错误预算，作废**。

## 二、limitation 作为代理的可靠性（30 点实测）

### 2.1 秩相关排名

| 代理量 | Spearman | 判定 |
|---|---:|---|
| **`n_cand × n_worlds`** | **0.960** | **强** |
| `n_cand × log2(n_worlds)` | 0.948 | 强 |
| `n_cand` | 0.923 | 强 |
| `n_worlds` | 0.919 | 强 |
| `n_worlds × log2(n_worlds)` | 0.919 | 强 |
| **`limitation`** | **0.786** | **不足（< 0.8）** |
| `total` | 0.746 | 中 |
| `tie_size` | **0.331** | **弱** |

### 2.2 这解释了此前的"非单调"现象

冒烟数据里 limitation 与成本出现非单调：
- (12,14] 269ms > (14,16] 30ms
- (16,20] 1409ms > >20 408ms

扩大样本后可见**同桶内成本差异极大**。

实例（`[14,16]` 桶内 5 点）：

| worlds | n_cand | n_worlds | ply3 ms |
|---:|---:|---:|---:|
| 16 | 19 | 16 | 33.7 |
| 48 | 17 | 48 | 35.5 |
| 64 | 28 | 64 | 538.9 |
| 96 | 31 | 96 | **3126.2** |

⇒ **同一 limitation 桶内，成本从 33ms 到 3126ms（94 倍差）**。
   这正是 Advisor 指出的：按 limitation 分档，延迟保证不成立。

### 2.3 另一个发现：tie_size 是弱代理（0.331）

我原以为平局集大小决定成本（因为只对平局算 ply），实测**相关性最弱**。

⇒ 成本主要由 `n_cand × n_worlds`（即求解规模）决定，
   平局集大小只是"要不要调用"的开关，不决定"调用一次多贵"。

## 三、正确的方案形态（据实测调整）

### 3.1 不要按 limitation 分档，改为运行前成本预判

既然 `n_cand × n_worlds` 的秩相关达 0.960，且这两个量在**决策前就能算**
（候选集与世界集在枚举阶段已得），就应该：

```
cost_est = n_cand × n_worlds          # 决策前可得
若 cost_est <= C_high:  k = 3          # 便宜，深前瞻
若 C_low < cost_est <= C_high: k = 2   # 中等
若 cost_est > C_high:  k = 1（退回 safety）
```

**这与"按 limitation 分档"的关键区别**：`limitation` 是局面的静态特征，
而 `cost_est` 是**当前这一步的真实求解规模**，更能预测本步开销。

⚠️ 阈值 C_low / C_high 需从实测数据标定，不能凭直觉。

### 3.2 还需补测：k=2 与 k=1 的耗时

Advisor 第二条要求：在判定某档"不前瞻"之前，先测降档能否压进预算。

已知（冒烟）：
- ply2 在 [12,14] 是 72.8ms（ply3 是 269ms）⇒ **k=2 约为 k=3 的 27%**
- k=1 时 `ply_score` 直接返回 `safety`，成本≈0

⇒ **降档确实能大幅压缩成本**，因此"不前瞻"应是最后手段，而非首选。
