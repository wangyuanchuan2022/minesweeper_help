## 一、已修 4 条

### P1-1 图例色带与现场不同源（最重要的一条）

**问题**：帮助页图例用 Qt **sRGB 线性**渐变（写死红→绿），而真实格子用
**OKLCH 感知均匀**渐变（`main.py` 的 `oklch_grad`）。两条曲线的中点差别极大：

| | 中点颜色 |
|---|---|
| 旧图例（sRGB 线性） | `rgb(128, 127, 0)`（暗橄榄） |
| 现场（OKLCH） | `rgb(247, 149, 0)`（亮橙） |

⇒ 用户照图例估色会**系统性高估 15~25%**，等于量具刻错了刻度。

**修法**：新增 `ui/window.py::_make_gradient_qss()`，从 `oklch_grad`
（100 阶）等距取 **11 个采样点**生成 QSS 的 `stop` 列表。色带仅 231px 宽，
每点约 23px，肉眼不可分辨差异。

**验证**（`bench/verify_ui_legend.py`，PASS 5/0）：

```
图例中点 (247, 149, 0) vs 现场中点 (247, 149, 0)，最大分差 0
对照：旧线性渐变中点 (128, 127, 0) 与现场中点分差 119
```

**分差 119 → 0。**

### P1-2 色带条与两侧文字垂直错位 5px

`label_4` 的几何槽位是 31px 高，但 `setMaximumSize(..., 21)` 把实际高度钳到 21
⇒ 中心 40.5，而同排文字中心 45.5，**错位 5px**。已改为 31。

### P1-6 `page_2` 的按钮选择器误伤热力图 480 个格子

`page_2` 容器样式写的是 `QPushButton{...}` —— 这是**后代选择器**，
会命中它下面**所有**按钮，包括热力图的 480 个格子。

后果：热力图的红/绿/渐变分支不声明 `color` ⇒ 文字色继承这里的
`rgb(0,0,0)` ⇒ **同一张网格里"已开格"白字、"概率格"黑字混排**，
看起来像渲染错误；且任何父级 QSS 改动都会**静默改变格子字色**。

已收窄为精确 objectName：

```css
#end_auto_play_thread, #return_to_main_page { ... }
```

### P1-7 `border-radius: none` 是非法 QSS 值

`none` 不是合法的 `border-radius` 值（应为 `0px` 或长度），Qt 解析到非法值
会让整条属性失效 ⇒ 侧栏 4 个按钮是**直角**，而内容区按钮是 10px 圆角，
四套圆角并存。已把 4 处 `none` 改为 `10px`。

## 二、暂缓 4 条及理由

### P1-3 红→绿对红绿色盲不可分

实测 p=0.40 与 p=0.60 在 deuteranopia 下 ΔE≈16（几乎同色）——**最需要细分的
中间段恰恰最不可分**。

但这需要**换色带方案**（单色相亮度渐变或蓝-橙发散），会连带改变：
- 格子文字色必须重算（深蓝底要白字，当前是黑字）
- 图例、`_HM_BASE`、热力图所有分支的配色

属**设计变更**而非修 bug，且牵涉面广，应单独一轮做。

### P1-5 热力图卡片 43% 空白

`heatmap_frame` 被布局撑到 809×716，而网格只需 744×408 ⇒ 底部 308px 纯灰空区。

但自适应高度需要在**切换棋盘尺寸时重算**（w/h 变了要重算），
而这正是交互域 P0-1「网格重建」的范畴。两件事必须一起做，否则改完切换棋盘会错位。

### P1-8 字体混排（楷体 1008 处 + 宋体 + SimSun 9）

**有一条硬约束**：评审实测最紧的 `label_14` 文本宽 **810px**、容器 **811px**，
**余量仅 1px**。换字体族必然改变文字宽度 ⇒ `label_14` 会立刻溢出。

⇒ **必须先做 P0-1 的自动换行改造**（7 个绝对定位 label 改 QVBoxLayout），
才能安全换字体。本轮 P0-1 只加了衬底、没改布局（保留原坐标），所以字体不能动。

### P1-9 已开格白字对比 4.80（余量 0.3）

需调格子底色，与 P1-3 的色带改动联动（换了色带，字色策略要整体重算）。

## 三、⚠️ 撤回 1 条：P1-4 统计栏截断「本机无法复现」

评审报告称：统计栏文本填满（`已完局: 99999` 等）时需 **825px**，
而控件只有 **809px** ⇒ 右端截断。

**本机实测无法复现**（`QFontMetrics` 逐字体实算）：

| 字体 | 字号 | 最坏文本宽度 |
|---|---:|---:|
| 楷体 | 11pt | **574px** |
| 楷体 | 12pt | 648px |
| 微软雅黑 | 11pt | 540px |
| 微软雅黑 | 12pt | 610px |

全部**远小于 809px**，不溢出。

我据此做了两项处理：
1. **回退了为修它而写的代码**（`main.py` 的小数位收敛 + 局数「万」缩写 + sizePolicy 改动）
   —— 问题不存在，改了反而无端改变显示格式（会破坏既有测试期望）。
2. 保留 `bench/verify_ui_stats.py` 的实测记录（后删除，结论写在此处）。

⚠️ **不排除评审方在别的字体/DPI 组合下测到了 825px**，
但结论应限定为：**当前字体配置下不溢出；换字体后需重测**。

## 五、诚实边界

1. **`_make_gradient_qss` 写在 pyuic 生成文件里**，若将来重新 `pyuic5` 会被覆盖。
   本仓无 window.ui 之外的生成流程，但这是已知脆弱点（已在代码注释注明）。
2. **P1-4 的撤回基于本机单一字体环境**，不能排除其他字体/DPI 下溢出。
3. **暂缓的 4 条不是"不重要"**，而是有硬前置依赖（布局重构/换字体）或属设计变更。
4. 本轮**未做整页截图目视确认**，只用像素取样与结构断言；
   视觉观感（如"色带是否好看"）不在自动验证范围内。
