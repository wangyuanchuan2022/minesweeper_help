4. **P0-b｜采纳判据把 MDE 当作效应门槛，而不是报不确定区间**
   预注册 `review/P2预注册_角落开局.md:43-46` 的采纳条件第 2 条是「效应量 ≥ MDE」。

   预注册流程本身意识到了这个陷阱（`review/P2复现预注册.md:10-25` 专门区分 MDE/显著性/预注册条件），但**判据没有随之改**（预注册不允许事后改，这是对的）；于是出现"文档解释正确、判据仍不合法"的僵局。这不是执行错误，是**设计错误**，应在下一份预注册里改掉（见【改进点】）。
5. **P2｜"两轮幅度不可比"的正确理由没有数值化**：报告用 MDE=4.26pp 论证不可区分；本席给了直接检验 p≈0.256。两者结论一致，但前者依赖上一条被否的 MDE 口径。

**【改进点】**
- A/B 脚本必须落盘逐局明细（`seed, won, died, opened, first_num, board_hash`），并在 summary 里带 `a_only/b_only/paired_ci/p`；判据脚本从明细重算而非读日志。
- 下一份预注册把采纳条件改为：**主判据 = 配对 CI 下界 > 0（或预注册的最小工程显著量 δ*），并明确 δ* 的来源**；MDE 只用于"说本设计能不能回答这个问题"，不进入采纳条件。
- MDE 必须用与设计一致的公式（配对：`SE=sqrt((b+c)−(b−c)²/n)/n`）；建议把该公式收敛到 `bench/paired_eval.py` 单点，各脚本 import，避免 `ab_first_click_corner.py:96` 与 `analyze_first_click_both.py:50` 两套公式并存。
- 中间指标应报"与理论值的精确二项检验 p"而非仅报"接近"；复现轮 p=0.063 必须写出来。

## 3. E4 规则差异（Arbiter deferred vs 现代 safe3x3）

- [事实] 设计：同一条生产流水线、同 seed 配对、只换 `Board.generate`（`review/胜率50%目标_可行性与路径.md:129-134`）；n=600 —— 但 `rule_gap_600.json` 的实际 seed 是 **20261102..20261701**，正是 2000 局基线的前 600 局。

- [计算] 独立重算 McNemar exact：`modern_only=161, arbiter_only=65, n=600` ⇒ **p = 1.395e-10**；Δ=**+16.00pp**，配对 95%CI **[+11.26, +20.74]pp**（SE=0.0242，报告未给 CI）。

- 缺陷（均为 P2）：
  1. 报告只报 p 值与"几何机制（4.7 格 vs 41.2 格）"，**未给 Δ 的 CI**；给了会让"不是结构惩罚"的边界表述（`:144-146`）更有力。
  2. `rule_gap.json`（8 局）与 `rule_gap_600.json`（600 局）并存，前者 p=1.0、gap=12.5pp，容易被误引用为"规则效应不大"。建议 8 局版本加 `SUPERSEDED` 标记或删除。
  3. [推断] "现代规则下 49.50% 已接近 MinesweeperHQ 的 50.7% 上限"是**跨口径比较**（对方是现代规则 + 完美逻辑 + 全部真实对局，本项目是离线 mock + 无点击延迟 + 视觉 100% 正确）——报告已在 `:140-147` 标注边界，属可接受，但该外部数字未经本席核验（外部资料不在本席范围）。

**【改进点】** 补 Δ 的配对 CI；把小样本版本标记为 superseded；若要用"接近上限"这类表述，需先在同一 harness 上跑对方的策略（当前不可能，故建议降级为"量级参照"）。

- ⇒ **P0-d｜两条 LOO 结论互相矛盾且都未被撤回**：`review/论文研读_随机搜索与MCTS扫雷.md` 与 `HANDOFF.md:106` 写「LOO 全部劣于 S0 ⇒ 过拟合直接证据」；`fast_loo.json` 与 `review/LOO方差预演_n77.md` 的多种子结论写「单次 LOO 符号不稳定，不能作方法比较」。前者用的是**已被判为口径混用**的旧读数，后者是修正后的。**当前项目文档里"连续权重过拟合"这一结论的证据链是断的**：正确表述应是"旧读数的 Δ 被高估 83%；修正后单次 LOO 符号不稳定（n=77），故本样本不足以判断连续权重是否过拟合"。
- **P0-e｜LOO 选择/超参搜索泄漏（真正的设计问题）**：
  `bench/fast_loo.py:219-240` 的 `loo_random` 每折**独立**跑随机搜索（`w = random_search_packed(pk_tr, trials, rng)`），这一步是正确的；
  **但整个过程本身又被用作"方法比较的选择准则"**：`review/LOO方差预演_n77.md:111-115` 建议"报多种子分布的 LOO−S0，再谈哪个方法更好"，而实际报告（`HANDOFF.md:106-107`）用的是**单次 LOO** 做"随机搜索 vs 坐标下降"排序。`bench/optimize_weights.py:14-15` 的 docstring 自己写了警告：「逐代 LOO 不是过拟合防线……LOO 被用作选择准则时其无偏性就失效了」，**但同一份报告接着用 LOO 排序方法**。⇒ 文档层面的自我警告没有落到执行面。
- 另一处泄漏（P1-g）：`review/P1预注册_发现验证集冻结.md:86-93` 预判验证集合格点"456 × 30.6% ≈ 140"，而 `p1_coverage` 实测全样本 ok 率 **40.26%**、`mm_full` 对同一批 462 点给出 62.1% —— **三个合格率预判/实测值互相差 1.5–2 倍**，"验证集 140 点"这个 MDE 预判因此没有可靠基础。

### 7.3 128 子集穷举（`metric_subsets.json`，n=41）

- [事实] `n_points=41`，`s0_mean=0.015668492`，`best_equal=["S0","E","B","R","L"]`、`best_loo=["S0","IG","U","E"]`。

- [计算] **"LOO−equal 间隙"分布：min −0.0266、max +0.0156、中位 0.0000**。⇒ 该搜索在 41 点上存在明显的过拟合-泛化间隙，报告已正确用 LOO 而非 in-sample 挑最优。
- 缺陷（P1-h）：报告 `HANDOFF.md:107` 写「最佳 LOO 与 S0 配对 6好/6差 p=1.000，Δ−0.0025 仅为 MDE(0.0090) 的 28%」。**这条同时犯了 §10.2 的两个错**：(i) 用 MDE 作为"效应太小"的判据；(ii) 用 p=1.000 论证"不显著"。正确表述：n=41 的配对符号检验在 6/6 时 p=1.000 是**定义使然**（完全对称，无方向性证据），不含"效应小"的信息；而 Δ−0.0025 的 CI 本席无法算（`metric_subsets.json` 只存了聚合值，未存逐点 regret ⇒ **P2：该实验不可独立复算**）。

### 7.4 分层权重（`layered_weights.json`，n=41）

- [事实] `n_disc=21, n_valid=20, global_disc_regret=0.0130544, global_valid_regret=0.0147522, layered_valid_regret=0.0147522, s0_valid_regret=0.0173875`。

- 附带（P1-i）：`bench/layered_weights.py:180-186` 用**位置奇偶**做发现/验证切分，注释写"位置顺序来自采集顺序，与 limitation 无系统关联"，但本席机检 `case_idx` 发现 disc 的 case_idx 是 `[0,13,32,41,…]`、valid 是 `[12,31,40,50,…]`，两者**严格不重叠**（无同一原始 case 跨切分）；不过奇偶切分仍**不是预注册要求的"按数据来源"**（`review/P1预注册_发现验证集冻结.md:20-34` 明确要求按来源划分，因为"随机切分仍可能因同一局的相邻决策点而泄漏"）。实际执行用了**被预注册否决的方法**，且脚本自己在 `:170` 打印了警告。

## 8. E12 性能：win_rate 14x 加速

- [事实] 口径：`bench/bench_wr_speed.py:8-12` 用 `bench/data/wr_cases_big.json` 的 **33 个生产真实决策点**；加速比 = **sum(ms) 之比**（`:91-95`、`:137-139`）；`--repeat` 默认 **1**（`:153`），即每个用例**只测一次**，取"多次中的最小值"（`:80-82`）——默认只跑 1 次时该机制无效。
- [计算] 独立重算三组读数（逐用例比值）：
  | 对比 | 加总加速 | 逐用例比值 中位/均值/范围 | 中位耗时加速 |
  |---|---:|---|---:|
  | before→final | **12.23x** | 9.33x / 14.55x / 1.88–42.58 | 6.82x |
  | final→boardpacked | **1.16x** | 0.98x / 1.01x / 0.70–1.29 | 0.87x |
  | before→boardpacked | **14.12x** | 8.76x / 15.41x / 1.65–49.67 | 5.97x |
  ⇒ 报告 `review/win_rate加速_14x.md:105,120` 的 "14.12x" **精确复现**（4652.15→329.49ms）。
- [计算] **该加速比被单个尾部用例支配**：before 的总耗时里 case13 一个就占 **48.3%**（2246.2ms），top-3 占 **73.6%**。
  - 剔除 case13 后 before→boardpacked = **20.49x**；
  - 用**中位耗时**（更抗尾部）只有 **5.97x**；
  - 逐用例比值的**中位数 8.76x**。
  ⇒ "14.12x"是一个**加总口径**的数字，**它衡量的是"总 CPU 时间省了多少"，不是"典型调用快了多少"**。报告 `:118-121` 只给了加总表，没有给中位/分位口径 ⇒ 读者会把它理解成"每次调用快 14 倍"。
- [计算] **`final→boardpacked` 的 1.16x 几乎全部来自 case13**（该用例 254.6→212.1ms，占 final 总时长 **66.9%**）；剔除 case13 后只有 **1.07x**，逐用例中位 **0.98x**（即多数用例**没有变快**）。报告 `:105` 把它写成"380.47ms → 329.49ms（12.23x → 14.12x）"，**未说明这个增量只体现在一个用例上**。
- 可信度：**有限**。真实性证据（三层）是扎实的：输出指纹逐用例一致（`hash` 字段 33/33 相同，本席核对 `wr_speed_before/final` 的 `hash` 完全一致）、增量哈希不变式、端到端整局。但**加速比的代表性与稳定性证据不足**。
- 缺陷：
  1. **P1-j｜单次测量、无重复、无方差**：`--repeat 1` 默认下，33 个用例各测 1 次，加总比值没有任何不确定度。这一条与 `HANDOFF.md:53-60` 自己发现的"同进程耗时漂移 2.4–5.4x"**直接冲突**：既然同进程调用可以漂移 5 倍，那么单次测得的 14.12x 里有多少是漂移？报告在 `HANDOFF.md:60` 规定"任何同进程内耗时对比不得用于策略排序"，但**加速比本身仍是同进程内对比**。
  2. **P1-k｜加速比口径未声明**：加总 / 中位 / 逐用例中位三个数分别是 14.12x / 5.97x / 8.76x，差 2.4 倍。报告只给加总，且标题写"目标 10x 已达成"。
  3. **P2｜用例集筛选偏差**：`wr_cases_big.json` 的 33 个用例 limitation 范围 **1.00–7.60**（中位 2.80），是"能进 win_rate"的筛选样本（`cap扫描…md:117` 自己也说"bench 用例是按能进 win_rate 专门筛出来的极端样本"）。用它做加速比是合理的（比的是同一批输入），但**不能外推成"整局快 14 倍"**——报告 `review/2000局胜率结果.md:108-111` 已正确指出这点。
- 【改进点】报三个数（加总 / 中位 / 逐用例中位）+ 重复 ≥5 次取中位与极差；对 before/after 做**交替随机**测量（`bench/timing_protocol.py` 已有，但 `bench_wr_speed.py` 未使用）；单独报 case13 与其余 32 用例两组，避免单点支配。

### 10.2 是否把"不显著"解释为"无效"

**多数地方没有，少数地方有**。项目在这点上整体做得比同类项目好（`review/P2结论_角落开局两轮.md:52-62` 有一整张"不能说的表述"表，`review/中局前瞻…md:43-46` 也明确"不能说该准则无效"）。但仍有三处越界：

1. `review/2000局胜率结果.md:17-18`：「落在本轮 CI 内 ⇒ 差异不显著 ⇒ **C++ 加速改动没有影响胜率**」——后半句是"不显著 ⇒ 无效"（且这里连"差异不显著"都没算，只做了 CI 包含性目测；本席算出 p=0.580/0.630）。
2. `review/B线_自适应深度未生效.md` 的 MDE 段（见 10.1 #5）：零暴露下说"不能排除 <9.5pp 效应"是方向反了的误导——不是"可能有小效应"，而是**没有任何暴露**。
3. `review/算法性能评估与优化方案.md:21,156`：「基线 33.3%（120 局）与历史 33.86% **吻合**，说明台架可信」——120 局的 CI 是 `[25.2, 42.6]`（宽 17pp），"吻合"几乎必然成立，**这个检验没有区分力**（任何 25–43% 的值都会"吻合"）。用它论证"台架可信"是循环论证；真正该做的是同 seed 的改前/改后对拍（项目后来确实做了：`review/胜率50%目标…md:73-96` 的最小双版本对拍，那一节方法论正确）。

### 10.3 是否按可评估样本自选择

**是，且这是本项目最深的结构性问题**：

- [计算] `p1_coverage`（全 462 点）：ok 组 worlds 中位 **106** vs 非 ok **1980**（**18.7×**）；`>10000 worlds` 的 39 点**全部** time_cap（ok=0）。
- [事实] 所有 regret/权重/分层结论都建立在"能算出 q 的点"上（77/287/300/186/222 等，见 §6.1）。这些点**系统性偏向 worlds 小的局面**。
- [事实] 真实对局里 81.6% 的中局决策点 worlds≈1e24（`review/中局前瞻…md:21-22`），**永远不会进入任何可评估样本**。

### 10.4 是否 LOO 选择/超参搜索泄漏

- **真泄漏（P0-e）**：单次 LOO 被用作"随机搜索 vs 坐标下降"的排序准则。`bench/optimize_weights.py:14-15` 与 `review/LOO方差预演_n77.md:111-115` 都写了这条禁令，但 `HANDOFF.md:106-107` 的结论表仍用单次 LOO 排序。且 `review/LOO方差预演_n77.md` 自己实测：LOO 的种子间跨度 **0.0069** > 方法间差 **0.0043** ⇒ **排序信号小于噪声**。

- **数据集身份问题的独立证据（组织者已指出，本席复核确认）**：
  - [事实] 三批共 **2286** 个原始 case，字段为 `F,U,a,cell_value,ck,clicks,clicks9,confidence,groups,h,limitation,n_cand,num10,picked,total,w` —— **没有 seed / game_id / step 任何一个**（机检：0/2286）。⇒ 无法判断两个 case 是否来自同一局的相邻决策，**也无法做按局聚类**。

  ⇒ **P0-h｜验证集的独立性声明不成立**。这使 `review/P1预注册…md` 的整条验证逻辑（"验证集只评估一次"）失去意义：即使只评估一次，评估集里也含 16–18% 的发现集重复点。

## 12. 关键重算公式与数值（供复核）

全部用 Python 标准库（`math.comb` / `math.lgamma` / `statistics`），无第三方依赖。

```python
# 1) McNemar 精确检验（双侧）
def mcnemar_p(a_only, b_only):
    n = a_only + b_only
    if n == 0: return 1.0
    k = min(a_only, b_only)
    return min(1.0, 2*sum(comb(n,i)*0.5**n for i in range(k+1)))

# 2) 配对风险差 CI + MDE
def paired(a_only, b_only, n):
    d  = (a_only - b_only)/n
    var= ((a_only+b_only) - (a_only-b_only)**2/n)/n**2
    se = var**0.5
    return d, (d-1.96*se, d+1.96*se), (1.959964+0.841621)*se

# 3) Wilson CI
def wilson(k,n,z=1.96):
    p=k/n; d=1+z*z/n; c=p+z*z/(2*n)
    s=z*(p*(1-p)/n + z*z/(4*n*n))**0.5
    return ((c-s)/d,(c+s)/d)

# 4) 精确二项检验（对数空间，避免大整数溢出）
def binom_two_sided(k,n,p0):
    lp = lambda i: lgamma(n+1)-lgamma(i+1)-lgamma(n-i+1)+i*log(p0)+(n-i)*log(1-p0)
    obs = lp(k)
    return min(1.0, sum(exp(lp(i)) for i in range(n+1) if lp(i) <= obs+1e-9))

# 5) 首格为 0 的理论概率（Arbiter：只保首格本格安全）
P0 = comb(479-nb, 99)/comb(479, 99)   # nb=3 角落 -> 0.498463 ; nb=8 中心 -> 0.154487
```
