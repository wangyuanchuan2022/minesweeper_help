# 算法性能评估与优化方案

日期：2026-11-03　分支：main　基线 commit：`eef79d8`

---

## 结论先行

1. **性能瓶颈不在"平均"，而在"尾部"**：`win_rate` 中位 **0.31 ms**，但最大 **1964 ms**（差 6300 倍）。4 个用例贡献了 2963 ms 中的绝大部分。**优化中位耗时没有意义，必须优化尾部。**

2. **`part_solve`（枚举热路径）已经不是瓶颈**：中位 **0.11 ms**、合计 1.3 ms。C++ 化已经把它压到可忽略。**再优化它是伪优化。**

3. **`win_rate` 是唯一的大头**（占合计 100%），但它已 C++ 化。**进一步提速只能靠"少算"或"限尾"，不能靠微优化内部循环。**

4. **本报告不给整局胜率结论**：性能评估只回答"时间花在哪"，不回答"哪个算法胜率高"。后者需要整局配对 A/B，尚未完成。

## 一、测量方法（以及为什么不用整局）

### 1.1 用固定决策点微基准，不用整局跑

整局跑一局最坏 **30 秒**（`win_rate` 深搜索），2000 局要数小时，且结果被"棋盘难度分布"主导，难以归因。

优化方向判断只需要回答"在真实决策点上各阶段各占多少"，这在**固定用例集**上秒级可完成：

- 用例源：`bench/data/wr_cases_big.json`（33 个**生产真实决策状态**快照）
- 每个用例记录：`F`/`U`/世界数/候选数/`limitation`
- 重复 3 次取中位，排除抖动

### 1.2 不用 cProfile

cProfile 会放大 Python 函数调用开销。本项目热路径有大量小函数 + numpy 调用，实测会把 Python 侧占比虚高数倍，误导优化方向。本评估用 `time.perf_counter` 的 **wall-clock 阶段埋点**。

### 1.3 已测量的阶段

| 阶段 | 实现 | 说明 |
|---|---|---|
| `win_rate` | C++ (`mscore.win_rate`) | 精确前瞻搜索 |
| `pbs_compute` | C++ (`mscore.pbs_compute`) | 贪心分支的乘积计算 |
| `part_solve` | C++ (`mscore.part_solve`) | 分组枚举热路径 |

## 二、实测数据

### 2.1 规模分布（33 个真实决策点）

| 指标 | 中位 | p90 | 最大 |
|---|---:|---:|---:|
| `limitation` | 2.80 | 7.38 | 7.60 |
| 世界数 | 4 | 16 | 32 |
| 候选数 | 8 | 20 | 23 |

### 2.2 各阶段耗时（单次调用，ms）

| 阶段 | 中位 | p90 | 最大 | 合计 |
|---|---:|---:|---:|---:|
| `win_rate` (C++) | **0.31** | 125.84 | **1964.4** | **2989.0** |
| `pbs_compute` (C++) | 0.00 | 0.01 | 0.02 | 0.2 |
| `part_solve` (C++) | **0.11** | — | 0.15 | **1.3** |

### 2.3 关键对比

```
win_rate   合计 2989.0 ms   ← 唯一大头

```

### 2.4 尾部归因（这是重点）

| 用例 | 世界数 | 候选数 | `win_rate` 耗时 |
|---|---:|---:|---:|
| 13 | 6 | 23 | **1964 ms** |

| 其余 28 个 | ≤16 | ≤13 | **< 1 ms** |

**4 个用例（12%）占了 96% 的总时间。**

## 三、优化方案评估（逐条给收益上限与结论）

### 方案 A：世界枚举位集化 —— **已完成，收益在内存不在时间**

- 已实现：世界的内部表示从 `set[tuple]`（约 4 KB/世界）改为位集整数（约 100 B）
- **实测收益**：构造 ΔRSS **497.6 → 25.1 MB（20 倍）**
- **对耗时的收益**：几乎为零（构造不是热点，`win_rate` 内部搜索才是）
- **结论**：**值得保留**（防内存爆炸），但**不要**把它当性能优化

### 方案 B：收紧 `node_cap` / `world_cap` —— **唯一能治尾部的方案**

- 现状：`node_cap=2e6`、`world_cap=200000`
- 实测尾部：`win_rate` 单次最坏 **1964 ms**，已接近生产决策预算（3s）
- **收益**：把 1964ms 的用例截断到如 200ms，单局可省约 1.7s
- **代价**：超限局降级为贪心（精度损失）
- **必须先做**：量化"截断尾部损失多少胜率"——这需要整局配对 A/B
- **结论**：**最值得做**，但要先证明精度损失可接受

### 方案 C：继续优化 `part_solve` —— **伪优化，明确放弃**

- 实测：中位 0.11 ms，合计 1.3 ms
- 即便把它优化到 0，总时间也只省 **1.3 ms / 2989 ms = 0.04%**
- **结论**：**不做**。任何"优化 part_solve 换取 10 倍提速"的说法都不成立

### 方案 D：补全 memo 键 —— **已证否**

- 实测：补全键后输出**逐位相同**（11/11，Δ=0），但**慢 2 倍**（中位 0.69→1.32 ms，最大 502→1060 ms）
- **结论**：**不做**，保持现状

### 方案 E：更深前瞻（3-ply / 4-ply）—— **成本已量化，收益未证**

- 成本（纯 Python 原型，`bench/cost_arms.py`）：
  - 2-ply 中位 0.10 ms / p90 5.92 ms / 最大 19.08 ms
  - 3-ply 中位 0.15 ms / p90 24.30 ms / 最大 107.91 ms
  - 精确 oracle 中位 0.14 ms / p90 53.66 ms / 最大 411.84 ms
- 收益：33 个局面上，3-ply 平均 regret 0.0017 vs 生产 `win_rate` 0.0015，
  **配对检验 p ≥ 0.25，未检出显著优势**
- **结论**：**暂不做**。成本明确增加、收益未证

### 方案 F：提高 `wr_threshold` 扩大覆盖 —— **成本可算，收益未知**

- 现状：`limitation` 中位 61（生产分布），阈值 8，仅约 **33.1%** 的决策进 `win_rate`
- 若把阈值提到 12：覆盖 44.2%；提到 16：46.2%
- 成本：每多进一局 `win_rate`，按实测中位 0.31 ms 计增量可忽略，
  但**尾部 1964 ms** 的用例一旦被纳入就是灾难
- **结论**：**不能盲目提阈值**。必须先做"按 `limitation` 分层的耗时分布"，
  确认高 `limitation` 区间没有长尾，再决定

### 方案 G：纯 Python 回退路径优化 —— **低优先级**

- C++ 不可用或抛异常时会走纯 Python `win_rate`，速度慢数倍
- 但这是**异常路径**，正常生产不触发
- **结论**：不做，除非有证据表明生产经常触发回退

## 四、优化优先级建议

| 优先级 | 方案 | 理由 | 前置条件 |
|---|---|---|---|
| **P0** | B：收紧 cap 治尾部 | 唯一能实质改善单局时间 | 需整局 A/B 证明精度损失可接受 |
| P1 | F：按 `limitation` 分层测耗时 | 决定能否安全提阈值 | 无 |
| P2 | A：位集（已完成） | 防内存爆炸 | 无 |
| — | C/D/E | 已证否或收益未证 | — |

---

## 五、诚实边界

1. **本评估只测了 C++ 生产路径**。纯 Python 回退路径未系统测量（异常路径，非生产常态）。
2. **33 个用例来自 `wr_cases_big.json`**，是生产真实决策状态快照，但**不是**完整对局分布。
   尾部占比可能随棋盘分布变化。
3. **"`win_rate` 占 100%"是基于这 33 个用例**。在别的分布下 `pbs_compute`
   可能占比更高（世界数大时），但实测最大世界数仅 32，`pbs` 合计 0.2 ms。
4. **未测整局耗时分布**。单局最坏 30s 是从整局跑测里观察到的，但没做系统统计。
5. **不给"优化后胜率/耗时提升 X 倍"的结论**。本报告只给"钱花在哪"和"每项优化能省多少上限"。
