# 算法性能评估与优化方案

日期：2026-11-03　分支：main　基线 commit：`eef79d8`

---

## 结论先行

### A. 微基准（33 个固定决策点）—— 只用于**热点定位**

1. **性能瓶颈不在"平均"，而在"尾部"**：`win_rate` 中位 **0.31 ms**，但最大 **1964 ms**（差 6300 倍）。4 个用例贡献了 2989 ms 中的绝大部分。**优化中位耗时没有意义，必须优化尾部。**

2. **`part_solve`（枚举热路径）已经不是瓶颈**：中位 **0.11 ms**、合计 1.3 ms。C++ 化已经把它压到可忽略。**再优化它是伪优化。**

3. **`win_rate` 是唯一的大头**（占合计 100%），但它已 C++ 化。**进一步提速只能靠"少算"或"限尾"，不能靠微优化内部循环。**

⚠️ **以上三条只回答"时间花在哪"，不回答整局问题。** 33 个固定决策点不能代表完整对局分布。

### B. 短整局验收（120 局，固定种子配对，限时）—— 用于回答整局问题

4. **基线胜率 33.3%（120 局）**，与项目真实历史胜率 33.86%（316 局）吻合，说明台架可信。

5. **`safety` 与 `exact` 臂的"快"是假象**：它们 `clean` 局耗时与 baseline 几乎相同（63–70 ms vs 65 ms），
   但 **`safety` 有 107/120 局、`exact` 有 44/51 局触发了 `world_cap` 降级**。
   降级后走贪心，**那是"没算"不是"算得快"**。

6. **降级明显损害胜率**：
   - `safety`：clean 局胜率 **61.5%**（13 局）vs degraded 局 **29.0%**（107 局）
   - `exact`：clean 局胜率 **71.4%**（7 局）vs degraded 局 **20.5%**（44 局）
   - 整体 `safety` 32.5%、`exact` 27.5%，**均低于 baseline 33.3%**
   ⚠️ 这不是"算法更差"，而是**降级把前瞻优势吃掉了**。

7. **结论：当前 `world_cap=200000` 对这两个臂过于严格**。要让前瞻真正生效，
   必须先解决"合法大局面（如 U=471）下世界数爆炸"的问题，而不是靠降级掩盖。

### C. 本轮发现并修复的一个基准自身 bug（影响此前所有含采样的读数）

8. `sim/eval_harness.install_stubs()` 会把 `time.sleep` 替换为空操作（为了让求解器内部
   `sleep(0.1)` 不拖慢模拟）。这**同时**把我的后台 RSS 采样线程变成**忙等循环**，
   持续抢 GIL。实测同一 seed 同一臂：
   - 无采样：**946 ms**
   - 有采样（忙等）：**186987 ms** → **197.68 倍**
   修复后（采样线程用 install_stubs 之前的原始 sleep）：**0.98x，决策轨迹 hash 一致**。
   ⇒ **此前所有"带采样"的耗时读数都不可用**，本报告数据均为修复后重测。

## 一、测量方法（以及为什么不用整局）

### 1.1 用固定决策点微基准，不用整局跑

整局跑一局最坏 **30 秒**（`win_rate` 深搜索），2000 局要数小时，且结果被"棋盘难度分布"主导，难以归因。

优化方向判断只需要回答"在真实决策点上各阶段各占多少"，这在**固定用例集**上秒级可完成：

- 用例源：`bench/data/wr_cases_big.json`（33 个**生产真实决策状态**快照）
- 每个用例记录：`F`/`U`/世界数/候选数/`limitation`
- 重复 3 次取中位，排除抖动

### 1.2 不用 cProfile

cProfile 会放大 Python 函数调用开销。本项目热路径有大量小函数 + numpy 调用，实测会把 Python 侧占比虚高数倍，误导优化方向。本评估用 `time.perf_counter` 的 **wall-clock 阶段埋点**。

### 1.3 已测量的阶段

| 阶段 | 实现 | 说明 |
|---|---|---|
| `win_rate` | C++ (`mscore.win_rate`) | 精确前瞻搜索 |
| `pbs_compute` | C++ (`mscore.pbs_compute`) | 贪心分支的乘积计算 |
| `part_solve` | C++ (`mscore.part_solve`) | 分组枚举热路径 |

## 二·五、短整局验收（回答整局问题）

### 2.5.1 设计

- **固定种子配对**：120 局，seed = 20261102..20261221，各臂面对逐字节相同棋盘
- **限时**：每臂 240 秒预算（`--time-budget-s`），到点停止并保留已完成样本
- **四维记录**：效果（won/died/opened/steps）、耗时（每局 + 分位）、内存（峰值 RSS）、降级（`gate_stats` 分类）
- **可靠性**：逐局追加落盘 `.jsonl`、`flush=True` 进度、退出码记录、支持 `--resume`
- **按降级分层**：`clean`（全程未触发闸门）vs `degraded`（至少触发一次）

### 2.5.2 结果

| 臂 | 完成 | 整体胜率 | clean n | clean 中位 ms | clean 胜率 | degraded n | degraded 中位 ms | degraded 胜率 | 峰值 RSS | 降级次数 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| baseline | 120 | **33.3%** | 120 | 65 | 33.3% | 0 | — | — | 78.6 MB | **0** |
| safety | 120 | 32.5% | 13 | 63 | **61.5%** | 107 | 66 | **29.0%** | 103.6 MB | **389** |
| exact | 51 | 27.5% | 7 | 70 | **71.4%** | 44 | 55 | **20.5%** | 168.9 MB | **143** |

闸门明细：

```
baseline  {world_cap: 0,   invalid_case: 0, no_world: 0, node_budget: 0}
safety    {world_cap: 389, invalid_case: 0, no_world: 0, node_budget: 0}
exact     {world_cap: 136, invalid_case: 0, no_world: 0, node_budget: 7}
```

### 2.5.3 三个关键发现

**① 基线可信**：baseline 120 局胜率 **33.3%**，与项目真实历史 33.86%（316 局）吻合。
说明模拟台架与真实对局分布接近，读数有参考价值。

**② `safety`/`exact` 的"不慢"是假象**：它们的 clean 局耗时（63/70 ms）与 baseline（65 ms）
**几乎相同**，看起来"没有代价"。但实际 **safety 有 89%（107/120）、exact 有 86%（44/51）
的局触发了 `world_cap` 降级**——降级后走贪心，**那是"没算"不是"算得快"**。
若只看整体耗时（65 vs 66 ms）会得出"新算法没有性能代价"的错误结论。

**③ 降级把前瞻优势吃光了**：

| 臂 | clean 胜率 | degraded 胜率 | 差距 |
|---|---:|---:|---:|
| safety | 61.5%（13 局） | 29.0%（107 局） | **-32.5 pp** |
| exact | 71.4%（7 局） | 20.5%（44 局） | **-50.9 pp** |

整体胜率 safety 32.5%、exact 27.5%，**均低于 baseline 33.3%**。
但这不是"前瞻算法更差"——在 **clean 局上前瞻明显更好**（61.5%/71.4% vs 33.3%）。
**是降级把优势抵消了，还倒亏。**

⇒ **当前 `world_cap=200000` 对前瞻臂过于严格。** 要让前瞻真正生效，
必须先解决"合法大局面（如开局 U=471）下世界数爆炸"，而不是靠降级掩盖。

⚠️ **样本量警告**：clean 局只有 13（safety）和 7（exact），
上述胜率差距**未做 McNemar 检验**，不能宣称统计显著。

## 三、优化方案评估（逐条给收益上限与结论）

### 方案 A：世界枚举位集化 —— **已完成，收益在内存不在时间**

- 已实现：世界的内部表示从 `set[tuple]`（约 4 KB/世界）改为位集整数（约 100 B）
- **实测收益**：构造 ΔRSS **497.6 → 25.1 MB（20 倍）**
- **对耗时的收益**：几乎为零（构造不是热点，`win_rate` 内部搜索才是）
- **结论**：**值得保留**（防内存爆炸），但**不要**把它当性能优化

### 方案 B：收紧 `node_cap` / `world_cap` —— **唯一能治尾部的方案**

- 现状：`node_cap=2e6`、`world_cap=200000`
- 实测尾部：`win_rate` 单次最坏 **1964 ms**，已接近生产决策预算（3s）
- **收益**：把 1964ms 的用例截断到如 200ms，单局可省约 1.7s
- **代价**：超限局降级为贪心（精度损失）
- **必须先做**：量化"截断尾部损失多少胜率"——这需要整局配对 A/B
- **结论**：**最值得做**，但要先证明精度损失可接受

### 方案 C：继续优化 `part_solve` —— **伪优化，明确放弃**

- 实测：中位 0.11 ms，合计 1.3 ms
- 即便把它优化到 0，总时间也只省 **1.3 ms / 2989 ms = 0.04%**
- **结论**：**不做**。任何"优化 part_solve 换取 10 倍提速"的说法都不成立

### 方案 D：补全 memo 键 —— **已证否**

- 实测：补全键后输出**逐位相同**（11/11，Δ=0），但**慢 2 倍**（中位 0.69→1.32 ms，最大 502→1060 ms）
- **结论**：**不做**，保持现状

### 方案 E：更深前瞻（3-ply / 4-ply）—— **成本已量化，收益未证**

- 成本（纯 Python 原型，`bench/cost_arms.py`）：
  - 2-ply 中位 0.10 ms / p90 5.92 ms / 最大 19.08 ms
  - 3-ply 中位 0.15 ms / p90 24.30 ms / 最大 107.91 ms
  - 精确 oracle 中位 0.14 ms / p90 53.66 ms / 最大 411.84 ms
- 收益：33 个局面上，3-ply 平均 regret 0.0017 vs 生产 `win_rate` 0.0015，
  **配对检验 p ≥ 0.25，未检出显著优势**
- **结论**：**暂不做**。成本明确增加、收益未证

### 方案 F：提高 `wr_threshold` 扩大覆盖 —— **成本可算，收益未知**

- 现状：`limitation` 中位 61（生产分布），阈值 8，仅约 **33.1%** 的决策进 `win_rate`
- 若把阈值提到 12：覆盖 44.2%；提到 16：46.2%
- 成本：每多进一局 `win_rate`，按实测中位 0.31 ms 计增量可忽略，
  但**尾部 1964 ms** 的用例一旦被纳入就是灾难
- **结论**：**不能盲目提阈值**。必须先做"按 `limitation` 分层的耗时分布"，
  确认高 `limitation` 区间没有长尾，再决定

### 方案 G：纯 Python 回退路径优化 —— **低优先级**

- C++ 不可用或抛异常时会走纯 Python `win_rate`，速度慢数倍
- 但这是**异常路径**，正常生产不触发
- **结论**：不做，除非有证据表明生产经常触发回退

## 四、优化优先级建议（已按短整局验收结果修正）

**重要修正**：短整局验收推翻了"收紧 cap 是 P0"的初判。
`world_cap=200000` 已经让 safety 89%、exact 86% 的局降级，
**继续收紧只会让前瞻彻底失效**。真正的 P0 变成"解决合法大局面下的世界数爆炸"。

| 优先级 | 方案 | 理由 | 前置条件 |
|---|---|---|---|
| **P0** | **解决合法大局面（U 很大）的世界数爆炸** | 当前 89%/86% 的局在降级，前瞻根本没机会生效；clean 局胜率 61.5%/71.4% 证明它有价值 | 需设计不靠"判非法"的解法（分层采样 / 局部枚举 / 只算候选格边际） |
| P1 | B：**放宽**（而非收紧）cap + 配套限时 | 降级是当前胜率损失的主因；但放宽会撞内存，必须同时有超时中断 | P0 完成后 |
| P1 | F：按 `limitation` 分层测耗时 | 决定高 limitation 区间的真实代价 | 无 |
| P2 | A：位集（已完成） | 防内存爆炸 | 无 |
| — | C（part_solve）/ D（memo 键） | 已证否：C 收益上限 0.04%，D 慢 2 倍 | — |
| — | E（3-ply） | 成本已量化（p90 24ms），收益未证（p≥0.25） | — |

## 五、诚实边界

1. **微基准部分只测了 C++ 生产路径**。纯 Python 回退路径未系统测量（异常路径，非生产常态）。
2. **33 个用例来自 `wr_cases_big.json`**，是生产真实决策状态快照，但**不是**完整对局分布。
   尾部占比可能随棋盘分布变化。
3. **"`win_rate` 占 100%"是基于这 33 个用例**。在别的分布下 `pbs_compute`
   可能占比更高（世界数大时），但实测最大世界数仅 32，`pbs` 合计 0.2 ms。
4. **短整局验收的 clean 局样本极小**（safety 13、exact 7），
   61.5%/71.4% 的胜率**不能**当作可靠估计，也**未做** McNemar 检验。
5. **`exact` 臂只完成 51/120 局**（限时 240s 到点），其整体胜率 27.5% 与
   baseline 不可直接比较（样本不同）。
6. **2000 局全量基线未完成**。500 局曾中断且结果缺失，见 `review/分级验证状态.json`。
7. **本报告是优化前基线**，不含任何"优化后提升 X 倍"的结论。
