## 二、命题的正确表述与证明

### 2.1 精确表述

设状态 `S`，候选格集合 `C(S)`。对候选 `c`：

```
after(c) = P(c 不是雷) × E[ 点开 c 后、用最优策略续玩能拿到的胜率 | c 不是雷 ]
V*(S)    = max_{c∈C(S)} after(c)
```

命题：若 `safety(c) = P(c 不是雷) = 1`，则 `after(c) = V*(S)`。

**证明（构造性）**：`c` 必然安全 ⇒ 点开它不会输。点开后得到的观测 `o` 是新的信息；
在 `o` 下按最优策略继续，可达胜率 `V*(S|o)`。而"先点 `c` 再按最优策略"本身就是
一个合法策略，故其胜率不超过 `V*(S)`；另一方面，任何从 `S` 出发的最优策略，
若第一步不是 `c`，可以改成"先点 `c`（零风险），再执行原策略"，所得信息单调不减，
故胜率单调不减。两者夹逼得 `after(c) = V*(S)`。∎

**关键前提**：① 无点击次数/时间成本惩罚；② 允许在拿到信息后改变后续策略；
③ "信息单调不减"成立（多看到一些已开格不会让局面变差）。
现实中若存在点击预算或时间压力，该命题可能不成立——这也是为什么生产实现里
"免费推理饱和"必须优先把安全格开掉。

### 2.2 机检结果

| 检验项 | 口径 | 样本 | 违反 |
|---|---|---|---|
| 弱占优 `after(c) ≥ V*` | 不预先饱和，逐候选评估 | 23 个安全格 / 6 个用例 | **0** |
| 强等式 `after(c) == V*` | 同上 | 23 | **0** |
| 风险格严格优于所有安全格 | 同上 | 6 个用例 | **0** |

脚本：`bench/verify_safe_dominance.py`、`bench/verify_all_oracles.py`

## 三、枚举器 bug：本轮最重要的发现

### 3.1 缺陷

`bench/compare_2ply_vs_winrate.py` 的 `enumerate_worlds` 原实现：

```python
for gi, sel in enumerate(idx):
    row = groups[gi][sel]
    for ci, v in enumerate(row):
        if v == 1:
            fm.append(clicks[ci])     # ← ci 只是"本组列号"
```

`groups[gi]` 的第 `ci` 列对应的是**该组自己的第 ci 个前沿格**，而不是全局
`clicks[ci]`。组 1 的雷因此被错写到组 0/2/3 的坐标上并互相覆盖。

### 3.2 后果

- 用例 3：`a=99`，但枚举出的 52 个世界雷数只有 95/96/97。
- 所有下游量（每格雷概率、safety、V\*、各臂排名）系统性偏移。
- 修正后用例 3 的 `V*` 从 0.8462/1.0000（两实现互相矛盾）变为 **0.2692**（三实现一致）。

### 3.3 为什么"两个独立实现对拍"没抓住它

我写的 `ExactEngine`（位运算）与 `Indep`（frozenset）**都调用同一个
`enumerate_worlds`**。共享了错误输入源 ⇒ 两边一起错、且错得一致，
"读数一致"反而给出了虚假的安全感。

**这条教训已写入脚本注释**：验证实现独立性时，必须确认**输入构造**也独立。

### 3.4 修复

```python
group_offset = []
_off = 0
for g in groups:
    group_offset.append(_off)
    _off += len(g[0])

for gi, sel in enumerate(idx):
    row = groups[gi][sel]
    base = group_offset[gi]
    for ci, v in enumerate(row):
        if v == 1:
            fm.append(clicks[base + ci])
```

并在 `emit()` 中加入**守恒断言**（`validate=True` 默认开启）：

| 断言 | 内容 |
|---|---|
| ① | 世界在 `w×h` 盘面内的雷数 **严格等于 `a`** |
| ② | 基底已标记雷全部包含在世界内 |
| ③ | 世界内不含任何已开格 |
| ④ | `num10 + 前沿雷 + 内部雷 == 总数` |
| ⑤ | 组列总数 `== len(clicks)`（分组与 clicks 同序） |

回归脚本：`bench/verify_world_enum.py` → **11/11 用例雷数分布恰好 `{99}`，失败 0**。

## 五、精确引擎的语义与两处必须保留的坑

引擎忠实实现真实扫雷规则：世界 = 与观测一致的完整雷布局（均匀先验、等权）；
点开后按实际布局算数字并 flood-fill（0 连锁展开）；观测分支 = 已开集合 + 新开格数字；
胜利 = 已开格数 == `w*h - a`。

**坑 1：免费推理饱和必须"逐格开、每格重新分叉"**
批量一次开掉所有必然安全格会破坏观测因果顺序（哪几格被 0 连锁带开取决于具体布局），使 `V*` 系统性偏低。实测同一局面从 0.4615 漂到 0.3077。

**坑 2：免费推理必须"完全饱和（对所有分叉递归）"，不能一遇分叉就返回**
只开一个安全格、遇分叉即返回，会使结果依赖"先开哪个安全格"。实测同一局面
两个实现给出 1.0000 / 0.8462 且都自洽——这是最隐蔽的一类错误。

正确写法：

```python
def saturate(self, wkey, opened, weight=1.0):
    while True:
        union, _ = self._union_inter(wkey)
        safe = self.all_mask & ~opened & ~union
        if not safe:
            return [(wkey, opened, weight)]
        cell = (safe & -safe).bit_length() - 1     # 确定性取一个
        outs = {}                                   # 按观测分桶
        ...
        if len(outs) == 1:                          # 收敛：继续饱和
            opened, wkey = ...; continue
        res = []                                    # 分叉：对每个分支递归
        for k, v in outs.items():
            res.extend(self.saturate(frozenset(v), k[0], weight * len(v) / n))
        return res
```

## 六、算法臂对比（33 个局面，仅选格质量）

口径：在同一决策状态（免费推理饱和后）比较各臂首格；质量 = 该格点开后
用完美策略续玩的胜率；`regret = 该状态 V* − 选中格质量`（0 = 选对）。

| 臂 | 平均 regret | 最大 regret | 全对用例 | 总损失 |
|---|---:|---:|---:|---:|
| 纯 safety | 0.0044 | 0.0714 | 28/31 | 0.1353 |
| 期望展开（信息增益代理） | 0.0090 | 0.1667 | 28/31 | 0.2798 |
| 2-ply 前瞻 | 0.0075 | 0.1000 | 27/31 | 0.2313 |
| 3-ply 前瞻 | 0.0017 | 0.0312 | 29/31 | 0.0535 |
| **生产 win_rate** | **0.0015** | 0.0417 | **27/28** | **0.0417** |

配对符号检验（`bench/summarize_arms.py`）：

| 比较 | A 更好 | B 更好 | n | p 值 | 判定 |
|---|---:|---:|---:|---:|---|
| 3-ply vs 纯 safety | 2 | 1 | 31 | 1.000 | 不显著 |
| 2-ply vs 纯 safety | 2 | 4 | 31 | 0.688 | 不显著 |
| 3-ply vs 2-ply | 3 | 0 | 31 | 0.250 | **不显著** |
| 生产 win_rate vs 纯 safety | 2 | 0 | 28 | 0.500 | 不显著 |
| 生产 win_rate vs 3-ply | 2 | 1 | 28 | 1.000 | 不显著 |

**读法**：33 个局部局面上，没有任何前瞻臂显著优于另一个，也没有显著优于生产
`win_rate`。因此**不能据此宣称"换算法能提升胜率"**。

### 各臂具体分歧

| 用例 | V* | 生产 win_rate | 最佳臂 |
|---|---:|---|---|
| 7 | 0.2083 | regret 0.0417，选 (6,1) safety=0.6667，wr_f 报 0.3125 | 2-ply / 3-ply（regret 0） |
| 22 | 0.8571 | regret 0（正确） | — |
| 32 | 0.4222 | regret 0（正确），wr_f 报 0.4222 | — |
| 2 | 0.1667 | regret 0（正确） | 3-ply 也正确；2-ply 错 0.0556 |
| 19 | 0.2812 | regret 0（正确） | 2-ply / 3-ply 均错 0.0312 |
| 23 | 0.4000 | regret 0（正确） | 2-ply 错 0.1000 |

即：生产 win_rate 有它自己的错误，前瞻臂也有；**在 33 个局面的样本里这两类错误没有检出系统性方向差异**。这不等于"前瞻和 win_rate 一样好"——样本量只够说"未检出"，不够说"等效"。

## 九、建议

1. **暂无充分依据替换生产算法**：33 个局部局面的 regret 差异不显著，样本量不足以下"换/不换"的结论。要判定必须跑完整局配对 A/B。
2. **优先修 `enumerate_worlds` 的调用方**：如果生产诊断脚本或此前的
   算法评估曾引用过它，那些读数需要重算。生产运行路径（`utils/probability.py`
   → `cpp/mscore.cpp`）**不经过**这个 bench 函数，因此生产行为未受影响。
3. **守卫 `win_rate` 的内存闸门保留**：`_wr_memory_ok` 已在上一轮加入，
   与本轮改动无关，仍然有效。
4. 若要继续推进胜率，最有希望的方向不是"更深的前瞻"，而是
   **扩大 `win_rate` 的触发覆盖**（`limitation` 中位数 61，阈值 8，
   仅 33.1% 的决策能进前瞻）；但这需要先有整局 A/B 台架证明边际收益，
   且必须解决尾部 2秒级耗时问题。
