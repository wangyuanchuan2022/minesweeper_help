## 一、判据（三条，全部预先冻结）

设 C++ 路径全样本 ok 率为 **R**（分母 = 462 个合格点，与 P1-c 同口径）。

| 情形 | 判定 | 后续行动 |
|---|---|---|
| **R ≥ 0.80** | **假缺口主导** ⇒ 上一轮"结构性阻塞"结论**撤销** | 恢复第 4–7 步：用 C++ 口径重建矩阵 → 权重优化 → 验证集一次 → 整局 A/B |
| **0.60 ≤ R < 0.80** | **部分可救** ⇒ 阻塞结论**降级为"受限但可推进"** | 用 C++ 口径重建矩阵，但报告必须限定适用范围；整局 A/B 预期收益仍低 |
| **R < 0.60** | **瓶颈是枚举规模** ⇒ 阻塞结论**维持** | 收口为报告阻塞，不再投权重优化 |

### 参照基准

| 口径 | ok 率 | 说明 |
|---|---:|---|
| Python `time_cap=30s`（P1-c 原始） | **40.3%** | 186/462，待替代 |
| 若 R 与 40.3% 无差异（< +5pp） | 说明 C++ 提速未转化为覆盖率 ⇒ 直接判"维持阻塞" |
| 理论天花板 | ≤100% | 有 17 点 `no_terms` 结构性不可算 ⇒ 实际上限约 96.3% |

**注意**：17 个 `no_terms` 点（worlds 极小但无可达终局）在**任何**口径下都不算 ok，
因此 R 的理论上限是 (462−17)/462 = **96.3%**，不是 100%。

## 二、必须同时验证的第二件事（Advisor 第一条）

**"覆盖率上升" ≠ "口径统一"。** 我已证明 `saturate` 会改写候选集与 q 定义：

- 实例：`(14,4)` 被 saturate 移出候选集，v2 加权给 0.25，C++ 从原状态给 0.375
- 实例：`(8,15)` 在所有终端中都是候选，加权 0.375 **恰好等于** C++ ⇒ 覆盖全时才对齐

⇒ 因此本轮**不得只重测覆盖率**。必须让以下三条路径统一到 C++ 全枚举口径：

| 路径 | 当前口径 | 是否需切换 |
|---|---|---|
| P1-c 覆盖率分类 | Python saturate + 30s | ✅ 本轮切到 C++ |
| F 矩阵构建（`mm_full_v2.json`） | **v2 = Python saturate 多终端加权** | ✅ **必须重建** |
| regret / q 评估（`merged_regret.json`） | 全枚举 + C++（`merge_and_eval_cases.py`） | ✔ 已经是正确口径，无需改 |

**重要更正预告**：我上一轮的 `mm_full_v2.json` 虽修掉了"只取 terms[0]"，但其
**聚合口径仍建立在 saturate 状态上**，对"部分终端已开出该格"的情形仍会算错
（(14,4) 一类）。因此 v2 **不是**最终可用矩阵；需重构为"C++ 从初始状态直接算 q +
指标在初始候选集上算"的版本（v3）。

这一点我上一轮没有意识到，Advisor 指出后我认为成立。
