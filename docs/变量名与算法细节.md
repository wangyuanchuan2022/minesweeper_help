## 1. 最容易误解的变量名（逐条警告）

### 1.1 `num10` —— 不是"数字 10 的个数"，是**已被标记为雷的格数**

```python
for index in range(1, w + 1):
    for j in range(1, h + 1):
        if cell_value[j, index] == 10:
            num10 += 1
```

- `cell_value` 用 `10` 表示"玩家插旗标记为雷"的格。
- 所以 `num10` = **已标记雷数**，不是"值为 10 的数字格个数"这种说法容易引起的歧义
  （它确实是数 10，但 10 的语义是"标记的雷"，不是"十号数字"）。
- ⚠️ **关键推论**：真实剩余雷数 = `a - num10`，**不是** `a`。
  很多地方（如 `rem = a - num10 - mine_total`）都依赖这一点。
- 混淆后果：算出的世界雷数会整体偏大或偏小。本项目曾因**世界枚举器的列号错位**
  （`fm.append(clicks[ci])` 应为 `clicks[base + ci]`）导致每个世界雷数是 95/96/97
  而真实 `a=99`，所有下游概率、safety、V\* 全部"自洽地错"。

### 1.2 `ck` —— 不是"检查/click"，是**每组解的数量（笛卡尔积的模长）**

```python
ck = []          # res_list 中 res 的长度
...
total *= _total  # total 是各组解数的乘积 = 世界总数
ck.append(_total)
```

- `res_list[i]` 是第 i 组的**所有解**（二维矩阵：行=解，列=该组覆盖的前沿格）。
- `ck[i] == len(res_list[i])`（该组的解数）。
- `total = ∏ ck[i]` = 所有组合的**世界总数**（枚举出的完整雷布局数）。
- ⚠️ `ck` 里存的是**每组的解数**，不是"每组格数"。两者极易混淆：
  - 每组覆盖多少个前沿格 = `res_list[i].shape[1]`
  - 该组有多少个解 = `res_list[i].shape[0]` = `ck[i]`
- 遍历所有世界 = 对 `ck` 做多重笛卡尔积（`Odometer(ck)` / `itertools.product`）。

### 1.3 `clicks` 与 `clicks9` —— 不是"点过的格"与"点 9 次的格"

```python
clicks = []   # 外围未开方格（与已开数字格相邻 → 受约束）
clicks9 = []  # 内部未开方格（远离已开格 → 无约束，只受总雷数约束）
```

判定依据是**距最近"未开格/标记格"的距离**（`cv.distanceTransform`）：

```python
if res[j, i] <= 1.5 and cell_value[j + 1, i + 1] == 9:
    clicks.append(...)       # 前沿（有约束）
elif res[j, i] > 1.5 and cell_value[j + 1, i + 1] == 9:
    clicks9.append(...)      # 内部（无局部约束）
```

- `clicks` = **前沿未开格**（frontier），受邻域数字约束，需要枚举解。
- `clicks9` = **内部未开格**（"9" 指格子的值 9=未开，不是"第 9 类"），
  远离已知信息，只受"剩余雷数"这一个全局约束。
- ⚠️ 注意 `clicks9` 中的 "9" 来自 `cell_value` 的编码 `9 = 未开`，
  **不是**"9 个"或"第九组"。

**`cell_value` 编码表（全局统一，务必记住）**：

| 值 | 含义 |
|---|---|
| `9` | 未开格 |
| `10` | 玩家标记为雷（插旗） |
| `0..8` | 已开数字格（该格 3×3 邻域雷数） |

⚠️ 内部真实棋盘另用 `-1` 表示雷，但**这个值不会出现在 `cell_value` 里**
（信息隔离：求解器只能看到 `9/10/0..8`）。

### 1.4 `limitation` —— 不是"限制值"，是**局面难度代理指标**

```python
limitation = len(clicks9) * 0.8 + math.log2(total)
```

- 它是**衡量"这个局面有多难算"的分数**，不是任何阈值。
- `len(clicks9)` = 内部无约束格数（这些格会组合爆炸）。
- `total` = 世界总数（`log2` 后是"世界数的量级"）。
- 用法：`if limitation <= wr_threshold` 才进 `win_rate`（精确前瞻），否则走贪心。
- ⚠️ 所以 `limitation` **越大越难**，`wr_threshold` 是"允许多难的局面进前瞻"的门槛。
  两者方向一致（都是越大越宽松），但**含义不同**：前者描述局面，后者是策略参数。
- 别名陷阱：`self.limit`（注意不是 `limitation`）是**组枚举上限**（超过该组大小的组
  会被放弃、并入 `clicks9`），是完全不同的东西。

### 1.5 `win_rate` 的返回值 —— 第一个不是"胜率"，是**逐候选格的胜率数组**

```python
_res, _clicks, _total, _clicks2p = native.mscore.win_rate(...)
#  _res:      list[float]，与 _clicks 对齐的逐格胜率
#  _clicks:   list[(x,y)]，**已按 clicks2p 降序重排**后的候选格
#  _total:    int，世界总数
#  _clicks2p: dict[(x,y)] -> float，"该格不是雷"的概率（safety）
```

⚠️ 三个高频误解：

1. **`win_rate` 返回的是数组，不是标量。** 要选格得自己取 `argmax`。
2. **返回的 `_clicks` 顺序已变**（内部做了 `stable_sort` 按 safety 降序）。
   拿它和传入的 `clicks` 按下标对齐会**错位**。
   本会话曾因此误判"`win_rate` 对点击顺序敏感"，实为**测试构造错误**：
   `clicks[i]` 与 `groups` 的列是绑定的（`r[i]==1` ⇒ `clicks[i]` 是雷），
   只反转 `clicks` 而不动 `groups` 等于构造出**不同的棋盘**。
3. **`clicks2p` 是按"排序前"的原始插入序构建的**（C++ 里用 `orig_clicks`），
   而 `_clicks` 是排序后的。两者要按**坐标**匹配，不能按下标。

### 1.6 `confidence` —— 在不同分支含义不同，务必看分支

- `win_rate` 分支：`confidence = win_rate[arg]`（**前瞻胜率**）
- `process_bigger_situation` 分支：`confidence = round(max_val, 5)`
  （**该格不是雷的概率**，即 safety）
- 随机分支：`confidence = 1 - (self.a - num10) / len(clicks9)`（均匀先验 safety）

⚠️ 它们不是同一个量，日志/统计里混用会造成误读。写校准或统计代码时，
必须以 `_last_heatmap["best_conf"]` 为准并注意其来源分支。

### 1.7 `res_list` —— 不是"结果列表"，是**每组的全部解**

- `res_list[i]` 形状 `[解数 × 该组前沿格数]`，元素 0/1（1=该格在此解中是雷）。
- 它是 `part_solve` 的返回值之一，喂给 `win_rate` / `pbs_compute` 做世界枚举。
- ⚠️ **`res_list[i]` 的列只对应第 i 组自己的前沿格**，不是全局 `clicks`。
  跨组引用时必须加组偏移（这是本会话修掉的那个 bug 的根源）。

### 1.8 `target` / `p` / `pos` —— 都是"候选格"，但类型不同

| 名字 | 类型 | 含义 |
|---|---|---|
| `pos` | `list[(x,y)]` | 最终选中的点击（通常 1 个元素） |
| `p` | `np.ndarray` 或 `float` | **重载严重**：既是概率分布数组 `p`，又是循环变量 `for p in range(...)` |
| `target` | 视上下文 | 有时是目标格，有时是统计目标数 |

⚠️ `p` 在 `number5_1` 里被复用了至少三种含义（概率向量、循环下标、概率值）。
读这段代码时**必须逐个作用域确认**，不要凭名字推断。

## 2. 算法细节（反直觉处）

### 2.1 `number5_1` 的三条决策分支（优先级从高到低）

```
1. len(clicks) == 0  且 len(clicks9) == 0
   → 识别错误/无未开格：全盘重置为 9，重新 complete_scan，return

2. len(clicks) == 0（只有内部格）
   → 随机分支：按 open_num5x5（5×5 内已开格数）加权随机选一格
   → confidence = 1 - (a - num10)/len(clicks9)（均匀先验）

3. len(clicks) > 0（有前沿格）
   → 先做分组 + part_solve 枚举，得到 res_list / ck / total
   → 然后二选一：
      a) limitation <= wr_threshold 且 _wr_memory_ok(...)
         → win_rate（精确前瞻），失败/超限则降级到 b)
      b) 否则 → process_bigger_situation（贪心/近似）
```

⚠️ 注意 `_prob`（热力图数据）由**各分支就地设置**，不要在外层统一重建。
源码里有明确注释说明这一点（曾因在外层重建而 `UnboundLocalError`）。

### 2.2 `win_rate` 的真实语义：它是**启发式**，不是精确最优胜率

这一点极其重要，因为"胜率"这个词会让人以为是精确值。

`cpp/mscore.cpp` 的 `wr_f`（递归核心）有四处与真实扫雷规则不符：

| # | 位置 | 问题 |
|---|---|---|
| a | `wr_f` 点开一格时 `nb[u,v] = c10` | 只把该格写成"邻域已标雷数"，**不做 flood-fill 展开**。真实点开 0 会连锁开一大片，免费信息被系统性低估 |
| b | 世界划分用"邻域雷数桶"近似 | 不按实际观测到的数字重建约束 |
| c | `depth > depth_limit` 时 `return 1.0` | 截断处**高估**胜率 |
| d | `depth_limit = 200 / len(clicks)` | 候选越少允许越深，但仍是截断 |

⇒ **`win_rate` 是启发式估值，不是 V\*(S)。** 若需要真值，用 `bench/arms_lookahead.py`
的 `ExactEngine`（忠实实现 flood-fill + 按观测重建世界）。

### 2.3 `wr_f` 的剪枝是正确的，**不要删**

```cpp
if (i > 1 && cp[i] < running_max) continue;   // 剪枝
```

证明：
```
win_rate(c) = safety(c) × E[点开 c 后继续获胜 | c 不是雷]  ≤  safety(c)
```
候选已按 `cp`（safety）降序排序，若第 i 个的 `cp[i] < running_max`，则
其后所有候选的 `win_rate ≤ 各自 safety ≤ cp[i] < running_max`，**不可能更优**。

⇒ `cp` 是 `win_p` 的**上界**，按 safety 降序 + 该剪枝是最紧的分支定界。
本会话曾误删此剪枝并声称"顺序敏感"，已回退。

### 2.4 `wr_f` 的 memo 键**不完整但不要改**

```cpp
ctx.memory[ctx.hash_board(boards[0])] = mx;   // 只取 boards[0]
```

- 键 = 第一个世界的盘面哈希（`>9 → 9` 归一化后 MD5），**不含 clicks/depth**。
- 理论上不完整，实测补全键后输出**逐位相同**（11/11，Δ=0）但**慢 2 倍**
  （中位 0.69→1.32 ms，最大 502→1060 ms）。
- ⇒ **保持原样**。这是"理论上有问题但实际无影响且改了对性能有害"的典型案例。

### 2.5 `wr_f` 的 memo **只写不删** —— 这是内存风险的根源

```cpp
ctx.memory[ctx.hash_board(boards[0])] = mx;   // 只写，从不 erase
```

- 所以 `live_nodes == 累计访问节点数`（不是"当前递归深度"）。
- 节点数随 `候选数 × 世界分叉 × 深度` **组合增长**，可到 1e7 量级。
- ⇒ 这才是内存爆炸的真因；**压缩世界表示（位集）几乎无用**（实测总内存
  19.2MB → 19.1MB），真正的防护是节点数封顶（见 2.6）。

### 2.6 `node_cap` 防护：三处设计不可随意改

```python
_wr_node_cap()            # 默认 2e6；环境变量 MSW_WR_NODE_CAP 可覆盖，0=关闭
_WrNodeCapExceeded        # 专用异常
number5_1 的 except 分支  # 降级走 process_bigger_situation
```

三条**不可改**的理由：

1. **超限不回退纯 Python**：纯 Python 的 `f()` 同样无上限，退过去等于没拦。
   必须降级走贪心（`process_bigger_situation`）。
2. **不让异常落到外层 `except`**：`number5_1` 外层把所有异常当"求解失败"→
   触发完整重扫，那比降级更糟。
3. **只有含 `"node cap exceeded"` 的异常才降级**：其他 `runtime_error`
   保持原有"回退纯 Python"语义，不能被静默吞成贪心结果。

⚠️ 默认值是 **2e6**，标定依据是内存预算（每节点实测 15–21B，2e6×25B≈48MB，
对照 1.5GB 预算留 30x 余量），**不是**"本机用例是否会触发"。
防护器的预期行为就是**正常路径不触发**——实测本机最大节点需求 424,114，
所以 2e6 零触发是正确的。

### 2.7 `process_bigger_situation` 有**两种返回形态**

```python
# 形态①：触发内部重扫（无解/识别异常）
return cell_value              # 一个 np.ndarray

# 形态②：正常返回
return pos, confidence, total, _prob    # 四元组
```

⚠️ 调用方 `pos, confidence, total, _prob = self.process_bigger_situation(...)`
只处理形态②。若写 wrapper 拦截此函数，**必须**原样透传形态①，否则会
`ValueError: too many values to unpack`。

另一个陷阱：`process_bigger_situation` 是**方法**，把它换成普通函数赋给类属性时，
Python 会自动把 `self` 作为第一个位置参数传入。所以 wrapper 签名必须
**显式写 `self`**：

```python
def pbs_arm(self, total, num9, num10, clicks, clicks9, res_list, ck,
            cell_value, pos):        # ← self 必须在
```

用 `def pbs_arm(*args)` + 按类型猜位置会错位（本会话踩过：`args[0]` 是 `Solver`）。

### 2.8 `_pbs_compute_dp`：生成函数 DP（跨组雷数耦合）

- 旧实现的错误假设：各组雷数独立、逐组归一化。
- 正确权重：`W(m_1..m_G) = ∏ H_g(m_g) · C(U, R − Σm_g)`
  其中 `H_g(m)` 是第 g 组恰有 m 颗雷的解数直方图，`R = a - num10`，
  `U = len(clicks9)`。
- 缺失的是 `C(U, R − Σm)` 这一项（跨组耦合），单组时该项为 1 所以**只在多组大局面暴露**。
- 实现分 Python（`_pbs_compute_dp`）与 C++（`pbs_compute`）两处，**必须同步改**。

### 2.9 `part_solve` 与 `part_solve_single` 的区别

| 函数 | 返回 | 用途 |
|---|---|---|
| `part_solve(clicks, cell_value, num10, num9, cs, _try=False)` | `(res_matrix, total, canopen_res)` | 枚举一个组的**全部解** |
| `part_solve_single(clicks, cell_value, num10, num9, cs, _try=True)` | `(res_matrix, num)` | 单格/试解评估 |

⚠️ `_try` 参数默认值不同（`part_solve` 是 `False`，`part_solve_single` 是 `True`），
且 `_try=True` 时走 Python 逻辑（不走 C++）。改优先级逻辑时注意这个开关含义反转。

### 2.10 坐标系：`cell_value` 是 1-based，且含 1 格外框

```python
cell_value.shape == (h + 2, w + 2)
# 索引 cell_value[y][x]，x ∈ [1, w]，y ∈ [1, h]
# 外框（第 0 行/列、第 h+1/w+1 行/列）恒为 0
```

- 所有 `clicks` / `clicks9` / `pos` 里的坐标都是 **1-based**。
- 屏幕点击换算：`pyautogui.click(bx + p[0] * cell_width, by + p[1] * cell_width)`
  —— 注意这里直接用 1-based 值乘，反算格子时**要减 1**：
  ```python
  x = int(round((px - bx) / cell_width)) - 1     # → 0-based
  ```
  本会话在评估台里曾因漏减 1 导致全线偏移一格、每局第一步就踩雷。
- C++ 侧用 `W2 = w + 2`，位索引 `y * W2 + x`。

### 2.11 模拟器的首点规则（Arbiter 保真）

```python
# sim/minesweeper_sim.py Board.generate
pool = [(x, y) for y in range(h) for x in range(w)
        if not (x == first_x and y == first_y)]      # 只跳过首点本格
```

- Arbiter 真实机制是**延迟布雷**：先点开首格，再布雷，拒绝采样只跳过**已开格**。
- ⇒ **只保证首点本格安全，不保证 3×3**。布雷后首格数字常 >0，所以开局常只有 1 个数字格。
- 实测（400 局）：真实首点平均展开 **7.7 格**、83.2% 只开 1 格；
  旧"3×3 排除"实现是 41.2 格、0%——**白送 5.3 倍已知区域**，系统性高估胜率。

### 2.12 信息隔离契约（不可破坏）

- 求解器只能拿到 `BoardView`（`sim/minesweeper_sim.py`），其中只有 `9/10/0..8`。
- 真实雷位只存在 `Board.mines`，**绝不**进入 `cell_value`。
- `BoardView.audit_no_leak()` 做审计，评估台每局开头都会调用。

## 3. 评估台与 bench 脚本的坑

### 3.1 `is_play` 控制剪枝，不是"是否在玩"

- `is_play=True` → `win_rate` 启用剪枝（`cp[i] < running_max`）
- `is_play=False` → **不剪枝**，且会记录 `pos_dict_list`（给 UI 用）
- 评估生产行为时**必须**设 `is_play=True`，否则测量的是另一套算法。

### 3.2 `_time_budget = None` 会让 `wr_threshold` 退化为常量

```python
# probability.py
wr_threshold = 6 + (native.LIMIT_BONUS_WIN_RATE if native.tuned() else 0)
```

`_wr_current_threshold(_tb)` 只在 `_tb is not None` 时被调用。
所以评估台里 `s._time_budget = None` 时，**改 `_wr_current_threshold` 是无效的**，
必须改 `native.LIMIT_BONUS_WIN_RATE`。
（本会话实测：阈值 8 与 999 两臂逐局完全一致，因为两臂实际都在用 8。）

### 3.3 同一进程连跑多局必须重置 numpy 全局随机态

```python
np.random.seed(seed)     # 每局开头必须
```

求解器内部大量使用 `np.random.choice` / `shuffle`（随机分支、平局随机选点）。
不重置会导致同 seed 重跑结果不同（实测 40 局中 8 局不一致）。

### 3.4 `enumerate_worlds` 必须配合守恒断言

`bench/compare_2ply_vs_winrate.py` 的 `enumerate_worlds(case, validate=True)`
会用断言检查：世界雷数严格 `== a`、基底雷全含、世界内无已开格、雷数分项守恒、
组列总数 `== len(clicks)`。

⚠️ 这个 bug 曾让每个世界雷数变成 95/96/97（真实 99），所有下游读数系统性偏移。
**任何使用 `enumerate_worlds` 的新代码都应该 `validate=True`。**

### 3.5 "两个独立实现读数一致"不能证明正确

本会话的实证：`ExactEngine`（位运算）与 `Indep`（frozenset）都调用同一个
`enumerate_worlds`，共享错误输入源 ⇒ 一起错、且错得一致。

⇒ 验证实现独立性时，**必须确认输入构造也独立**。
真正独立的参考实现是 `bench/oracle_bruteforce.py`（只读 `cell_value` 重枚举世界，
完全不碰 `clicks/clicks9/groups/ck`）。

### 3.6 免费推理饱和：两个必须遵守的规则

在精确引擎里，"把必然安全格开掉"（免费推理）有两条规则，
违反任意一条都会得到**自洽但错误**的数值：

1. **逐格开、每格重新分叉**。批量一次开掉所有必然安全格会破坏观测因果顺序
   （哪几格被 0 连锁带开取决于具体布局），使 V\* 系统性偏低
   （实测同一局面 0.4615 → 0.3077）。
2. **完全饱和（对所有分叉递归）**，不能一遇分叉就返回。否则结果依赖
   "先开哪个安全格"（实测同一局面 1.0000 vs 0.8462，两个实现都自洽）。

### 3.7 整局 A/B 前必须先过台架等价性闸

`bench/verify_ab_baseline.py`：`ab_policy` 的 baseline 臂 vs
`sim/eval_harness.py`，判据 `won / died / steps` 逐局相同。

本会话就是靠这道闸抓出我复刻的 `play()` 循环漏了 3 处：
① 每步开头 `drv.in_decision = False`
② `number5_1` 后回写 10/11 标记格
③ stall 判据是"连续 3 次无点击"才 break，不是 1 次

**未过此闸的整局读数一律无效。**

### 3.8 统计口径纪律

- 200 局批次跨批标准差实测 **σ ≈ 3.66pp**。非配对的胜率差小于约 2σ 不可信。
- 必须用**配对设计**（同 seed 同棋盘）+ McNemar 精确检验。
- **统计不显著 ≠ 等效**：只表示"当前样本未检出差异"，不能证明两策略等价，
  也不能证明某策略没有价值。
- 局部局面的 regret 差异**不能外推**为整局胜率变化。

## 4. 常见误判速查表

| 症状 | 实际原因 |
|---|---|
| `ValueError: too many values to unpack (expected N)` | 被 patch 的函数有**两种返回形态**（如 `process_bigger_situation`），wrapper 没透传形态① |
| wrapper 收到的参数整体错位、`args[0]` 是 `Solver` | 把普通函数赋给**类属性**时 Python 自动传 `self`，签名必须显式写 `self` |
| `UnboundLocalError: local variable 'clicks2p' ...` | 只有走 `win_rate` 分支才有 `clicks2p`，降级/贪心分支没有 |
| 同 seed 重跑结果不同 | 没重置 `np.random.seed(seed)` |
| 改阈值无效（两臂结果完全相同） | `_time_budget is None` 时阈值来自常量 `native.LIMIT_BONUS_WIN_RATE` |
| 每局第一步就踩雷 | 屏幕坐标 1-based，反算格子漏减 1 |
| 概率/胜率整体偏移一点 | 世界枚举器列号错位（`clicks[ci]` 应为 `clicks[base+ci]`） |
| 内存暴涨、进程 `0xC0000005`/exit 134 | `wr_f` 的 memo 只写不删 + 节点数组合爆炸；检查 `node_cap` 是否生效 |
| `win_rate` 返回顺序与传入 `clicks` 不一致 | 返回值里的 clicks **已按 safety 降序重排** |
| CSS/UI 断言失败但功能正常 | 既有过时文案断言（`tests/test_ui_heatmap.py:87`），按纪律不改测试 |
