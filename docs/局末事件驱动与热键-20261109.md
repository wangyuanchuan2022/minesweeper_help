## 一、局末 sleep 链改事件驱动

### 问题

253 局实测：265 次、每次中位 2.86s 的**纯空白等待**，合计 734s = **31.7% 墙钟**。
来源是 `utils/solver.py` 4 个胜负分支里写死的：

```
sleep(1.2) + locate_exit() + sleep(1.0) + sleep(0.5) + sleep(0.1) = 2.8s/局
```

这些 sleep 是「等 Arbiter 渲染完成」，实际渲染通常几十毫秒就结束，绝大部分是白等。

### 方案

4 个分支合并为统一入口 `_restart_after_game()`，用**棋盘区域像素变化**做事件驱动判据
（不依赖表情模板语义，避免「点表情后变回普通笑脸、win/lose 模板是否仍命中」这个
我没有真机验证过的假设）：

| 步骤 | 原 sleep | 新判据 | 超时 |
|---|---|---|---|
| ① 局末盘面稳定 | 1.2s | 连续两帧棋盘区域 `array_equal` | 0.6s |
| ② 点关闭/新局按钮 | — | 保留（模板分支点表情、标题分支点 X） | — |
| ③ 新棋盘就绪 | 1.0 + 0.5s | 棋盘像素相对步骤①已变化且连续两帧一致；**兜底**旧胜负表情不再命中 | 2.0s |
| ④ 首点生效 | 0.1s | 首点后棋盘变化且连续两帧一致 | 1.0s |

抓屏用**屏幕 DC 的 BitBlt 区域抓屏**（`BoardVisionMixin._grab_region_bgr`）：
实测抓 720×384 棋盘区域 **6.3ms**，且与 `ImageGrab` 逐像素一致（mean 差 0.002 / max 1）。
轮询间隔 25ms，每轮都检查协作式取消。

**离线验证**（`output/_verify_event_wait3.py`）：完整局末流程 **73ms**（原 2.8s），
仅 2 次 25ms 轮询、零长 sleep；超时场景 128ms 退出不卡死；纯棋盘判据下不依赖任何表情语义。

**可回退**：`MSW_LEGACY_SLEEP=1` 走原固定 sleep 链（4 段 `1.2/1.0/0.5/0.1` 已断言逐值一致），
用于真机 A/B 对照。缺省走事件驱动。这是窄豁免，不动其它路径。

### 顺带修正

- 原 4 个分支 `_gs_save(total, win)` 与 `win += 1` 的先后顺序**不一致**（2 个先存后加、
  2 个先加后存）⇒ `game_stats.json` 偶发少记/多记一局。现统一为「先累加、再落盘、再发帧」。
- `ok` 弹窗原本是**每轮无条件**检测，合并分支时差点被塞进胜负条件里，已保留无条件语义。

### 口径提醒

离线 73ms 是**受控 stub**（棋盘瞬间变化）下的读数，真机渲染耗时未知。
预期节省 2.8s − 实际渲染耗时，但**真实端到端收益尚未实测**，需用户再跑一轮确认。

## 二、locate_exit / 弹窗匹配改为窗口矩形内

### 方案（`utils/vision.py`）

- `_window_rect()`：DPI-aware 取 Arbiter 主窗口矩形（本机 765×600 @ 464,431）。
  ⚠️ 必须先 `import pyautogui` 触发 `SetProcessDPIAware`，否则拿到逻辑坐标 510×400 ⇒ 裁剪错位。
- `_grab_region_bgr(rect)`：屏幕 DC BitBlt（不是窗口 DC）——**含独立顶层弹窗**，
  且实测 6.3ms（PIL 整屏 44.6ms / 区域 38.7ms），逐像素一致。
- `_grab_dialog_screen(pad=24)`：窗口矩形 + 24px 四周扩展 → 813×648。
  padding 是必需的：最宽模板 `ok.png` 158px，紧贴窗口边缘时无 padding 会被裁掉 ⇒
  命中点差 5px（实测）；加 24px 后 `win.bmp`/`lose.bmp` 命中点与整屏**完全一致**，
  `ok.png` 差 1px（亚像素）。
- `_dialog_templates(names)`：一次区域抓屏批量判定多个模板，xy 已换算回屏幕坐标。
- `locate_exit()`：窗口内匹配为主；当 `min > 0.05`（窗口内没找到可信 X，标题弹窗可能
  落在主窗口矩形外）时**自动回退整屏**重新定位。窄豁免，只在不确定时触发。
- `_grab_screen_bgr()` 找不到窗口 / BitBlt 失败 / 被测试 stub 成 None 时，一律透明回退，
  绝不因优化让胜负判定失效。

### 实测

| 项 | 原（整屏） | 新（窗口区域） |
|---|---|---|
| `_dialog_templates` 3 模板 | 1817.9ms | **56.6–62.6ms** |
| 加速 | — | **约 31×** |

> 口径：这是本机离线微基准（无弹窗时的模板匹配耗时），不是端到端收益。
> 253 局里 `vision.match_template` 合计 120.7s（5.2% 墙钟），预期可降到 ~4s 量级，
> 但**真实收益需用户再跑一轮 900 局确认**。

### 坐标换算验证（DPI-aware）

| 模板 | 整屏 xy | 窗口内 xy（+24px padding） | 差 |
|---|---|---|---|
| win.bmp | (848, 539) | (848, 539) | 0 |
| lose.bmp | (847.5, 540.5) | (847.5, 540.5) | 0 |
| ok.png | (925, 489.5) | (924, 489.5) | 1px |
| exit.bmp | (431.5, 845) 伪匹配 min=0.13 | 窗口内 min=0.31 | 由分数回退兜底 |

## 三、紧急终止热键

### 问题（用户指出）

自动模式持续用 `pyautogui` 真实点击，鼠标被程序驱动 ⇒ 用户点不到 GUI 停止按钮；
`pyautogui.FAILSAFE` 又要求把鼠标移到屏幕角落，同样做不到 ⇒ **用户失去终止手段**。

### 方案（`utils/solver.py` 的 `AutoPlayThread`）

后台守护线程轮询 Win32 `GetAsyncKeyState`（**物理键状态**，不依赖窗口焦点、不需要鼠标、
不需要消息循环），命中即调 `request_cancel()` —— 与 GUI 停止按钮**共用同一取消通道**。

- 默认热键 **ESC**（VK 0x1B）
- `MSW_STOP_HOTKEY=0x7B` 改 F12；`=0` 关闭；`stop_hotkey_label()` 给用户看可读名称
- **边沿触发**：按住不重复请求，松开后才能再次触发
- 只监听 `is_play=True`（帮助模式不抢键）
- `start()` 拉起、`run()` finally 收尾，daemon 线程不残留
- 非 Windows / ctypes 失败时静默降级，不影响主流程

### 让取消真正生效（关键）

光置位不够，点击密集链必须能退出。新增 3 个检查点：

1. `probability._number5_1_core` 的 decide 循环每轮开头（原最长要 512 轮才退出）
2. `certain_safe` 批量点击的**每格**循环内（原一次最多连点 64 格 ≈ 1.9s）
3. `_wait_for` 每 25ms 轮询 + `_restart_after_game` 各步骤之间（已有）

### e2e_900.py 的漏洞修复

自动重启逻辑原本会在 `clear_cancel()+start()` 时把**用户刚停掉的线程重新拉起**
⇒ 热键形同失效。现加判据：`cancel_requested()` 为真 ⇒ 不重启、直接退出并标记 interrupted。

### GUI 提示

- 局数输入对话框：显示当前热键名 + 「无需用鼠标点停止按钮」
- 启动后状态栏：`自动运行中 · 按 ESC 可随时紧急终止（无需鼠标）`
- `run_e2e_900.cmd` 头部说明 + `MSW_STOP_HOTKEY` 覆盖方式
- `bench/e2e_900.py` 启动提示

### 验证

- `GetAsyncKeyState` 本机可用（实测 0x1B / 0x7B / 0x10 均可读）
- 4 个新增单测（默认 ESC / 可配置可关闭 / 帮助模式不启动 / 边沿触发）全绿
- 集成模拟：预置取消时 0ms 退出、零点击；中途 0.1s 按热键时 114ms 退出（不等超时）
- 全量 **307 测试通过**（skipped=1）

## 五、待用户确认的口径

1. **真实端到端收益未测**：事件驱动省多少、窗口匹配省多少，需要用户在真实终端
   再跑一轮（建议先 `--games 200`，与 253 局基线同口径对比 `s/局` 与
   `vision.match_template` 合计）。离线 73ms / 31× 都是微基准，不能直接当整局收益。
2. **事件驱动判据的可靠性**：`_reset_done` 主判据是「棋盘像素变化且稳定」，
   兜底是「旧胜负表情不再命中」。若 Arbiter 点表情后的实际渲染行为与假设不同，
   会走满 2.0s 超时才继续（仍比原来 2.8s 快，但收益变小）。真机跑一轮即可确认
   `probe.jsonl` 里的 `game_end.settle` / `game_end.reset` / `game_end.first_click`
   三个 mark 的 `ok` 字段与 `ms` 分布。
3. **A/B 对照**：`MSW_LEGACY_SLEEP=1` 可切回原 sleep 链做同 seed 配对对比。
4. **ESC 冲突**：若用户其它程序占用 ESC，可用 `MSW_STOP_HOTKEY=0x7B`（F12）等覆盖。
