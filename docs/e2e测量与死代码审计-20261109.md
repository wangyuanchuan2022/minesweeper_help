## 一、本轮修掉的一个真实正确性 bug（最重要）

### 现象

C++ OPTIMAL 层返回的逐格安全概率，在同一批 odometer 行上算出两个互相矛盾的数：

| 读数 | 值 | 应有值 |
|---|---|---|
| `transition_meta.world_count`（物化世界数） | **36** | 30 |
| `situations`（准入精确计数 ‖S‖） | 30 | 30 |
| `Σ P(该格是雷)` | **98.666667** | 99（= 剩余雷数） |

两者都由同一批行产生，**数学上必须相等**。三条算术完全闭合：
`ΣP(雷) = [2×12×99 + 2×6×98] / 36 = 98.6667`，分叉量 `36−30=6` 恰等于
「`rem==n9` 的行数 6 × (n9−1)=1」。

### 根因

`cpp/mscore.cpp:get_list_sizes` 与 `utils/combinatorics.py:get_list` 同款 off-by-one：

```c
if (num > listnum - 1) num = listnum - 1;   // 上限被钳到 listnum-1
```

OPTIMAL 物化时调用 `get_list_sizes(rem, rem, n9)`，于是 `rem == n9` 时：
- 正确语义：从 n9 个内部格里放 **n9** 个雷 → `C(n9,n9)=1` 个世界
- 实际行为：放 **n9−1** 个雷 → `C(n9,n9−1)=n9` 个世界，且**每个世界少 1 个雷**

### 影响

- OPTIMAL 层在 `rem==n9` 的行上物化出「雷数不足」的世界 ⇒ 逐格概率错误
- 实测触发率：200 局 / 1333 次 optimal 中 **5 次 = 0.38%**
- 危害：该局面下错误概率可能诱导去点必雷格，输掉本可赢的局

### 修复

```c
if (num > (int64_t)listnum) num = (int64_t)listnum;   // 原为 listnum - 1
```

同步修 Python `get_list`，并修正依赖该钳制的上界估算 `inner_expand_log2_upper`
（`s_hi` 从 `N-1` 放到 `N`；`C(N,N)=1` 不放大上界，保守安全）。

### 验收（可复现）

| 检查 | 结果 |
|---|---|
| `bench/repro_world_count_split.py` | world_count 36→**30**（=‖S‖），ΣP(雷) 98.667→**99.0** |
| `bench/verify_getlist_fix.py --games 200` | 1349 个 optimal 决策点，两条恒等式**全部成立**（最大偏差 9.9e-14） |
| `bench/verify_prob_truth.py` | **74/74** 局面逐格概率与暴力真值完全一致（含 rem==n9 重点组 14 个） |
| `tests/` 全量 | **303 个测试全绿**（skipped=1） |
| 200 局胜率（修复后） | 80/200 = **40.00%** |

> 仪器纪律说明：对拍过程中我曾把 float32 精度差（~4e-8）和暴力枚举被 cap
> 截断（trial=124，应枚举 2718576 个世界只跑到 363258 个）误报成 bug，
> 两处都已修正仪器并加了阳性对照（真值布局必须出现在枚举结果里）。

## 二、顺带修掉的一个健壮性缺陷

`ImageGrab.grab()` 在 Windows 上会**间歇性**抛 `OSError: screen grab failed`
（锁屏切换 / 驱动重置 / 远程会话重连 / 桌面被短暂占用）。

原 `Solver.play()` 只捕 `FailSafeException` 与 `win32ui.error` ⇒ 这个 `OSError`
会把**整条自动线程打死**，用户看到「自动模式突然停了」且界面无任何解释。

修复（两处）：
1. `utils/vision.py:_grab_screen_bgr` —— 短重试 3 次（20ms 间隔），仍失败才上抛；
2. `utils/solver.py:play` —— 新增 `except OSError` 分支：ERROR 日志 + 弹窗告知
   用户具体原因（不再静默死亡），语义与其它两个 fatal 分支一致。

> 这是本轮真实端到端冒烟连续两次撞上的真实故障，不是构造出来的。

## 三、新增的测量能力

### 3.1 端到端探针 `utils/e2e_probe.py`（新文件）

**默认关闭，关闭时零开销**（每个入口第一行 `if not enabled(): return`）。
`MSW_E2E_PROBE=1` 开启，落盘 `state/e2e/probe.jsonl`（JSONL 追加）。

记录六类事件：

| 事件 | 内容 |
|---|---|
| `game_begin` / `game_end` | 每局起止：胜负、墙钟、内存基线/峰值 |
| `span` | 代码段耗时（屏幕抓取 / 模板匹配 / 整盘扫描 / 重扫 / decide / 点击 / UI 渲染） |
| `decision` | 每次 C++ decide：reason、ms、world_upper、situations、DSTAR、prob/tied 规模 |
| `click` | 每次真实点击：坐标、自评安全率、来源、批次大小 |
| `mem` | RSS + commit 采样（默认 2Hz） |
| `mark` / `error` | 运行时功能覆盖打点 / 生产侧捕获的异常告警 |

**接线点**（全部在热路径外或微秒级）：
`utils/vision.py`（抓屏/匹配/扫描/重扫/低置信度）、`utils/probability.py`
（decide/点击/决策失败）、`utils/solver.py`（局生命周期/主循环各段/异常）、
`main.py`（UI 渲染帧/样式变更/进程启动收尾）。

### 3.2 分析器 `bench/analyze_e2e.py`（新文件）

把探针 JSONL 分成四份账，正是你问的四件事：

1. **性能** —— 每个 span 的 n/中位/p90/p99/合计/占整局比，指出最大热点
2. **准确性** —— reason 分布、decide 耗时分布、‖S‖ 分布、点击自评安全率分布
3. **功能是否实现** —— `mark`/`error` 计数（运行时证据，回答「哪些代码真的被调到」）
4. **内存** —— commit 序列分 5 段的趋势形态（区分锯齿=系统回收 vs 单调=真泄漏）

### 3.3 900 局真实端到端跑者 `bench/e2e_900.py` + `run_e2e_900.cmd`（新文件）

跑的是**生产真实链路**：真实 Arbiter → 真实截图 → 模板识别 → C++ decide →
真实鼠标点击 → GUI 实时渲染。不是模拟器。

- 直接起 `main.MyMainWindow()`（与生产同一个类、同一套信号接线），
  后台 `Solver` QThread 与生产完全一致 ⇒ `heatmap_signal → update_heatmap`
  的真实渲染路径全部被走到并计时
- 前置检查：Arbiter 在前台、原生模块可用、棋盘抓取尺寸/灰度合理
- 断点续跑（`--resume`）、单实例锁、墙钟上限
- **自动重启**：环境性线程死亡（如抓屏失败）记录后重启续跑，超 30 次才判真故障
- 跑完自动调分析器 + 死代码审计，出 `state/e2e_900/report.md`

## 五、怎么跑 900 局（需要你在真实终端执行）

**为什么必须你跑**：沙箱进程是 **Low 完整性级别**，而 Arbiter 是 Medium IL。
实测确认：`SetCursorPos` / `SendInput` / `PostMessage` 全部被拒
（`pywintypes.error: (0, 'SetCursorPos', ...)` / `(5, 'PostMessage', 拒绝访问)`），
且 `ImageGrab` 在沙箱内会间歇性失败。这不是代码问题，是权限边界。

**步骤**：

1. 确认 Arbiter 已运行、窗口可见、不被遮挡
2. 双击项目根目录的 **`run_e2e_900.cmd`**
3. 它会依次做：前置检查 → 跑 900 局 → 分析探针 → 死代码审计
4. 中断后重跑同一个文件即可续跑（`--resume`）

**产出**：

```
state\e2e\probe.jsonl          探针原始事件
state\e2e_900\games.jsonl      逐局明细
state\e2e_900\summary.json     汇总（胜率/CI/墙钟/内存峰值/pyd sha）
state\e2e_900\report.md        四份账的分析报告
state\audit\dead_code.md       死代码 + 合并候选
```

**跑完请把控制台输出（或上面几个文件）带回来**，我做归因与优化建议。
重点会看：

- 哪个 span 占整局墙钟最大（预期：整屏模板匹配 4 次，本机实测单次 135–616ms）
- `decide` 的 reason 分布是否与历史口径一致（`certain_safe`/`optimal`/`memory_gate`）
- 内存 commit 是否单调上升（真泄漏）还是锯齿（系统回收）
- 有无 `error` 事件（决策失败 / 抓屏失败 / 线程异常）
