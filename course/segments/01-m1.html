1 · 模板仓库：程序是怎么认出「3」的

你把扫雷窗口打开，程序做的第一件事不是推理，而是「看」。它看的方式很朴素：给每个格子拍小照，然后跟 25 张标准小卡片逐一比对——最像谁，就是谁。这些卡片全部住在 image/ 目录里，登记册写在 utils/vision.py 的 _TEMPLATE_LAYOUT。

结构层先定位：这个模块讲的是 utils/vision.py 里的 BoardVisionMixin——它是 Solver 三大 Mixin 之一（视觉 / 推理 / 概率），只负责「认字」，不负责「想」。它依赖的原料只有两样：image/ 目录的 33 个文件（其中 25 张是格子模板），和实例属性 cell_width（每个格子多少像素宽，来自 cfg.json）。

📄 真实代码 utils/vision.py · L23-L36 
    # 每个格子数字对应的模板文件（顺序与 self.images 一致）
    _TEMPLATE_LAYOUT = [
        ["0.bmp", "0_1.bmp", "0_2.bmp"],
        ["1.bmp", "1_1.bmp", "1_2.bmp"],
        ["2.bmp", "2_1.bmp"],
        ["3.bmp", "3_1.bmp"],
        ["4.bmp", "4_1.bmp"],
        ["5.bmp", "5_1.bmp"],
        ["6.bmp", "6_1.bmp"],
        ["7.bmp", "7_1.bmp"],
        ["8.bmp", "8_1.bmp"],
        ["9.bmp", "9_1.bmp", "9_2.bmp"],
        ["10.bmp", "10_1.bmp"],
    ]
这张二维表是整个识别系统的「分格抽屉」：一行代表一种识别结果（0~8 是数字、9 是未开、10 是雷），抽屉里放这个数字的 2~3 个外观变体。数一数正好 25 个 bmp 文件，与 image/ 目录清点一致。识别时在整张表里找「最像的行」，行号就是格子值。

为什么同一个数字要备 2~3 张卡？因为 Arbiter 扫雷的同一数字在不同主题、不同底色下渲染不同——备齐变体，模板匹配才能跨主题工作。这也是「换皮肤后识别失灵」的第一排查点：新外观没登记进对应行。

📊 模板库存：25 张 bmp 的分布（清点自 _TEMPLATE_LAYOUT）
📄 真实代码 utils/vision.py · L38-L63 
    def _template_mtime(self):
        """返回所有格子模板文件的最大修改时间，作为缓存指纹。"""
        try:
            return max(
                os.path.getmtime(os.path.join("image", fname))
                for row in self._TEMPLATE_LAYOUT
                for fname in row
            )
        except OSError:
            return -1.0
    def load_img(self):
        """加载格子模板；仅在 cell_width 变化或模板文件更新时重新读取。"""
        mtime = self._template_mtime()
        if (
            self.images is not None
            and self._images_cell_width == self.cell_width
            and self._images_mtime == mtime
        ):
            return
        self.images = [
            [cv.imread(os.path.join("image", fname)) for fname in row]
            for row in self._TEMPLATE_LAYOUT
        ]
        self._images_cell_width = self.cell_width
        self._images_mtime = mtime
缓存指纹 = 25 个模板文件的最大修改时间。你用「截图帮助」重新截一张模板存盘，mtime 立刻变化——缓存自动失效，无需重启程序。
三个条件全满足才跳过重读：已经加载过、格子宽度没变、模板文件没动过。reload()（换设置后）和每次扫描都会调用 load_img()，但真正的磁盘读取只发生在这三者之一变化时。
真正重读时，按 _TEMPLATE_LAYOUT 的行列结构把 25 张图读进嵌套列表 self.images——结构与登记册一一对应，后面的匹配循环完全由这个结构驱动，代码里没有任何写死的「25」。

🎯 押一注：模板匹配抛异常时，这个 except 会怎么收场？

下面这段 compare_img 里藏着一个 except cv.error: pass。假设某次格子切片的尺寸和模板对不上，cv.matchTemplate 抛了异常——先押一注，再看代码。

📄 真实代码 utils/vision.py · L117-L131 
    def compare_img(self, img, no_10):
        result = np.ones((11, 3)) * 100
        for i in range(len(self.images)):
            for j in range(len(self.images[i])):
                try:
                    res = cv.matchTemplate(img, self.images[i][j], cv.TM_SQDIFF_NORMED)
                    result[i, j] = np.sum(res)
                except cv.error:
                    pass
        res = np.unravel_index(np.argmin(result, axis=None), result.shape)[0]
        if no_10:
            if res == 10:
                res = 9
        return res
「拿 25 张身份证逐一比对」：双重循环遍历每个数字的每个变体，TM_SQDIFF_NORMED 算归一化平方差（0 = 完全一致，越大越不像）。result 预填 100，配合 except: pass——失败的比对自动出局，不会中断整盘扫描。
全矩阵找最小差值，取行号（0~10）作为识别结果。no_10 是模式开关：自动模式传 True，识别成「雷」（行 10）一律塌缩回「未开」（9）——对局未结束时棋盘上不该出现已揭示的雷，识别出 10 基本是误判；帮助模式传 False，保留雷识别（比如你自己标过的旗）。

为什么这样设计：不用 OCR（如 Tesseract）而用模板匹配，是因为扫雷数字字体固定、总量只有 11 种，却存在主题渲染差异——把「字典」做成 25 张小图（每个数字多个变体），零训练、零额外依赖，且 compare_img 完全由 self.images 的结构驱动。换 OCR 反而引入依赖、拖慢每格识别。而阈值法（比像素颜色）在主题一换就全灭。_TEMPLATE_LAYOUT 的二维结构就是留给「换主题」的扩展缝：加变体只动数据，不动算法。
