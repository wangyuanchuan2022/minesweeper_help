4 · 单格判定：数字自己就能说清的事

棋盘认完了（m1–m3），现在开始「想」。推理引擎一共三层：单格规则 number0 → 双格规则 number_3_1 → 概率引擎 number5_1。本模块讲第一层——一个数字格自己就能宣布的确定结论，玩家熟悉的「清点包围圈」。

结构层定位：utils/deduction.py 的 DeductionMixin，Solver 的第二个 Mixin。它消费 cell_value 沙盘（m2 的产物），产出两种确定标记——10（是雷）和 11（确认安全但还没点开）。所有方法都围绕一个朴素问题：这个数字周围还剩几个 9、几个 10？

📄 真实代码 utils/deduction.py · L14-L24 
    def cell_around(self, i, j, cell_value):
        cnt9 = 0
        cnt10 = 0
        for n in range(j - 1, j + 2):
            for m in range(i - 1, i + 2):
                if 0 <= m <= self.w + 1 and 0 <= n <= self.h + 1:
                    if cell_value[n, m] == 9:
                        cnt9 += 1
                    if cell_value[n, m] == 10:
                        cnt10 += 1
        return cnt9, cnt10
全项目被调用最多的函数之一：数一数 (i, j) 周围 3×3 里有几个未开（9）几个已标雷（10）。注意它把中心格自己也扫了——中心是数字不会是 9/10，多扫无害，换来循环不用特判。行边界检查 0 <= m <= w+1 看似多余（m2 讲过有零边框），其实兜的是「m 取到 w+1 本身合法」这一侧——边框格永远是 0，同样无害。

    def number0(self, i, j, cell_value):
        c = False
        cnt9, cnt10 = self.cell_around(i, j, cell_value)
        if not cnt10 <= cell_value[j, i] <= cnt9 + cnt10:
            raise ValueError("识别错误")

先做一致性体检：真实棋盘里，一个数字周围「已标雷数」不能超过数字本身，「未开 + 已标雷」不能少于数字——违反即识别出了错（合法局面不可能出现）。这个 ValueError 是整个推理层唯一的报警器，两种模式的接法截然不同（见下方赌注）。
规则一（全雷）：未开 + 已标雷 == 数字，说明雷全在剩下的未开格里——全部写 10。帮助模式下不点击，只把结论记进 pos_dict_list（置信度 0 = 是雷），appended_pos 防止同一结论重复进列表；self.cell_value（原始扫描快照）还要二次确认这格视觉上真是 9，防止「推理标记」污染「视觉事实」。

规则二（全安全）：雷已凑满数字，剩余未开格必安全。is_play 在这里分叉两个驾驶舱：自动模式直接 pyautogui.click 屏幕坐标（m2 的换算链），帮助模式写 11 + 记录 pos_dict（置信度 1）。同一个推理函数服务两种交互形态，这就是「一套引擎两个驾驶舱」。
收尾同样按模式分叉：帮助模式 num += 1（推理轮次计数，供 GUI 分批显示），自动模式立刻 rescan_after_click（m3 的增量重扫）——点击改变了世界，推理必须马上看到新证据才能继续。
🛤️ 把一条「全安全」结论拖过驾驶舱岔口

同一个 number0、同一个结论，两种模式的执行路径完全不同。岔路口就是 pair-m4-safe 翻译块里的 if self.is_play——切换驾驶舱投放令牌，看结论分别变成什么动作。

为什么这样设计：用 11 而不是把安全格改成某个数字，是因为 0–8 属于「视觉识别的事实」，11 属于「推理得出的结论」——两者必须可区分：帮助模式的按钮网格靠这个差别渲染推理产物（m9），complete_scan 靠它知道哪些 9 格已被推理接管。而 is_play 单开关贯穿全部推理代码，代价是推理层混入了 IO（点击）——HANDOFF 文档的 T4「解耦 GUI 和业务逻辑」正是冲着这个来的。
