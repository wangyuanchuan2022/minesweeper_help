5 · 双格判定：两份名单互相勾稽

m4 的两条规则只会「清点包围圈」——一个数字格自己就能说清的事。但扫雷里最锋利的确定性推理，往往要两个数字格把各自的账本摊开来互相对：你的名单上有谁、我的名单上有谁、谁被两份名单同时记着。number_3_1 就是玩家口中的 1-1、1-2 模式的程序化——把这种「两份名单互相勾稽」写成三次集合运算。

从一个真实的小局面说起。棋盘一角摆出这样一排：上排两个已开数字格 1 和 2 肩并肩，下排贴着四个未开格（记作 a、b、c、d）。1 号的名单是 {a, b, c}，2 号的名单是 {b, c, d}——b、c 同时被记在两份名单上，d 只归 2 号管。单格规则逐一试过：1 号周围 3 个未开、0 个已标雷，3 + 0 ≠ 1，凑不出「刚好相等」；2 号同样 3 + 0 ≠ 2。两条规则全部沉默——但两张名单正要开始互相勾稽。

        x1 = cell_value[j, i]
        a, cnt10 = self.get_set(i, j, cell_value)
        x1 -= cnt10
        if x1 <= 0:
            return cell_value
        for x in range(i - 2, i + 3):
            for y in range(j - 2, j + 3):

锚点是 (i, j)——例子里那个 1。x1 先做一次「扣除」：get_set 顺手数出它周围已标了几雷（cnt10），从数字里减掉，得到「还有几个雷没着落」；差值 ≤ 0 说明雷已标满，这格没信息量，直接收工（m4 规则二管过的地方不必再来）。然后开一个 5×5 扫描窗逐格找搭档——窗为什么是 5×5 而非 3×3，答案在下方 mine_clear3_1 的翻译块。搭档资格只有一条：是 1 到 7 的数字格（0 是已开空格，9 及以上不是数字）。
三行集合算术就是整个算法的核心（对应动画第 3 帧）：bj 是两份名单的并集；x_set = bj − b，即 1 号名单里 2 号名单没有的——1 号独占区；z_set 反过来是 2 号独占区；y_set 是两份名单的重叠区。x2 同样先扣掉自己已标的雷。三区把「谁归谁管」一刀切干净——之后的推理只对这三区做算术，不再关心具体格子长什么样。
差值条件是两份账本相减：1 号地盘（x_set ∪ y_set）记 x1 个雷，2 号地盘（y_set ∪ z_set）记 x2 个——公共区 y_set 两边各记一次，相减时自动消掉，得「x_set 与 z_set 的雷数之差 = x1 − x2」。当这个差恰好等于 1 号独占区的格数时，唯一解是 x_set 塞满雷（写 10）。帮助模式顺手把一条「人话证明」记进 pos_dict_list——exp 字段就是 m9 弹窗里原样显示给用户的推理理由。
同一枚硬币的反面：x_set 必须满，差值才凑得齐；而 z_set 此刻被挤得一格雷不剩——2 号独占区全部安全。z_set 的格子要逐个确认还是 9 才动手（已被推理写成 10/11 的不重复处理），is_play 在这里分叉「直接点击」或「标 11 + 记推荐」，与 m4 完全同构。对称的另一半在 L182：x2 − x1 == len(z_set)，方向整个反过来——动画第 4 帧演的正是这个镜像条件（例子里 2−1 == 1 = len({d})）。

    def get_set_1(self, i, j, cell_value):
        result = set()
        for n in range(j - 1, j + 2):
            for m in range(i - 1, i + 2):
                if 0 <= m <= self.w + 1 and 0 <= n <= self.h + 1:
                    if 0 < cell_value[n, m] < 8:
                        result.add((m, n))
        return result
    def get_set(self, i, j, cell_value):
        result = set()
        cnt10 = 0
        for n in range(j - 1, j + 2):
            for m in range(i - 1, i + 2):
                if 0 <= m <= self.w + 1 and 0 <= n <= self.h + 1:
                    if cell_value[n, m] == 9:
                        result.add((m, n))
                    elif cell_value[n, m] == 10:
                        cnt10 += 1
        return result, cnt10
get_set_1 收集的不是格子，是「数字格名单」——(i, j) 周围 3×3 里所有 1 到 7 的数字格坐标。有趣的是它在 deduction.py 里没有任何调用者：全仓库只有 m6 概率引擎的分组循环用它（probability.py L109/L115）。定义放在推理层，用家在概率层——先在这认识它，m6 里它会回来当主角。
get_set 是 number_3_1 的原料供应商，一次调用交两样货：周围 3×3 的未开格坐标集合（result），以及已标雷计数（cnt10）。对比 m4 的 cell_around：那边只数个数、回答「几个」，这边交坐标集合、回答「哪些」——双格推理必须知道「谁跟谁重叠」，光有计数勾稽不起来。已标的雷（10）不进名单，只折进 cnt10 直接从数字里扣掉。

为什么用集合交并差，而不是逐格计数？因为要证的东西本身就是集合层面的恒等式：x_set ∪ y_set 记 x1 个雷、y_set ∪ z_set 记 x2 个，两笔账一减 y_set 自动消掉——三行运算（L124-L127）就是完整证明，对任何局形成立，不用枚举任何具体格子。换成「对每个格子讨论是不是雷」的写法，同样的结论要嵌套两重循环加一堆边界讨论，还容易把「恰好」写成「至少」。为什么逐对勾稽，而不是把所有数字格连成一张约束图一次求解？因为约束满足的搜索空间随格子数指数膨胀——m6 的 limit（每加 1 计算时间翻倍）就是这堵墙的直接证据。逐对勾稽一次只看两个数字格：外层扫一遍棋盘、每个锚点只在 5×5 邻域里找搭档，成本与格子数成正比；全局求解则交给概率引擎，而且还得先分组降维（m6 的主题）。

    def mine_clear3_1(self, cell_value, clicks=None):
        if clicks:
            for i, j in clicks:
                cell_value = self.number_3_1(i, j, cell_value)
            return cell_value
        for i in range(2, self.w):
            for j in range(2, self.h):
                if 0 < cell_value[j, i] < 8:
                    if self.cell_around(i, j, cell_value)[0] > 0:
                        cell_value = self.number_3_1(i, j, cell_value)
        return cell_value
驱动器：外层两重循环决定「谁当锚点」——i 从 2 到 w−1、j 从 2 到 h−1，最外圈的数字格不做锚点（配对中只要有一格不在最外圈，这个组合就会被另一半的 5×5 窗扫到）。两道预筛：得是数字格（0 < v < 8），且周围确实还有未开格（cell_around 的 cnt9 > 0——没有 9 的格连名单都交不出来）。过了筛才调 number_3_1，进它自己的 5×5 找搭档。为什么是 5×5：两个数字格要有共同的邻居，各自的 3×3 邻域必须相交——锚点邻域最远伸到 i+1，搭档邻域最近从 x−1 开始，要相遇必须 x−1 ≤ i+1，即 x ≤ i+2（对称得 x ≥ i−2）。距离 3 以上的两个数字格连一个共同格子都没有，勾稽无从谈起，多扫一格都是白费。带 clicks 参数的版本与 m4 的 mine_clear1 同构：定点处理指定格——m6 分组重算时走的正是这条路。
