9 · 帮助模式：一套引擎，两个驾驶舱

m8 结束时，概率引擎已经能在死局里给每一格算出胜率。但这些数字躺在 cell_value 矩阵里，用户一个也看不见——本模块讲它们怎么变成屏幕上的东西：用户点下「帮助」按钮后的一次扫描分析、一份 pos_dict_list 推荐清单、一张按概率着色的按钮网格，和一段点开就能看的推理理由。

        for i in range(steps):
            t = i / (steps - 1)  # 0到1的插值参数

            # 找到当前t在哪个颜色段
            segment_length = 1.0 / (len(colors_oklch) - 1)
            segment_index = min(int(t / segment_length), len(colors_oklch) - 2)
            segment_t = (t - segment_index * segment_length) / segment_length
            # 计算最短的色调路径（考虑360°循环）
            hue_diff = end_H - start_H
            if abs(hue_diff) > 180:
                if hue_diff > 0:
                    start_H += 360
                else:
                    end_H += 360

            # 线性插值
            L = start_L + (end_L - start_L) * segment_t
            C = start_C + (end_C - start_C) * segment_t
            H = start_H + (end_H - start_H) * segment_t
            H = H % 360  # 确保色调在0-360范围内
渐变生成器：100 步，每步算一个 0 到 1 的插值参数 t，先把两端颜色转到 OKLCH 色彩空间（rgb_to_oklch，color.py L20-L62），再在空间里插值。调用方只有一行（main.py L56）：oklch_grad = gradient_gen.create_gradient([(1, 0, 0), (0, 1, 0)])——纯红到纯绿，100 步。
插值本身是三个分量各自线性：亮度 L、色度 C、色调 H。色调是 360 度的环，必须走最短路径（否则红到绿可能绕远路经过紫蓝）；OKLCH 的坐标是为人类视觉的正交性设计的——等步长的插值看起来也等步长，这是中段不脏的根源。

为什么这样设计：温度计为什么不用 RGB 直接插值？纯红 (1,0,0) 和纯绿 (0,1,0) 的 RGB 中点是 (0.5,0.5,0.5)——一摊灰色，既不像红也不像绿；而帮助模式里大量格子恰恰落在渐变中段（五五开的局面最常见），中段失真等于最重要的信息失真。OKLCH 里亮度与色度分离，中段是仍然鲜艳的橙黄过渡。color.py 的 example_usage（L192-L263）还留着与 HSL 渐变的对照实验可自行运行。至于「一键点击」：着色时攒好的两份清单由 click_all_func（main.py L627-L656）统一执行——先遍历 self.clicks 逐格左键点开（L634-L640），再按住 Ctrl 右键遍历 self.mines 把雷旗插上（L642-L650），执行完清空清单、锁按钮，等待下一轮「帮助」。
