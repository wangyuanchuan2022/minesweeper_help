1 · 模板仓库：程序是怎么认出「3」的

你把扫雷窗口打开，程序做的第一件事不是推理，而是「看」。它看的方式很朴素：给每个格子拍小照，然后跟 25 张标准小卡片逐一比对——最像谁，就是谁。这些卡片全部住在 image/ 目录里，登记册写在 utils/vision.py 的 _TEMPLATE_LAYOUT。

结构层先定位：这个模块讲的是 utils/vision.py 里的 BoardVisionMixin——它是 Solver 三大 Mixin 之一（视觉 / 推理 / 概率），只负责「认字」，不负责「想」。它依赖的原料只有两样：image/ 目录的 33 个文件（其中 25 张是格子模板），和实例属性 cell_width（每个格子多少像素宽，来自 cfg.json）。

这张二维表是整个识别系统的「分格抽屉」：一行代表一种识别结果（0~8 是数字、9 是未开、10 是雷），抽屉里放这个数字的 2~3 个外观变体。数一数正好 25 个 bmp 文件，与 image/ 目录清点一致。识别时在整张表里找「最像的行」，行号就是格子值。

📄 真实代码 utils/vision.py · L117-L131 
    def compare_img(self, img, no_10):
        result = np.ones((11, 3)) * 100
        for i in range(len(self.images)):
            for j in range(len(self.images[i])):
                try:
                    res = cv.matchTemplate(img, self.images[i][j], cv.TM_SQDIFF_NORMED)
                    result[i, j] = np.sum(res)
                except cv.error:
                    pass
        res = np.unravel_index(np.argmin(result, axis=None), result.shape)[0]
        if no_10:
            if res == 10:
                res = 9
        return res
「拿 25 张身份证逐一比对」：双重循环遍历每个数字的每个变体，TM_SQDIFF_NORMED 算归一化平方差（0 = 完全一致，越大越不像）。result 预填 100，配合 except: pass——失败的比对自动出局，不会中断整盘扫描。
全矩阵找最小差值，取行号（0~10）作为识别结果。no_10 是模式开关：自动模式传 True，识别成「雷」（行 10）一律塌缩回「未开」（9）——对局未结束时棋盘上不该出现已揭示的雷，识别出 10 基本是误判；帮助模式传 False，保留雷识别（比如你自己标过的旗）。

为什么这样设计：不用 OCR（如 Tesseract）而用模板匹配，是因为扫雷数字字体固定、总量只有 11 种，却存在主题渲染差异——把「字典」做成 25 张小图（每个数字多个变体），零训练、零额外依赖，且 compare_img 完全由 self.images 的结构驱动。换 OCR 反而引入依赖、拖慢每格识别。而阈值法（比像素颜色）在主题一换就全灭。_TEMPLATE_LAYOUT 的二维结构就是留给「换主题」的扩展缝：加变体只动数据，不动算法。

def ClientToScreen(hwnd, x, y):
    rect = ctypes.wintypes.RECT()
    ctypes.windll.user32.GetWindowRect(
        ctypes.wintypes.HWND(hwnd),
        ctypes.byref(rect),
    )
    win_x, win_y, _, _ = rect.left, rect.top, rect.right, rect.bottom
    return win_x + x, win_y + y
    def _grab_board(self):
        """抓取棋盘区域并转为 BGR，同时更新 self.img。"""
        hwnd = win32gui.FindWindow(None, setting.win_name)
        bx, by = ClientToScreen(hwnd, self._bx, self._by)
        pil_img = ImageGrab.grab(
            (
                bx + 0.5 * self.cell_width,
                by + 0.5 * self.cell_width,
                self.w * self.cell_width + bx + 0.5 * self.cell_width,
                self.h * self.cell_width + by + 0.5 * self.cell_width,
            )
        )
        pil_img = np.array(pil_img)
        self.img = cv.cvtColor(pil_img, cv.COLOR_RGB2BGR)
        return self.img
注意一个「名不副实」：函数叫 ClientToScreen，实现却是拿 GetWindowRect 的窗口矩形左上角做原点——含标题栏和边框，不是真正的客户区。校准（m11）会把这个偏差连同 cell_width*0.5 的半格回退一起算进 bx/by，所以整条链路自洽，但读代码时别被名字骗了。
四元组的含义：从 bx + 0.5 格起步、宽 w × cell_width——每格从「格子中心」开始取，跨过格与格之间的边线；PIL 抓的是 RGB，OpenCV 的模板是 BGR 读入，所以中间必须 cvtColor 转一次通道序，否则比对全错。

    def _slice_cell(self, board_img, i, j):

        y = j * self.cell_width

        h = self.screenshot_h

🧅 剥一颗数据洋葱：一个「3」是怎么来的

最外层是推理引擎直接消费的数字，往内逐层剥回屏幕像素——每一层都有明确的手，也丢了东西。

为什么这样设计：不用逐格截图（每格一次 ImageGrab 要向系统请求几百次），而是一次抓整盘、内存里切片——把 I/O 次数从 480 降到 1。(h+2)×(w+2) 的边框约定则用一点内存（约 3% 的额外格子）换掉全部越界判断。两个决定都是「数据布局服务于算法形状」的典型。

3 · 点击后增量重扫：多米诺倒下之后

自动模式里程序刚点开一格，扫雷的 flood-fill 可能瞬间翻开一大片——像推倒一张多米诺。下一轮推理需要最新的棋盘，全盘重识别太贵，于是这里有一条「像素指纹」快速通道：只对真正变了的格子重新认字。

    def rescan_after_click(self, cell_value):
        """点击后重扫：抓取新棋盘，只重新识别发生变化的未开格子。

        扫雷点击空白格会触发 flood-fill，实际打开的区域可能远大于 5×5，
        因此不能固定扫描 5×5 窗口，而是对「所有仍标记为未开(9)」的格子做变更检测，
        只对真正变化的格子重新做模板匹配。
        """
        old_img = self.img
        self._grab_board()
        for y in range(1, self.h + 1):
            for x in range(1, self.w + 1):
                if cell_value[y, x] == 9:
                    new_cell = self._slice_cell(self.img, x, y)
                    old_cell = (
                        self._slice_cell(old_img, x, y) if old_img is not None else None
                    )
                    if self._cell_changed(old_cell, new_cell):
                        cell_value[y, x] = self.compare_img(new_cell, no_10=True)
        return cell_value

📄 真实代码 utils/vision.py · L149-L155 
    @staticmethod
    def _cell_changed(old_cell, new_cell, threshold=3.0):
        """比较新旧格子图像，判断是否发生变化（用于点击后只重扫变化区域）。"""
        if old_cell is None or old_cell.shape != new_cell.shape:
            return True
        diff = np.abs(old_cell.astype(np.int16) - new_cell.astype(np.int16))
        return float(diff.mean()) > threshold
像素指纹比对：两张切片逐像素做差、取绝对值、再求全图均值——一个标量概括「这格变没变」。先 astype(np.int16) 再相减是防 uint8 的无符号回绕（200 - 250 会绕成 206 而不是 -50）。阈值 3.0 意味着平均每个通道只动 3 个灰阶就算「变了」，抗轻微反光，但挡不住「浅色数字 vs 浅色背景」这种 2.9 的边界情形。

4 · 单格判定：数字自己就能说清的事

棋盘认完了（m1–m3），现在开始「想」。推理引擎一共三层：单格规则 number0 → 双格规则 number_3_1 → 概率引擎 number5_1。本模块讲第一层——一个数字格自己就能宣布的确定结论，玩家熟悉的「清点包围圈」。

结构层定位：utils/deduction.py 的 DeductionMixin，Solver 的第二个 Mixin。它消费 cell_value 沙盘（m2 的产物），产出两种确定标记——10（是雷）和 11（确认安全但还没点开）。所有方法都围绕一个朴素问题：这个数字周围还剩几个 9、几个 10？

📄 真实代码 utils/deduction.py · L14-L24 
    def cell_around(self, i, j, cell_value):
        cnt9 = 0
        cnt10 = 0
        for n in range(j - 1, j + 2):
            for m in range(i - 1, i + 2):
                if 0 <= m <= self.w + 1 and 0 <= n <= self.h + 1:
                    if cell_value[n, m] == 9:
                        cnt9 += 1
                    if cell_value[n, m] == 10:
                        cnt10 += 1
        return cnt9, cnt10
全项目被调用最多的函数之一：数一数 (i, j) 周围 3×3 里有几个未开（9）几个已标雷（10）。注意它把中心格自己也扫了——中心是数字不会是 9/10，多扫无害，换来循环不用特判。行边界检查 0 <= m <= w+1 看似多余（m2 讲过有零边框），其实兜的是「m 取到 w+1 本身合法」这一侧——边框格永远是 0，同样无害。

5 · 双格判定：两份名单互相勾稽

            return hashed_cell_value

            assert len(_cell_value_list) > 0
            try:
                return self.memory[hash_cell_value(_cell_value_list[0])]
            except KeyError:
                pass

            if len(_cell_value_list) == 1:
                return 1
            if depth > depth_limit:  # 防止死循环
                return 1
                for new_uv_value, new_cell_value_list in new_cell_value_dict.items():
                    trans_prob = len(new_cell_value_list) / total
                    new_clicks = clicks.copy()
                    new_clicks.pop(i)
                    win_r = f(new_clicks, new_cell_value_list, depth + 1)
                    win_p += trans_prob * win_r
                _res.append(win_p)

            self.memory[hash_cell_value(_cell_value_list[0])] = max(_res)

            return max(_res)
深度预算：depth_limit = 200/len(clicks)——候选格越多，深度上限压得越紧，两者的乘积约恒定 200。self.memory 是登记簿本簿，进门先清空（L654）——它的生命周期是一次搜索，不跨局复用。
f 的门口两道闸：先查登记簿——用局面的身份证号（哈希）查，命中直接返回存档，整棵等价子树免算；再过深度剪枝——只剩一种局面（没有分歧，当作赢）或 depth 超限（防死循环的乐观截断）都返回 1，不再细分。
f 的主体在两段之间（L674-L695，含按胜率排序与逐格剪枝）：把所有假设局面按「点这格会开出什么数字」分桶，每桶按转移概率递归下一层，全部返回后取 max——这格的期望胜率。算完写进登记簿（L705），同样局面下次进门即中。

为什么这样设计：给每个局面发身份证号，进门先查登记簿。搜索树里大量节点其实是同一个局面的不同到达顺序——先点甲再点乙，与先点乙再点甲，走到中间态时手里往往是同一批剩余局面。等价局面归并成同一个键，等价子树就只算一次：这是把「指数级搜索」压回可解的第二刀（第一刀是 m7 的剪枝）。
